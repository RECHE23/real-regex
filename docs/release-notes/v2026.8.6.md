# v2026.8.6 — the non-ASCII paths, and what a call costs before it scans anything

Three changes, one theme: work that happens *before* the scan, and work on text that is not ASCII.
Every match count, span and capture group is identical to v2026.8.5, on both ISAs.

## A standalone `search()` was building two heap containers it never used

`search()` constructs a fresh VM state. Two of that state's containers were
`std::vector<std::uint64_t>` mark tables, and `reset` reallocates whenever `mark.size() != code_size`
— which within one walk happens once, but on a standalone search happens **every call**, because the
state is fresh and its size is 0. On a 16-byte subject:

| pattern | before | after | |
| --- | ---: | ---: | ---: |
| `[a-z]+` | 59.4 ns | **44.5** | −25.1 % |
| `hello` | 65.6 | **50.8** | −22.5 % |
| `^[a-z]+$` | 59.9 | **47.7** | −20.4 % |
| `(a)(b)` | 74.6 | **59.3** | −20.5 % |

**The saving is not the avoided allocation, and that distinction decided the design.** It shows up on
patterns that never allocate at all — shape routes allocate exactly zero per search, measured. What
it removes is `std::vector`'s destructor from a state every call builds and tears down, so the inline
capacity is irrelevant to the gain and is deliberately small.

**The two halves of this change belong together or not at all**, each having been measured alone:

| variant | short-subject latency | x86-64 class-scan | arm64 |
| --- | --- | --- | --- |
| SBO mark table alone | −20…−25 % | **+10 %** | — |
| `noinline` on `reset` alone | nothing | **+5.8 %** | — |
| **both** | **−20…−25 %** | **−14 %** | flat |

Outlining `basic_thread_list::reset` has no value of its own — alone it makes `words` 5.8 % *slower*
and buys nothing cold. It pays only by repairing the codegen the type change costs gcc: `mark.assign`
is a per-element `construct_at` loop whose mere presence spends the translation unit's inline budget
on class-scan routes that never build a thread list. Together, on x86-64: **`words` −14.1 %** and its
ASCII witness −13.9 % (two instances of one pattern, so not layout noise), `digits` −13.7 %,
`[à-ÿ]+` −11.6 %. arm64 is flat.

**A compile-time ceiling nobody had announced is gone with it.** `small_vec::reserve` threw
`std::bad_alloc` during constant evaluation, so a `constexpr real::regex` whose program outgrew the
scratch's inline buffers broke the **build** — and an 18-instruction pattern was already enough.
Growth now goes through `std::allocator`, the only constexpr-usable source in C++20; its blocks are
transient, so the destructor releases unconditionally. Two latent bugs came out with it: both moves
left `is_heap_` false without reactivating the inline buffer, and a heap-target/inline-source
assignment wrote through an inactive union member.

## The prefilter thought every UTF-8 byte was the rarest byte there is

`byte_frequency` returned 1 — its rarest rank — for **every** byte ≥ 0x80. So `café` picked as its
`memchr` target the `0xC3` that leads every accented Latin letter: one byte in six of French prose,
chosen in the belief that it was rare. Against an ASCII literal of the same match density in the same
corpus, that ran **6.3× slower** (1.761 vs 0.279 ns/B). Ranked by *selectivity* instead — a lead byte
stands for 64 or more characters, so it cannot discriminate like one ASCII byte — it is **0.258**, at
parity. CJK is untouched by construction: a script whose text is nothing but high bytes still picks
its lead exactly as before.

## The document's worst ratio, and the diagnosis that was wrong

`(?i)café` sat at **0.26×** against PCRE2-JIT. The obvious reading — that case-insensitivity is the
cost — is **false**: plain `café` used to be *slower* than `(?i)café`, because the fold is what turns
`é` into a code-point class, and that is what stops the prefilter's fixed-offset walk. Decomposed at
equal match density:

| form | ns/B |
| --- | ---: |
| literal `café` | 0.257 |
| explicit class `caf[éÉ]` | 0.700 |
| `(?i)café` | 1.226 |
| alternation `caf(é\|É)` | 3.405 |

The dominant step is the code-point-class emission — and it need not be one. `é` and `É` are `C3 A9`
and `C3 89`: same length, one shared lead, one differing continuation, i.e. `byte C3` followed by a
two-member **byte** class. Fixed width, no branch. A non-ASCII class whose members share one length
and differ in exactly **one** byte position is now emitted that way:

| | before | after | vs PCRE2-JIT |
| --- | ---: | ---: | --- |
| **arm64** | 1.286 | **0.404** | 0.26× → **0.84×** |
| **x86-64** | 2.057 | **0.671** | 0.29× → **0.89×** |

**Narrow on purpose**, because the neighbouring shape is a known trap: `(?i)[a-z]` gains the long s
and the Kelvin sign at 2 and 3 bytes, so byte-wise it needs an *alternation* — the form measured at
3.405 above, and refused since v2026.7.61. Requiring one common length and a single varying position
excludes every alternation-shaped case: no branch is ever emitted.

**Why it cannot widen the language:** with one varying position the byte form accepts exactly the
cross product of the fixed bytes with that position's set — and that product *is* the member set,
precisely because only one position varies. Two varying positions would admit non-members, which is
why they are refused. `exhaustive-compat` reads identically to the case before and after: 3 218 434
cases, `agree` = 3 213 886 on both sides.

**What it costs, in two numbers rather than one.** In the benchmark harness, gcc/x86-64 `words` is
**+16.8 %**, its ASCII witness +16.9 %, `digits` +16.9 %, `[à-ÿ]+` +15.3 %. In a translation unit
that includes only `real.hpp` — the shape a caller compiles — the same change costs `words` **+4.6 %**
and `[à-ÿ]+` +3.9 %, for the same −64 %. arm64 pays nothing either way (worst row +0.2 %). Both
figures are in §A's protocol; publishing only the flattering one would have been a choice, and it
was not made.

## Four things were built, measured and refused

- **The capture pool as SBO containers.** The same shape as the mark table, and it looked like a free
  repeat. Three packagings, each worse than the last on gcc/x86-64 `words`: +16.8 %, +19.7 % with the
  paired `noinline`, **+26.1 %** using an instantiation that already existed. The cold gain was 6–8 %
  and only on capture-carrying patterns. Two hypotheses died here: the paired `noinline` is **not** a
  transferable recipe, and the cost is **not** the number of new `small_vec` instantiations.
- **A benchmark row for the accented literal.** Added so the 6.3× fix would be visible — and adding
  one brace-initialised case to `bench_engines.cpp`, no new code at all, moved gcc/x86-64 `words`
  **+27.7 %**, its witness +26.9 %, `digits` +23.7 %. Reverted. That file already said "do not
  instrument me" on the strength of a 12 % runtime switch; it now also says a *data row* spends the
  same budget, because the unit's cost is what it **contains**, not only what it runs.
- **Lazy state initialisation.** Refuted by a note already in the code: the state's parts measure
  0.3–0.9 ns each, so there is no lever to pull, only reuse — and reuse across regexes segfaults.
- **`noinline` on the new fold emission.** It runs once per pattern compile, so outlining is free —
  and it changed nothing (+17.4 % against +16.8 %). Not kept.

## The instrument was wrong twice, and said so both times

Two full measurement sets were discarded rather than published. One arm64 set ran while the machine
was building and reads slower on exactly the longest-scanning rows — contamination only inflates, so
it cannot enter a per-cell minimum. And one x86-64 set linked the container's **system PCRE2 10.42**
instead of the pinned 10.47: that alone moved `anchored`'s PCRE2 cell from 0.52 to 0.77, a 1.01× that
would have been published as **1.50× in REAL's favour**. The harness prints the version it *linked*
for exactly this reason, and that one line has now caught the same trap twice.

§Unicode was also nine trains stale — its x86-64 leg quoted `\w+` at 6.10 ns/B where it now measures
3.679. Both tables are re-stamped on this tree.
