# v2026.10.17 — The Rust binding declines a class range the regex crate reads otherwise

## Fixed

- **Rust: a range from a class's leading `]` is declined** (`Error::Unsupported`), where it compiled and matched
  differently from the `regex` crate. `re`, Go and REAL read `[]-~]` as the range `]`..`~`; the crate reads the
  three members `]`, `-` and `~`, so `|` matched one and not the other. As with the crate's class set notation,
  the binding now refuses the pattern rather than answer otherwise than the crate it stands in for; with the
  `fallback` feature it is delegated to the crate. `[]-]` and `[]a]` mean the same to both and stay accepted.
  Found by the long fuzzing run of v2026.10.16.

## Changed

- **The Rust binding's tests sweep every pattern of up to three syntax characters against the crate** (about
  46 000, bare and inside classes): a pattern both accept must give the same matches. Over every pattern of up to
  four such characters (1.04 million), the only difference left is the possessive quantifiers, which the two
  read differently on purpose.
- **The long fuzzing runs hold again.** The compat fuzzer stops on undefined behaviour, as the others now do; it
  skips two unbounded quantifiers over a subject past 96 bytes, where the `std::regex` it compares against is
  cubic (170 ms for one failing search over 234 bytes); and it keeps a 64 MB quarantine and a 3 GB resident limit, where the memory `std::regex` frees outgrew
  libFuzzer's 2 GB in an hour. The C ABI fuzzer bounds its subject to 1024 bytes: its seven iterating passes are
  quadratic at worst, as documented.
- **Benchmark tables re-stamped** on both ISAs at 2026.10.16 (`docs/BENCHMARKS.md`): no row regressed; the
  x86-64 capture rows of the duel moved with the binary's code placement, not the engine.
