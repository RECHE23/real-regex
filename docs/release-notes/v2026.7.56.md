# v2026.7.56 — performance: the cold path, and the bench rows that could not see it

A **performance** release, entirely on the **cold path**: work done once per
`regex`, outside every scan loop. No behaviour changes, no API changes, no
`pattern_hints` change. The scan itself is untouched, and that is stated as a
measurement rather than an intention: `find_iter` over a 64 KiB corpus under x86
callgrind reads `[a-z]+` 45 249 882 → 45 249 867 instructions and `\b\w+\b`
79 627 285 → 79 627 260 across the whole train — identical to five decimals.

The train has an unusual shape worth naming up front. Two of its costs were
**invisible to every bench row this repository had**, because `find`/`captures`
build the pattern *outside* the timed closure and criterion's warm-up absorbs
anything the engine builds lazily on the first match attempt. One of them was
21 milliseconds. So the first change here is to the bench, and the rest is what
the new rows exposed.

## The bench first: `compile/` and `first_use/`

`bindings/rust/benches/engines.rs` gains two groups per case. `compile/` times
`Regex::new` alone. `first_use/` times a *fresh* `Regex::new` plus one short
search, so anything built lazily is paid inside the timed closure; subtracting
the `compile/` row gives the lazy build on its own. `first_use` deliberately
includes `compile` rather than subtracting it in the harness — two medians
measured separately and then subtracted is an estimate carrying both error bars,
not a measurement, so the row states what it measures and the reader subtracts
knowing that.

The two costs that lived in the gap: a quadratic Unicode word-subset test cost
`\b\w+\b` **105 µs at compile**, and the one-pass capture table for
`(\w+)@(\w+)` cost **21.3 ms on first use**. Both are fixed below. Neither moved
a single pre-existing row.

## One sorted merge for the Unicode word-subset test

`is_unicode_word_subset_cp_class` carried **94.73 %** of the cost of compiling
`\b\w+\b` — 1 794 665 of 1 894 469 instructions. Its inner scan restarted at
index 0 on every advance, justified by a comment whose premise does not hold
("called only on the (small) user-class range list"): for `\w` that list *is* the
Unicode word set, 771 ranges, so 771² ≈ 594 k steps, which is the measured count
to the arithmetic. Both lists are sorted and disjoint, so the subset test is one
merge; a monotone cursor carries the position across a class's ranges, and it is a
hint rather than a precondition — if a range before it could still cover the
interval the scan rewinds, so the answer never depends on the caller's order,
only the speed does.

    \b\w+\b compile   105.4 → 7.3 µs   arm64/clang   (14.4×)
                      237.9 → 10.8     x86-64/g++    (22×)
                  Ir 1 894 469 → 121 846             (−93.6 %)

Every other pattern is instruction-identical on x86: `\w+` 79 735, `\bx` 14 948,
`(\w+)@(\w+)` 188 123, `[a-z]+` 19 041 — unchanged to the instruction. Against
the `regex` crate the ratio goes 0.47× → **0.032×**, back into the 0.02–0.07×
band every other pattern already occupied.

## The one-pass build: 21.3 ms to 2.9 ms, in five passes

`(\w+)@(\w+)` built its capture extractor lazily on the first match attempt, and
that build cost 21.3 ms for a search over a 37-byte subject. Five passes, each
measured on both ISAs, each verified not to touch the scan:

**Flat, hoisted scratch in `minimize()`.** The Moore refinement rebuilt three
scratch containers every round: *n* signature vectors, `next_cls`, and 4096 bucket
vectors — *n* + 4096 allocations *per round*. All of it is now flat and hoisted:
four allocations for the whole call.

**Sparse signature rows.** An unassigned byte-class added the same (0, 0, 0) to
every node's dense row, so dropping it cannot change any comparison, and each
sparse entry carries its class index so two nodes with different assigned *sets*
can never compare equal. Density decides the win, and it was measured before the
rewrite: 39.4 assigned classes of 103 for `(\w+)@(\w+)` gives 162 words a row
against 313. The second half doubled it — the assigned set never changes between
rounds, only the partition ids do, so the layout and every invariant word are
written once and a round rewrites 1 + assigned words per node instead of 313.

**One interned class per UTF-8 byte range.** `emit_utf8_trie` pushed a fresh
`char_class` per trie edge, and every edge class is a single range; a UTF-8 trie
repeats the same range on nearly every node. 2507 interned classes for 475
distinct ranges, now 476. That alone would have bought nothing, and reading said
so before measuring: `compute_lazy_alphabet` iterates `code`, not `classes`, so
its linear-scan dedup still ran once per `klass` *instruction*. Hence the second
half, a memo by class index — safe because an index already processed had its
content pushed the first time, and worthless before the dedup because indices
never repeated.

**Jump-chain resolution in the flood.** `emit_utf8_trie` writes
`split / klass / jump(target)` per trie edge, so the successor of a consuming
instruction — taken as `pc + 1` — was the *jump's* pc: one node per trie edge.
**2506 of 2508 nodes for `(\w+)@(\w+)` sat on a jump.** A `jump` is a pure epsilon
step, so the node at its pc and the node at its target receive identical edges,
and resolving the chain makes the flood land **on the minimal automaton**: 660
nodes in and 660 out, where it was 2508 in. Both halves of the cost — the flood
and the minimization — stop paying the 3.8×.

**One byte-program expansion instead of two.** The immutables build expanded the
program twice, Tier-A for the DFAs and Tier-B for the extractor. But
`build_byte_program` reads `keep_assertions` at exactly one place,
`opcode::assert_position`, and every other ineligibility is decided identically
either way — so a program with no such op yields a byte-for-byte identical
expansion. `\b(\w+)\b`, which *has* an assertion and takes the other branch,
comes out instruction-identical: 2 016 641 → 2 016 642.

    (\w+)@(\w+) first use   21 305 → 2 821 µs   arm64   (−86.8 %)
                        Ir 185 298 076 → 37 102 661     (−80.0 %)
    (\d+)-(\d+)                930.3 → ~195 µs
    ([^,]+),([^,]+)            111.5 → ~32

## Capture extraction: a `memcpy` call to move two words

`SlotStore::from_flat` copied the slot run with `copy_from_slice`. The length is
not a compile-time constant, so that compiles to a **`memcpy` call** — to move two
`usize` in the shape that dominates, a groupless pattern's group 0. This
repository already knows the failure mode and says so where the C ABI reads
slots: "pairwise specifically, NOT one memcpy (a runtime length compiles to a
libc call, dearer than the stores at the 1–2 slot shapes that dominate; that is
how the earlier memcpy regressed)". The same fault had survived on the Rust side.

It was located by ablation after reading settled where reading could: `Matches::next`
and `CaptureMatches::next` call the identical `advance()`, so the engine does the
same work for both and the whole excess is the object each yields. Two ablations
then apportioned it on `\b\w+\b` over a 64 KiB corpus, where `captures_iter`
trailed `find_iter` by 171.4 µs — a `Drop`-free 40-byte `Captures` with no `Arc`
atomics took it to 114.5, and removing `slot_store()` as well took it to zero. So
**two thirds was this one call**.

    captures/class     207.9 → 186.45 µs   1.10× behind → parity with regex
    captures/digits     61.0 → 54.72       REAL 1.39× ahead
    captures/fields     43.4 → 39.76       REAL 3.86× ahead
    captures/literal    27.7 → 18.98
    find/literal        17.3 → 16.31
    captures/email     143.6 → 137.15

## Verification

- `full-local-gate` **22/22 green** — and for the first time in this train's
  history, that is literal: step 19 (`check-vendor`) cannot pass until the
  vendored Go tree is committed, and it sits ahead of `lint`/`sanitize`/`coverage`,
  so those three had been reached only through a manual substitute. See Notes.
- 758 tests, **340 454 checks**, 0 failures; line coverage **95.81 %** (floor 95.0).
- `exhaustive-compat` 3.2 M cases, `fowler-compat`, `test_onepass`, `test_dfa`,
  `test_lazy_dfa`, MISRA, and the c/rust/python legs all green — the one-pass
  changes alter *which nodes exist* in the extractor, so those nets carry the
  weight here.
- Both ISAs on every perf claim: arm64 wall-clock and x86-64 callgrind
  instruction counts, with the warm-path controls quoted above.
- `docs/BENCHMARKS.md` §E.4 **is** re-stamped in this release, with the six moved
  rows and the two new families. §A/§B/§Unicode/§multi-pattern are **not**, and
  the reason is measured rather than asserted: they are untouched, and the
  identical instruction counts for `find_iter` are the evidence.

## Notes

- **`(\w+)@(\w+)` first use is still 4.94× behind the `regex` crate** — 2.91 ms
  against 589 µs — after −86.8 %. Disclosed, not chased. Declining the one-pass
  table instead was measured and rejected: it buys **3.3×** on the scan (`find`
  135 µs against 443 over 64 KiB), with a break-even near 900 KB, so declining
  would trade a one-time cost for a sustained one.
- **7 of 9 dispatch routes bill nothing to the deterministic work counter**, so
  the linearity gate does not cover them: `cp_class_loop`, `alternation`,
  `aho_corasick`, `general_full`, the two possessive loops, and their `\b`
  variants. All nine measure linear — 3.77×–4.04× for 4× the bytes — so this is a
  missing net, not a defect. It is not theoretical: the `fixed_shape_pair` route
  shipped in 7.55 billed zero, which made the gate's `large < small * 8` read
  `0 < 0`. `class_loop` is closed here; the rest is a follow-up, with the caveat
  that `extend_run` exists in two copies (clang in `pike.hpp`, gcc in
  `cpclass_gcc_loop.hpp`) and both must bill.
- **A gate-verification hole, found and closed.** `make lint` exits 0 with
  warnings present, while `full-local-gate` step 20 pipes it through
  `grep -qE 'warning:|error:'` and fails on any. Because the gate stops at the
  first failure and step 19 cannot pass pre-commit, steps 20–22 had not actually
  run on the commits of this train, and the manual substitute called `make lint`
  — which does not enforce the rule. Four analyzer warnings reached `main` that
  way and are fixed here. CI could not have caught them: `ci.yml` runs
  `format-check` and `misra`, not `lint`, so the clang-analyzer pass is
  local-gate-only. The rule going forward is to reproduce the *step*, not its
  underlying target.
