# v2026.7.37 — triage: 4 correctness fixes, fuzzer-found

Correctness release. A 5-seed × 100k-iteration differential fuzz battle against
`re` on v2026.7.36 surfaced two real bugs; running that same closure criterion
to completion during the fix surfaced two more, pre-existing and previously
undocumented. All four are fixed and regression-tested here. No breaking API
changes, no performance regressions — D1-perf's possessive fast-path ratios
are unaffected (route-toggle A/B, below).

## The four bugs

1. **Lost captures on a `\b`/`\B`-prefixed fixed-shape match.** `fill_fixed_saves`
   (the `fixed_shape` fast path's capture filler) hardcoded its scan start at
   the body's assumed first instruction — true only without a leading `\b`/`\B`
   wrap. With one, that hardcoded offset lands on the assertion itself, which
   the scan does not recognize, silently filling zero capture slots. Reproduces
   with plain greedy `\B(\w){2}` — no possessive quantifier involved — so this
   predates and is unrelated to v2026.7.36's possessive fast paths, despite the
   fuzz repro using one. Fixed by reading the body's real offset off the
   program's own hints instead of assuming it.

2. **ASCII-mode `\s` wrongly included four control separators (`U+001C`-`U+001F`).**
   Python's `re` under `re.ASCII` excludes them; only its default *text*-mode
   `\s` includes them (via `str.isspace`). REAL's ASCII set had conflated the
   two. Fixed by threading mode-awareness into the shorthand-class lookup so
   ASCII mode gets the narrow set and text mode keeps the broad one — a real
   fix, not a one-line table edit, because both modes had shared a single
   bitmap representation. **Consumer-visible**: `flags::ascii` tokenization of
   these four control bytes now matches Python exactly.

3. **A word-boundary optimization broke under a windowed search.** An internal
   optimization drops a leading `\b` check when it can prove the check is
   redundant for a maximal run — reasoning that such a run can only start where
   the preceding byte is non-word. That reasoning implicitly assumed "no
   preceding byte" means the true start of the text; it does not when a caller
   passes `search(text, pos, endpos)` with `pos > 0`. Confirmed pre-existing
   (reproduces on an unmodified v2026.7.36 tip with plain `\b\w+`) and fixed
   across all three affected runners, including the possessive fast path.
   `endpos` on the *trailing* side was independently confirmed correct and
   left untouched — the bug was leading-only.

4. **An index-table collision let a possessive-loop recognizer match anything.**
   A structural check meant to confirm a loop's mandatory leading copy tests
   the *same* character class as the loop itself compared raw table indices
   without checking which of two different tables (byte classes vs code-point
   classes) they came from. When a byte-class mandatory copy and a code-point-
   class loop happened to share a numeric index — `[abc].*+` is a real,
   minimal repro — the pattern matched unconditionally, ignoring its own
   leading class. Fixed by requiring both the table *and* the index to match.

## A CPython oracle bug, not a REAL bug

Differential fuzzing also flagged a scoped-ascii-group inconsistency in
CPython 3.14 itself: `(?a:\S)`, when it is a pattern's own first construct
with nothing preceding it, wrongly fails to match the same four control
separators bug 2 above concerns — an outright partition violation against
`(?a:\s)` on the identical input. Prepending anything at all (`\B`, `^`, a
lookahead, a literal byte) "fixes" it on `re`'s side; REAL has no such
inconsistency either way. Not fixed (there is nothing on REAL's side to fix)
— filtered out of the differential fuzzer and pinned directly against `re`'s
own buggy value, so a future CPython release that corrects it is caught
rather than silently masked. See `\ref div_cpython_scoped_ascii_bug` in the
C++ docs.

## Verification

Full test suite (577 C++ tests, 52.6k checks); `make full-local-gate` 18/18;
line coverage 95.66% (floor 95.0%); the differential fuzzer's own closure
criterion — 5 seeds × 100,000 iterations against `re` — clean post-fix,
including the CPython-bug filter above. A route-toggle A/B (D1-perf's
possessive fast path forced off vs auto-routed) confirms none of these fixes
eroded v2026.7.36's own possessive-vs-greedy gains.

## Honesty

Two of the four bugs (3 and 4) were not in the original fuzz report — they
surfaced only because the fix work re-ran the closure criterion at its full
stated scale (100k iterations per seed) rather than stopping once the
originally reported bugs looked fixed. Bug 1's root cause was initially
misattributed to the possessive fast path shipped in v2026.7.36; the actual
cause is older and independent of it, corrected after a route-disabled
control test contradicted the first attribution.
