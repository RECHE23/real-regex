# v2026.7.63 — a quadratic API on a linear engine, and a codegen defect that had been vetoing its own fix

Three things, in the order they matter to whoever is reading. A **Python bug** that made a
documented linear-time guarantee false at the API surface. A **12–23 % Unicode gain** on Linux/gcc
that had been measured, valid and blocked for weeks by something unrelated to it. And the thing
that was blocking it: a **codegen defect** that made one pattern's compile-time cost land on a
different pattern's run time, which also explains a long run of contradictory measurements in this
project's own history.

Matching is unchanged. Every span, capture group and match count is identical to v2026.7.62.

## `finditer(...).start()` was quadratic on non-ASCII subjects

A linear-time engine with a quadratic offset API is the one shape this project must not ship, and
it shipped. Converting a byte offset to a character offset means counting UTF-8 lead bytes, and
every `Match` walked from byte 0 — so a `finditer` loop that read `.start()` cost O(n²):

| units | matches | `.group()` only | `+ .start()` before | after |
| ---: | ---: | ---: | ---: | ---: |
| 4 000 | 8 000 | 1.6 ms | 41.4 ms | **2.5 ms** |
| 16 000 | 32 000 | 6.8 ms | **633.2 ms** | **10.1 ms** |

The iterator now owns one monotone walk and hands it to every `Match` it yields, refcounted
because a match legitimately outlives its iterator. The ratio to a `.group()`-only loop stops
growing: 1.5–1.6× across a 16× range where it had gone 7× → 91×.

**Laziness is preserved.** A scan reading only `.group()` still computes nothing. Reading matches
*out* of order — a saved list walked backwards — finds the cursor ahead of the target and restarts
from zero: correct, just not accelerated, and the cursor is never rewound, so matches that still
have it ahead of them keep theirs. A `bytes` subject allocates no cursor at all.

Pinned by **shape rather than by a wall-clock budget**, so it cannot become a flaky timing test:
16 000 units must cost less than 8× the 4 000-unit run (linear is ~4×, the old behaviour ~15×).
Proved both ways — with the shared walk disabled the pin fails and prints the two timings.

## The Unicode property/script band, 12–23 % faster on gcc

On the devbox under g++ 13.3.0 — the toolchain that builds the manylinux wheels:

| pattern | before | after | |
| --- | ---: | ---: | ---: |
| `\p{sc=Han}` (CJK) | 13.12 | 10.14 ns/B | **−22.7 %** |
| `\p{scx=Cyrl}` (mixed-script) | 11.23 | 8.92 | **−20.6 %** |
| `\p{N}+` (arabic digits) | 7.32 | 6.08 | **−17.0 %** |
| `\w+` (mixed-script) | 6.34 | 5.43 | **−14.3 %** |

`\p{L}+` (−12.2 %) and `[à-ÿ]+` (−12.9 %) sit nearer this translation unit's floor and are recorded
as bounded rather than claimed. arm64/clang is unaffected **by construction** — the file lives
behind `#if defined(__GNUC__) && !defined(__clang__)` and `c++ -E` finds zero occurrences of the
symbol under clang.

Two smaller cp-class changes land with it. The scan tests the **ASCII row before the width test**,
which is sound because a code-point class never sets a bit at or above `0x80`, so a table hit is
necessarily a single-byte member. And `extend_run` **captures by value** instead of `[&]`, which
removed two indirections per call: `\d+` −13 % wall / −7.4 % Ir over three interleaved rounds.

**The interesting part is why the first one had been refused.** Dropping the inlining attributes
was measured, valid and reproduced across three compilers — and it cost `(?i)cafe`, on an ASCII
no-match scan, **+217 %**. That pattern compiles to four byte classes and zero code-point classes;
it never enters the loop being changed. See below.

## `static_regex` stops multiplying the engine into your translation unit

GCC caps how much a translation unit may grow from inlining (`--param inline-unit-growth`, 40 % by
default). This library exhausted it: **3 028 refused inline decisions** in one benchmark TU, 2 637
of them in `engine/pike.hpp`. Past the cap GCC declines in traversal order, so *which* inlinings
survive stops depending on their value — and an unrelated change re-shuffles the whole allocation.

The cause was in the mangled names: a route instantiated `[with State =
static_storage<fixed_string<12>{"(\w+)@(\w+)"}>::state_type]`. **The pattern's value was a template
argument**, so every distinct `static_regex` carried a private copy of every Pike VM route — 82.4 %
of the ~48 KB each one added to `.text`.

Fixed in three steps: the sized members moved to a namespace-scope scratch keyed on dimensions, the
three byte-class table addresses moved into `program_view` where a program's runtime data belongs,
and the scratch capacity was **tiered** (powers of two, floor 8) so neighbouring shapes share one
instantiation.

| | before | after |
| --- | ---: | ---: |
| `.text` per pattern, same shape | ~45 KB | **7.7 KB** (x86-64) / 7.2 (arm64) |
| `.text` per pattern, all shapes differing | 50.9 KB | **10.8 KB** / 9.3 |
| budget refusals, 32-pattern TU | 19 735 | **1 457** |
| an unrelated pattern at 11 / 12 / 14 patterns | 33.5 / 33.7 / 20.4 µs | **11.8 / 10.7 / 10.8** |

That last row is the defect itself: timing that was **not monotone in pattern count** — fine at 9
and 10, 3× off at 11 and 12, fine at 13, intermediate at 14 — deterministic per TU and chaotic in
its contents, so there was no safe pattern count and no margin to keep. It is flat across N = 0…32
on both platforms now.

The scratch costs more: `[a-z]+`'s goes 1792 → 2328 bytes (×1.30). Powers of two were chosen over a
coarse 32/64 ladder for exactly this reason — about the same collapse, a fraction of the
over-allocation, where the coarse ladder would have cost ×3.8.

## The measurement instrument, and what it says about the past

The defect above has a consequence beyond its own fix: **an A/B measured inside an exhausted
inlining budget is a lottery draw**. A pattern that never executes the changed code can move by
+220 %, and one row here read −25 % in a container against +217 % on the devbox. That is the
standing explanation for a long run of unstable results in this area, where instruction counts and
wall clock disagreed and the same change won on one machine and lost on another.

Two rules now sit in `docs/BENCHMARKS.md`, and both earned their place in this train:

- **Read the rows a change cannot reach before believing any delta.** If they moved too, the
  measurement is a draw, not a result. This caught three would-be findings here, one of them a
  19 % "gain" that was the control moving with it.
- **Measure x86-64 on the devbox, not in Docker on a laptop.** Worst within-arm spread 1.045×
  against the container's 1.98× — and on the A/B that decided this train, the two disagreed about
  the **sign** of the deciding row.

**Nine approaches were measured and refuted** along the way, and are recorded so none is retried:
annotation changes of every shape, a per-call-site split, a `<bool>`-templated dispatch with a
runtime subject probe, PGO (which reproduces the identical cliff and exhausts the cap faster,
because a profile changes which inlines GCC *wants*, not the cap it runs into), and "stay under a
safe pattern count", which the sweep killed.

## ReDoS: the classic demo does not discriminate

§C of `docs/BENCHMARKS.md` asserted the linear-time guarantee against `std::regex`, Python `re` and
RE2 — and omitted PCRE2-JIT, the engine that leads REAL on the Unicode band everywhere else in that
document. The guarantee was being demonstrated against the engines REAL already outruns.

Correcting that produced the more useful half of the finding: **`(a+)+b` at N = 100 000 answers in
microseconds under PCRE2-JIT.** Two optimisations apply — `a` and `b` are disjoint so `(a+)+` is
auto-possessified, and `b` is a required literal it scans for first. Every textbook comparison
built on that pattern measures optimisers, not guarantees. The shape that does discriminate is
`^(a+)+$`, anchored at both ends so there is no required literal to short-circuit on, and it is
now the row in the table.

## Hardening and tooling

**`onepass` no longer keeps spans over a program it does not own.** One caller builds the table
from a *local* byte program, so the borrowed `code_`/`classes_` spans dangled at the closing brace.
Nothing dereferenced them and that was provable rather than hopeful — but "safe because nothing
currently reads it" is an invariant held by audit, and the next member that reads `code_` after
construction turns it live. The spans are emptied once the build that needed them is done.

**The doc-style checker was broken in both directions**, found by using it rather than reading it.
Its freshness guard compared against the *oldest* XML file Doxygen left behind, and Doxygen rewrites
only what changed — so after a clean run every header read as stale, permanently: a false STALE,
the mirror of the false clean the guard was added to prevent. And `--refresh` re-ran Doxygen without
clearing the output, whose XML is incremental per compound, so a header edited between runs could
keep the XML of its previous revision.

## Disclosed, not chased

- **The tiered scratch is `static_regex`-only.** `real::regex` was never exposed: sweeping the same
  32 patterns through the dynamic API moves `.text` by 5 KB and the timing not at all.
- **`real::regex` pays a fixed ~29 ns per `search()` that `static_regex` does not**, decomposed here
  but not fixed: 10.2 ns constructing the scratch state, 4.4 ns building `program_view`, and ~15 ns
  unattributed — though now known to be route-independent, since a bare literal pays the same as an
  alternation. Two standing proposals to shrink `program_view` were priced against that 4.4 ns and
  both refused, one of them by arithmetic rather than by taste.
- **`pattern_hints` is already hot/cold ordered**, deliberately, with a measurement behind each
  placement. Now stated on the struct so it stops being proposed as an opportunity.
- **Dimension tiering shares by tier, not by shape.** A translation unit whose patterns all differ
  still pays ~10.8 KB each rather than 7.7.
- **The AVX2 two-byte prefilter leg for x86 is still unwritten.** No public row demands it.

## Verification

786 tests, 345 259 checks, 0 failures. Line coverage 95.36 % against the 95.0 floor (engine logic;
`bindings/c` guarded by sanitize + fuzz). `full-local-gate` green across all 22 steps, and CI green
on 29 jobs including the `linux-gcc / g++-14` leg that covers the gcc-only cp-class change, the
`windows-msvc` leg that is the tightest `constexpr`-step budget and the named hazard for tiering,
the `linux-arm` and `macos-clang` legs, MISRA, both fuzzers, conformance and six Python matrices.

The cp-class change cannot move semantics — an inlining attribute leaves the function body
byte-identical — and was confirmed anyway by a route differential under g++ over 20 cp-class-heavy
patterns × 11 subjects including mixed scripts, invalid UTF-8, empty and punctuation-only: 533 spans
and capture groups, byte-identical between the two arms. The storage lift is layout-neutral:
`sizeof(state_type)` was byte-identical on all five probe patterns after step one, and the tiering
step's growth is stated above rather than discovered.

## Notes

Nothing here changes what REAL matches. The linear-time / ReDoS-safe guarantee, the bounded
lookarounds and the matching API are unchanged. The one behavioural change is in the Python
binding, and it is a bug fix: `.start()` / `.end()` / `.span()` return what they always did, in
linear total time instead of quadratic.
