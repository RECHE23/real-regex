# v2026.7.61 — a folded ASCII class stops losing its route

A **performance** release on the case-insensitive scan path, and a **capability**
release on `real::dfa`, which the first one required. No API changes, no behaviour
changes to matching: every span, every capture group and every match count is
byte-identical to v2026.7.60, verified as a differential against the same engine —
494 pattern × subject pairs on spans, 28 on every capture group of every match, plus
624 pairs over folded and non-ASCII classes specifically.

## The row this was about

v2026.7.60 added an `icase_class` family because the suite had no case-insensitive
pattern at all — a gap two compile-cost defects had already come through. It read
3.37× behind the `regex` crate immediately, and the profile refuted the obvious
explanation: `(?i)[a-z]+` was not on the code-point scan, it was on the lazy DFA
(`lazy_dfa::anchored_end`, 23.5 %).

| criterion row | v2026.7.60 | v2026.7.61 | vs the `regex` crate |
| --- | ---: | ---: | :--- |
| `find/icase_class` | 631.8 µs | **252.1** | 3.37× behind → **1.34× behind** |
| `captures/icase_class` | 680.0 | **295.8** | 3.66× behind → **1.57× behind** |
| `compile/icase_class` | 1.9 µs | **1.3** | 9.66× ahead → **14.01× ahead** |
| `first_use/icase_class` | 3.0 µs | **1.8** | 7.33× ahead → **12.04× ahead** |

## The cause, which was not the one proposed

Under icase `[a-z]` gains the long s (U+017F) and the Kelvin sign (U+212A), both
**multi-byte**. The class was therefore expanded to a byte-level alternation — one
branch for the ASCII bitmap, one per UTF-8 sequence — so `(?i)[a-z]+` compiled to 8
byte classes and 18 instructions against 1 and 5 for `[a-z]+`, stopped being a class
loop, and matched no route at all.

Two rare fold partners were costing the route.

An ASCII bitmap with a few non-ASCII members *is* a code-point class, so it is emitted
as one: a single `klass_cp`, 8 instructions, and the class-loop route takes it.

arm64 wall clock, 64 KiB walk: `(?i)[a-z]+` 545.0 → 230.3 µs (**−57.7 %**),
`(?i)[a-zA-Z0-9_]+` 595.2 → 247.4 (**−58.4 %**), `(?i)[a-z]` −31.7 %. x86-64
instructions: **−58.2 %** and **−58.7 %** on the same two. `[a-z]+`, `\w+`, `.`,
`[^,]+`, `dog`, `(?i)dog` and `\b\w+\b` are all 0.0 % on arm64 and within 0.7 % on
x86-64.

One-pass eligibility improves as a side effect: `klass_cp` reaches `build_utf8_trie`,
whose disjoint per-node transitions are what make a Unicode class one-pass, so
`(?i)[àé]+` goes from "byte-class conflict" to one-pass.

## `real::dfa` had to be widened, not narrowed

That entry point refused `klass_cp` outright — "no DFA can represent" — so the change
above would have made these patterns unconstructible there: a user-visible capability
regression, which is not an acceptable price for a scan gain.

The refusal was a limit of the entry point and not of the DFA. `dfa_flatten` now
expands `klass_cp` through the same `build_byte_program` the lazy DFA has always used,
so the deterministic UTF-8 trie recognising the class becomes ordinary byte
transitions. **Text-mode `\d` and `\s`, Unicode properties, non-ASCII classes and
case-folded ASCII classes all build there now**, where that API had never accepted one.
The audit still runs over the pattern's own program, so every refusal message names
what the user wrote.

## And the widening had a second-order cost, which the fuzzer found

Within the hour, through a path the change never touched. `regex_set` builds one of
these DFAs internally, so widening what the DFA *accepts* widened what `regex_set`
*attempts*: on `^\w` it spent 27.9 s where it had returned an error immediately.

Not a wrong answer — a cost defect. The third this project's fuzzer has found, and the
first that was a second-order effect of a change rather than the change itself.

What it exposed: `max_dfa_states` bounds the **result** of subset construction and
nothing bounded the **work** to reach it, while that work is superlinear in the
expanded program.

| expanded byte program | size | release-build construction |
| --- | ---: | ---: |
| case-folded ASCII class | 26 | 0.04 ms |
| `(?i)[a-z]{8}` | 179 | 0.25 ms |
| `\p{Greek}+` | 168 | 0.79 ms |
| `\d+` | 261 | 1.88 ms |
| **text-mode `\w+`** | **3434** | **418 ms** |

Thirteen times the size for two hundred and twenty times the time.
`max_dfa_byte_program` = 512 sits above every shape that builds in about a millisecond
and below the one that does not. Everything it refuses was **already refused** before
`klass_cp` became expandable here, so the cap restores the previous answer for the wide
classes and keeps the widening for everything below it. A repeat multiplies the
expansion, since each occurrence gets its own trie: `\d{2}` is already 517 and
declines — stated in the test rather than left to be rediscovered.

The fuzzer's exact input, rebuilt from the log and run under the same sanitized build:
**27.91 s → 0.33 s**.

## Disclosed, not chased

- **`(\w+)@(\w+)` first use stays 2.64× behind** the crate.
- **`find`/`captures` `no_match` stay 2.09× and 2.05× behind** — a ratio on 1.6 µs
  against 778 ns, so the gap is in ratio and not in substance.
- **`captures/word_bound` stays 1.82× behind**, `find/literal` 1.57×.
- **Text-mode `\w` still declines in `real::dfa`**, by the cap above and as before.

## Verification

Criterion figures come from an interleaved A/B against v2026.7.60 with the same bench
file on both sides, one group at a time, machine otherwise idle: two rounds for every
group, and **four rounds of 5 s for `captures`**, which was load-bearing —
`captures/word_bound` read +3.1 % on two rounds and **−0.3 % on four**. No row
regresses. Every row other than the four `icase_class` gains lands within ±1.6 %.

The DFA's agreement with the engine is pinned by two new probes: every accepted
code-point-class pattern builds, and finds an anchored non-empty match exactly when the
engine does; the wide ones decline.

`full-local-gate` on every commit in the train, plus CI green including the
windows-msvc leg and the fuzz job that first reported the cost defect. 782 tests,
345 225 checks. Coverage 95.60 % (floor 95.0). clang-tidy clean, MISRA 0, sanitizers
clean, Go and Python bindings green, gcc-14 green.

## Notes

Nothing here changes what REAL matches. The linear-time / ReDoS-safe guarantee and the
bounded lookarounds are unchanged, and so is the matching API. `real::dfa` accepts
strictly more than it did.
