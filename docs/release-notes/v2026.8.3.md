# v2026.8.3 — three accessors that answered the wrong question first

Six performance changes, all found by asking where REAL *loses* and profiling there rather than by
reading the code. Every answer is unchanged: spans, capture groups and match counts are identical to
v2026.8.2 on every table in `docs/BENCHMARKS.md`, on both ISAs.

The headline is one line moved in three places, and the fact that the same move needed three
different packagings.

## The membership accessors asked two invariant questions before the one that varies

`class_table`, `cp_ascii_table` and `cp_page_table` each hand back a 256-entry membership row. All
three began by asking which storage the program uses — `class_tables != nullptr`, then
`immut != nullptr` — and only then whether the row they cached is still the row wanted. The first two
questions have the same answer for an entire walk. The third does not.

`class_table` runs **once per match** on a walk. Bisected on executed conditional branches — the
x86-64's 3 % noise floor cannot resolve a 6 % step, and a simulated counter has no floor at
all — across the 174 commits since v2026.7.55:

| revision | Bc per 40 scans | |
| --- | ---: | --- |
| `3cd9c81` | 68 193 357 | good |
| `1e5bc9c` | 69 737 997 | good (parent) |
| **`6d80c52`** | **72 274 677** | **first bad** |
| v2026.8.2 | 72 282 877 | |

The lazy per-class row fill introduced there took the accessor from 1 conditional branch per call to
**exactly 3.00**, over 1 270 040 calls. Asking the row key first restores it: 69 742 877 branches,
within 4 880 of the parent, and 421 498 433 instructions — below *both* endpoints.

### The packaging decided each one, in opposite directions

This is the part worth keeping, because no counter in this repository predicts it.

- **`class_table` needs its cold half OUTLINED** behind a `noinline`. The accessor must stay small
  enough to inline into `basic_match_iterator::advance`; left inline, the same reordering split the
  platforms, costing gcc/x86-64 `[0-9]+` +7.2 % while clang/arm64 gained.
- **The code-point pair is destroyed by exactly that.** They are called from *inside* the
  per-code-point loop, where a `noinline` body is a barrier the loop cannot be optimised across:
  arm64 `[à-ÿ]+` **+39 %**, `\p{sc=Han}` +27 %, `\p{scx=Cyrl}` +20 %. And it is destroyed **while
  every deterministic counter reports an improvement**:

  | | Ir | Dr | Dw | Bc |
  | --- | ---: | ---: | ---: | ---: |
  | before | 736 058 953 | 207 472 955 | 110 028 515 | 112 405 477 |
  | outlined | 660 968 193 | 199 051 875 | 97 677 315 | 101 597 837 |
  | | −10.2 % | −4.1 % | −11.2 % | −9.6 % |

- **Even an `always_inline` function of its own costs 10–17 %** on gcc/x86-64 — on §A rows that never
  touch these accessors (`digits` 1.813 → 2.114, with a 0.05 % spread across runs). Two extra
  function bodies shift the translation unit's inline budget. Folded in place, `digits` reads 1.790,
  better than before the change.

Both refutations were settled by building the *discriminating* variant — reorder without outlining,
outline without reordering — and measuring it. Neither showed up in an isolated probe: the isolated
ASCII witness was flat for the second case while the same pattern in the real harness moved 14.4 %.

## `date` was on the inner-literal route, and the seam said it should not be

§A's worst row asked to be profiled. The route counters put
`[0-9]{4}-[0-9]{2}-[0-9]{2}` on `inner_literal` 254 times out of 255, and the seam differential — the
same pattern forced down each route, answers compared — said that route is the slower one for this
shape:

| pattern | corpus | inner-literal | fixed-shape | |
| --- | --- | ---: | ---: | --- |
| `[0-9]{4}-[0-9]{2}-[0-9]{2}` | dense | 0.859 ns/B | 0.801 | IL 1.07× slower |
| `[a-z]{3}-[0-9]{4}` | dense | 0.805 | 0.718 | IL 1.12× slower |
| `[0-9]{3}[.][0-9]{3}` | | 0.554 | 0.554 | tie |
| `[0-9]{4}-[0-9]{2}-[0-9]{2}` | rare | 0.022 | 0.022 | tie |

The route condition now declines when a fixed-shape route exists. Never worse across a density sweep,
better where the old gate was most confident.

## The trailing lookaround was re-resolved at every candidate end

A trailing lookaround whose sub-expression does not depend on the match is invariant for the whole
walk, and `try_ends` was calling `lookaround_holds(sub_id, e)` once per candidate end position.
Hoisted to once per walk.

## First search: two allocation defects

- **The one-pass extractor was built for programs with nothing to extract.** `with_search_dfas`
  called `ensure_op_table()` unconditionally, but a 2-slot program has no capture to fill. On
  `\w+@\w+` over 8 KB: **1627.35 → 580.44 µs (2.8×)**, allocations −36 %, bytes **−78 %**.
- **The reverse DFA's transpose allocated per program counter.** Two adjacency lists held as vectors
  of vectors, nearly every pc taking a first `push_back`. Counting degrees, prefix-summing and
  filling gives the identical structure in four allocations: **7003 → 38** for the transpose
  (−99.5 %), and the whole first search 16 146 → 9171 (−43 %).

## The benchmark document, which was lying by omission

§A had not been re-measured since `3cd9c81` (v2026.7.55) — a dozen trains. Both §A and §Unicode are
now stamped on the released tree, three harness runs per ISA, minimum per cell. Three things came out
of doing that honestly:

- **Two of §A's four improved rows are this document catching up, not this train gaining.** `words`
  4.15 → 3.39 and `digits` 2.36 → 1.89 on x86-64 came from code-point-class work landed several
  versions ago and never stamped. They are labelled as such in the table's reading.
- **A version trap was found and closed.** §A claimed PCRE2 10.47 "built from source on x86-64 to pin
  the exact version", but the recipe resolves the library through `pkg-config`, so the pin only
  applies when `PKG_CONFIG_PATH` points at that build. The first re-run silently linked the system
  10.42 and shifted the entire PCRE2 column 5–12 % — with nothing in the output able to contradict
  the claim. `make bench-engines` now prints the library version it actually **linked**.
- **`fields [^,]+` is reclassified rather than chased.** Published at an intermediate stamp as an open
  +9.8 % regression, it does not reproduce in an isolated probe over the same corpus and pattern on
  the same machine (the released tree measured 4.8 % *faster* than v2026.7.55 there), and the
  accessor work that moved every other row read −25 % in that probe against +1.0 % in the table. Two
  independent disagreements on that row alone. The document now says plainly: do not read it as scan
  throughput, and the next move on it is a harness question, not a routing one.

## Disclosed, not chased

- **`\p{sc=Han}` is the worst §Unicode row at 10.7 ns/B on x86-64**, nearly double the next, and the
  only one the accessor reordering barely touched (−1.8 %). Its sparse high-table path is the one
  route of these classes that has not been opened.
- **`[^,]+` is on the code-point route, and a byte-level scan is not equivalent.** Every non-ASCII
  code point is a member, so a greedy byte run cannot split a sequence — but REAL excludes invalid
  UTF-8 from a code-point class and a byte scan would not: on `ab,c\xC3d,ef` it yields `[3,4)` and
  `[5,6)` where a byte scan gives `[3,6)`. That is the correct answer, and it is work the engines it
  is compared against are not doing on that row.

## Verification

805 tests, 0 failures. Line coverage 96.68 % against the 95.0 floor. All 23 `full-local-gate` steps
green, CI green on every commit of this train. Every performance figure measured on both platforms —
arm64 under Apple clang 16 and x86-64 under g++ 13.3.0 — as the minimum across
interleaved rounds, with an untouched gauge read before any delta was believed, and match counts
compared before any ratio was printed.
