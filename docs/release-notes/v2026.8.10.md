# v2026.8.10 — the two weakest rows are no longer the two weakest rows

Three routing gains, all measured on both ISAs and two builds each, and one of them found where nobody
had looked: in the **hint table**, not in any loop.

## `fields [^,]+` and `.` were never scan measurements

They were this document's two weakest rows against PCRE2-JIT — 0.58× and 0.81× on arm64 — and
profiling said why. `[^,]+` costs **~19 ns of fixed per-match overhead** plus ~0.086 ns/byte, flat at
18.6 / 19.3 / 18.8 ns per match for fields of 4, 8 and 16 characters. On the benchmark's own 4–7
character fields the fixed cost **is** the measurement. It is also why `words [a-z]+`, whose matches
are longer, sat at parity all along.

The cause was a shape nobody had wired up. Batching requires `greedy_class_loop` or
`greedy_cp_class`; the `.`/negated-class family sets a third hint, `codepoint_class_ascii`, and so
crossed a **full route entry per match** where the other two class routes cross one per sixteen.
Measured on their own fast paths: `[a-z]+` 5.55 ns per match, `[^ ]+` 19.04, `[^,]+` 19.45.

`fill_codepoint_class_spans` is the filler that was missing:

| | arm64 | x86-64 |
| --- | ---: | ---: |
| `.` (emoji) | −52.6 %, 0.81× → **1.75×** | −50.3 %, 1.25× → **2.67×** |
| `fields [^,]+` | −26.8 %, 0.58× → **0.82×** | −52.8 %, 0.80× → **1.70×** |
| `[^ ]+` | 3.84 → **2.09 ns/B** | 6.12 → **4.28** |

`fields` now **leads** PCRE2-JIT on x86-64, and `.` leads it on both.

## An alternation of single atoms is the class it is

`(?:a|b|c)+` measured 3.03 ns/B against `[abc]+`'s 0.66 — the same language, 4.6× apart, because the
split chain matches no shape recognizer while the class does. Fused, the program is not merely
equivalent to the hand-written class: it is **identical** to it (5 instructions, one `klass`, one
`split`, where the chain took 11 with three of each).

| | before | after | |
| --- | ---: | ---: | ---: |
| `(?:e\|o\|u)+` | 7.05 | **1.105** | **6.2×** |
| `(?:é\|à\|è)+` | 7.47 | **1.904** | **3.9×** |
| `(?:a\|b\|c)+` | 2.31 | **0.640** | 3.7× |
| `(?:é\|a)+` | 9.35 | **2.478** | 3.8× |

Exact rather than approximate, and the argument is short: every branch consumes exactly one atom and
none captures, so leftmost-first preference among them has no observable effect. An empty branch
(`a|` matches the empty string), a multi-atom branch, a class branch and a single-branch alternation
are each refused, and each refusal is pinned by the compiled **shape** so a later widening cannot
swallow one quietly.

**A faster version of this was refused.** Emitting the fused set directly as a code-point class
measured 1.85 against 4.42 ns/B on the bare form — and made `(?:é|à|è)` and `[éàè]` compile to
different programs. Same language, two routes, decided by spelling. One spelling, one program.

## Possessive quantifiers over non-ASCII literals

Carried from v2026.8.9's train and worth restating: `é++`, `あ++`, `𝔘++`, `é*+`, `é?+` and `é{2,}+` all
threw "possessive/atomic over a compound body", while `[é]++` compiled and so did `(?i)é++`. Nothing
fundamental stood in the way — an AST shape did. Verified against CPython 3.14.6 on all eight
discriminating cases.

## What it costs, and what is not claimed about it

Six rows move the other way: on arm64 they regress 3–15 % (`\w+` +15.3 %, `digits` +15.3 %,
`\p{sc=Han}` +10.3 %, `words` +8.9 %, its ASCII witness +8.8 %, `\p{L}+` +6.7 %); on x86-64 the same
rows read +4.3 %, +4.3 %, +0.4 %, +4.3 %, +2.9 % and **−0.8 %**.

`\w+` being +15.3 % on one ISA and −1.4 % on the other is the **placement** signature this project
documented this week — rows that disagree in direction across ISAs are not tracking engine work. Rows
that agree in direction but not in magnitude are partly that and partly the translation unit carrying
one more function. **This release does not separate the two**, and says so rather than choosing the
attribution that reads better. The delta also spans three commits, so no row's movement belongs to a
single change.

## Two ideas built, measured, and refused

Recorded on the code that will invite them again, because a refutation nobody can find gets redone:

- **A standalone non-ASCII class as a code-point class.** arm64 wants it by 1.5–2.4× (`[éàè]` 1.347
  against 3.207); x86-64 wants the opposite by 1.15–1.3× (`[éÉ]` 2.932 against 2.544). No single
  choice wins on both, so the current emission is a deliberate trade, not an oversight. Where a
  literal *precedes* the class the two ISAs agree emphatically, which is the case it exists for.
- **Removing a redundant `width()` call** in the search loop, which callgrind showed being made three
  times per match where two suffice. Carrying it cut total instructions by **21 %** — and made the
  path *slower*, reproducibly: `\w+` +20.6 % / +19.4 %, `[à-ÿ]+` +12.5 % / +12.6 %. Fewer
  instructions is not faster.
