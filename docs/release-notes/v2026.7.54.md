# v2026.7.54 — correctness: reassigning a warmed regex, a reusable capture API, and two smaller fixes

A **correctness** release, headlined by a fix for a long-standing
silent-wrong-answer bug: **assigning a new pattern onto a regex that had
already been used returned zero matches.** Ordinary container operations
triggered it. If you keep `real::regex` (or `real::compat::regex`) objects in a
`std::vector` or `std::map`, or sort / swap them, **upgrade for this.**

## The correctness fix

**Reassigning a warmed regex now rebuilds its cache** (`0464f46`). A
`real::regex` builds a small per-pattern cache (byte program, one-pass
extractor, inner-literal prefix) on first use, previously guarded by a
`std::once_flag`. Assignment — `re = real::regex(other)`, and everything that
move-assigns under the hood: `vector::erase`, `std::sort`, `std::swap`,
overwriting a map entry — reused the destination object *with its spent
once-flag*, so the cache was never rebuilt for the new pattern. The router then
mixed the new pattern's hints with the old pattern's compiled program and
**silently returned zero matches** — no exception, no diagnostic. `std::regex`
is correct on the same code, so this was also a drop-in fidelity break for
`real::compat`.

The once-flag is replaced by **program-identity invalidation**: the cache
records the program it was built for (`built_for == program.code.data()`), the
same pattern the engine already uses for its per-search DFA caches. The hot path
is a single atomic load; a rebuild — after assignment, when the identity changes
— runs under a striped lock kept distinct from the shared-DFA locks so it cannot
deadlock. The assignment operators need no change: they structurally cannot see
the new program, and the identity check makes that unnecessary. Verified by a
seven-case container matrix (`erase` / `sort` / `swap` / map-overwrite /
`assign`, plus copy and cold-assign controls), a differential against
`std::regex`, and a thread-sanitizer run; the hot path showed no measured
regression. C++ surface only — the Rust / Go / C / Python bindings pass through
handles and were never affected. **Pre-existing, present in prior releases;
upgrading closes it.**

## Also in this release

- **Rust: a reusable capture-location API** (`bd89f74`). `capture_locations()`
  plus `captures_read` / `captures_read_at` / `captures_read_iter` (and the
  `bytes` variants) fill a reusable buffer instead of allocating an owned
  `Captures` per match — mirroring the `regex` crate. In capture-dense loops
  that is ~2.3× faster than `captures_iter` on a single group (arm64, measured);
  `captures_iter` remains the ergonomic owned iterator.
- **Clearer diagnostic for an over-long bounded lookbehind** (`df15637`). A
  fixed but too-long repeat such as `(?<=\w{64})b` (256 bytes, over the 255-byte
  cap) now reports "lookaround sub-pattern too long" instead of "unbounded
  lookaround … use a fixed repeat count" — advice impossible to follow on an
  already-fixed count. Acceptance is unchanged; only the message.
- **`\b` in lookbehind, documented** (`0ecca5e`). REAL evaluates word
  boundaries inside a lookbehind per the ECMAScript reading, agreeing with
  Python `re` and node; PCRE2 has known mis-evaluations there, so it is a
  benchmark competitor, not an oracle for those patterns — now recorded on the
  divergences page.

## Discipline

The correctness fix was reproduced before and after on the exact container
operations, with a permanent regression test added; its concurrency passed a
thread-sanitizer run and its hot path showed no measured regression. The change
set was verified in code and by measurement — the reassignment bug against
`std::regex`'s own answer — before it landed.
