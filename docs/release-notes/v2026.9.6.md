# v2026.9.6 — `$` has two ends, and a DFA is not always the match

This train ships for two reasons. **`\s$` answered nothing over `"ab\n"`**, where `re` and the
engine's own general VM answer `(2, 3)` — a false answer present in twenty-two published releases.
And **`real::dfa`'s public header promised a criterion that is false**: it said a DFA reproduces a
rule's `match()` for "greedy, assertion-free" rules, and `(?:ab|a)(?:bc)?` is greedy, assertion-free,
and matches two bytes of `"abc"` where the DFA takes three. `real::dfa_faithful` now decides the
question exactly, with a witness.

## The false answer: `$` has two end positions

`$` matches at the true end **and** just before one final newline — two positions, an alternative
rather than a replacement. Both class runners kept only the second: they stripped the final newline
unconditionally. A class that can consume that newline (`\s`, `\W`, `[ \t\n]`, `[\n]`) therefore has
its legitimate match at the true end, which the runners treated as a miss.

```
\s$        on "ab\n"   → None      (re: (2, 3))
[ \t\n]+$  on "ab \n"  → (2, 3)    (re: (2, 4))
```

**Affected releases: `v2026.8.5` through `v2026.9.5`, twenty-two of them**, located by installing
each published wheel and asking (`v2026.8.4` answers correctly).

Both runners are fixed rather than narrowed, so the routes stay armed: the byte runner strips the final
newline only when its class cannot hold `\n`, and the code-point runner accepts the true end for `$`
and `\Z` and the before-newline position for `$` alone. `[ \t]+$` over `" \n"` still answers `(0, 1)`:
that class cannot hold the newline and must end before it.

**Why no test saw it, and what now does.** Every class in the end-anchor agreement lists refused the
newline, so stripping it always agreed with the general VM. This is the second silent answer in two
trains that curated (pattern, subject) lists could not reach — 9.5's `\w{2}$` was the first — so this
train adds a **cartesian gate** rather than one more pair: one shared subject corpus, newline-ending
edges included, times a pattern list that arms every Pike route, against the general VM and under
each of the eleven route-disable knobs. Breaking the 9.5 refusal reddens it on 75 checks, breaking this
fix on 272; the word-boundary family joined it with a guard that fails if its rows stop arming.

## `real::dfa_faithful`: decided, not assumed

A DFA recognises a pattern's language and takes the **longest** match; `regex::match()` takes the one
its priority order prefers. Which patterns keep the two equal is not visible in the syntax:

| pattern | on | `match()` | longest | faithful |
| --- | --- | --- | --- | --- |
| `a\|ab` | `ab` | 1 | 2 | no |
| `as\|assert` | `assert` | 2 | 6 | no |
| `(?:ab\|a)(?:bc)?` | `abc` | 2 | 3 | no — greedy, longer branch first |
| `x*?y` | any | = | = | yes — lazy |

`real::dfa_faithful(pattern)` answers `faithful`, `divergent` with an input that separates the two, or
`undecided` when its state budget (`real::dfa_default_state_budget`, the construction cap) runs out —
which a caller must read as not faithful. The answer is exact for the pattern: the search walks the
product of the priority simulation and the DFA's set simulation, and every divergence has a reachable
state that names it. Over a set, all-faithful is sufficient for a `real::dfa` to reproduce the
per-rule munch, not necessary; a masked rule is refused, which is correct and only cautious.

The decision replays the Pike walk, including its empty-iteration exit, and that detail decides
answers: without it `(?:c??)*` on `"c"` reads as faithful while the engine answers the empty match. A
differential over 600 random patterns — each answer checked against the engine on every input of up to
four symbols — holds the two walks together.

**Who it matters to.** SciLex's DFA fast path compared the two with sampled probes and missed ordinary
grammars — `as|assert` beside an identifier rule and a catch-all lexed `assert` as the keyword. Its
next release decides with this call.

The same page said a Unicode `\d` raises `dfa_error`; code-point classes expand and build, and only an
expansion too wide (text-mode `\w`) is refused. The error, both constructors, the reference page and
its example now say so.

## Public statements corrected

- **`real.error`'s stub derived from `Exception`**, while the runtime class derives from `re.error`.
  Under mypy, `except re.error` and `e.pos` failed to type-check. `mypy.stubtest` cannot see a base
  class that is too general, so `make python-stubtest` now also type-checks the code a `re` caller
  writes.
- **The Rust `Error::Unsupported` docs listed `\p{…}`**, which compiles; only an unknown property is
  unsupported.
- **The Go README cited `Test_Differential_*` and `Test_BeyondRE2_*`**, which match no test; its
  `go test -run` ran nothing and now runs seven.
- **A group inside a lookaround** is numbered and never filled (`(?=(a))a` gives `(None,)`, `re` gives
  `('a',)`). It was decided in the compiler and missing from the divergences page, and the syntax
  reference said capturing lookarounds are rejected; they are accepted. Now `div_lookaround_captures`.
- **The POSIX layer's captures** are the winning thread's, not POSIX submatch; the compat pages said
  "the POSIX semantics". macOS's libc maximises group 1 then group 2; glibc and Go agree with this
  engine.
- **The drop-in landing described the Go binding as `v0.1`**, three minors behind; the version-label
  guard now derives its perimeter instead of listing pages.

## Build and CI

The CMake `SCIFORGE_TAG` moves with the workflow pins (`v2026.9.0`), and `REAL_FETCH_SCIFORGE=ON` no
longer calls the deprecated `FetchContent_Populate` from CMake 3.18. CI refreshes only Ubuntu's apt
indexes, after a third-party index failed two workflows, and a guard refuses a workflow that goes
around it. The conformance runner's scorecard is coupled to `docs/TESTS.md`, and its flag-mapping
witness keys on the corpus's stored answers, where a flag dropped by both engines alike cannot hide.

Python wheels; the engine header is shared, so the other surfaces carry the same code, but they were
not installed release by release.
