# v2026.7.57 — the inner-literal prefilter learns to work without an automaton

A **performance** release on the **scan** path. No API changes, no behaviour
changes: every span, every capture group and every match count is byte-identical
to v2026.7.56, verified as a differential against the same engine with the routes
switched off rather than asserted.

Its shape is worth naming up front. The inner-literal prefilter — memmem a
required literal, then find where the match starts around it — had two ways to
place that start: arithmetic when the whole pattern is fixed-width in bytes, and
otherwise a **reverse DFA** over a compiled prefix sub-program, held in a
per-regex cache. This release adds three cases that need neither, and the reason
they matter beyond their own speed is that `static_regex` **has** no per-regex
cache. It could reach none of the automaton-backed routes at all.

## The row this was about

`(\w+)@(\w+)` was the one family in the criterion suite where the `regex` crate
led on **both** operations. It is `class+ <literal> class+`: so the start is where
the prefix class run ending at the `@` begins, and the end is where the suffix
class run stops. Two walks. No reverse DFA, no forward DFA, no one-pass
extraction, and every capture slot is one of four positions.

| criterion row | v2026.7.56 | v2026.7.57 | vs the `regex` crate |
| --- | ---: | ---: | :--- |
| `find/email` | 132.36 µs | **46.20** | 3.06× behind → **1.07× behind** |
| `captures/email` | 140.75 | **52.10** | 3.25× behind → **1.21× behind** |

Interleaved A/B, same bench file both sides, one criterion group at a time, two
rounds. Every other row in the suite moves by at most 2.8 %.

## Three shapes, each read off the compiled program

The class index a route needs only exists after emission, so each of these is
recognised by walking the compiled program rather than the AST — which also puts
the analysis inside `compile()`, already `constexpr`, for a linear scan's worth of
budget. That matters: a second full compile is exactly what does not fit there.

- **One greedy class loop before the literal** → the start is a backward class
  walk. `[a-z]+@…`, `\w+-…`, `\d+\.…`.
- **One greedy class loop after it as well** → the end is a forward class walk,
  and the whole match needs no engine.
- **A loopless fixed sequence of code-point atoms** → `\d{4}-\d{2}-\d{2}`. The
  byte width of a `klass_cp` is never fixed (a Unicode `\d` matches multi-byte
  digits), which is why `il_fused_eligible` could not take it, but the code-point
  **count** is — so the start is arithmetic in the right unit.

Each declines strictly. A fixed repeat count emits no `split`, so it is not a loop
shape; a lazy suffix has different split targets; a trailing byte, a second
literal, an assertion or a lookaround all leave the hint clear and the general
confirm in place. The tests pin both directions, because a shape wrongly admitted
would place starts the pattern never asked for.

## What it does for `static_regex`

Five rows of `make bench-static` used to lose to the dynamic regex. None do now:
its eleven-row table and all ten inner-literal rows favour the compile-time regex
on both walk and single-shot.

| pattern, matches present, 64 KiB walk | v2026.7.56 | now | vs `real::regex` |
| --- | ---: | ---: | :--- |
| `(\w+)@(\w+)` | 2252 µs | **39.0** | **1.11×** (was 0.06×) |
| `[a-z]+@[a-z]+` | 1043 | **34.0** | **1.14×** (was 0.18×) |
| `\d+\.\d+` | 598 | **33.0** | **1.22×** (was 0.17×) |
| `\d{4}-\d{2}-\d{2}` | 671 | **49.5** | **1.09×** (was 0.12×) |

Two more compile-time changes contribute, both about not paying for what is
already known:

- **The VM scratch is no longer zeroed on every `search()`.** `static_regex` is
  stateless (`sizeof` 1) and `search()` is `const` and thread-safe, so both
  storages build a fresh state per single search; `static_vec`'s whole worst-case
  capacity and two lookup tables were value-initialized each time and never read
  before being written. Single-shot on an 81-byte subject: `dog` 39.6 → 18.5 ns,
  `[^,]+` 280 → 172. Verified with valgrind memcheck (zero uninitialised-value
  errors, byte-identical error profile) and with the suite rebuilt under clang's
  `-ftrivial-auto-var-init=pattern`, which fills those members with a poison
  pattern instead of zeros: 344 492 checks, none failing.
- **The inner-literal route admits a cacheless storage**, under a criterion
  measured across eight patterns rather than assumed: a pattern whose core already
  has an arithmetic-width scan gains nothing and pays 20 %, so `fixed_shape`
  excludes it — in the state type, not by a branch, because compiling the block in
  at all cost `[^,]+` 5.2 %.

## Scan, separately

The cp-class leftmost scan asked `width()` for a decoded result where one bit was
wanted — a three-field struct, a `valid` test and a re-branch, to learn what the
ASCII table already held. `\d+` **−36.2 %**, `\w+` −5.4 % (arm64, each pattern
alone in its translation unit, since a nine-pattern TU moves `[a-z]+` by 12 % on
code placement alone). The same fault in the possessive loop is fixed too, and
**split by compiler**: applied to gcc the ASCII-direct predicate *reduces* its
instruction count 3.89 % and costs it 37 % of wall clock, so gcc keeps the old
form — proven byte-identical by callgrind on all six reference patterns.

`\b\w+\b` ends 2.5 % ahead of 7.56 through the crate. It remains the largest scan
deficit at 2.42× behind the `regex` crate, and `\b` is not the reason: `\w+` alone
measures within 0.7 % of it.

## Fixes

- **An empty program no longer claims byte-DFA eligibility.** `eligible` is read
  everywhere as "the byte automata can run this", so a reverse pass built over an
  empty byte program answered `npos` at every position and the caller silently
  dropped every candidate — a wrong-answer shape, not a slow one. Unreachable in
  the shipped tree; reached within ten minutes by a prototype exploring the next
  step, which is why the guard now sits at the API boundary.
- **MSVC compile-time matching.** MSVC's constant evaluator refuses an object
  carrying an indeterminate subobject even where nothing reads it, so the scratch
  change above broke every compile-time `static_assert` with C2131. The scratch is
  value-initialized under `std::is_constant_evaluated()`; the run-time path, which
  is the one that was paying, keeps the trivial initialization. The local gate has
  no MSVC leg — CI caught this.

## Two faults this train introduced, and what they cost to find

Stated because both were invisible to the instruments the work was tuned against.

**The hint fields were added mid-struct.** Six of them, placed next to the
inner-literal block they belong with, reflowed every field after them and moved
the class-loop fast path's own hot fields across a cache line. Through the crate:
`dog` **+30 %**, `\b\w+\b` **+27.7 %** — on patterns that read none of them. No
C++ harness saw it, because they call the engine directly where the crate crosses
the C ABI per match; it surfaced only when re-measuring for this stamp.
`pattern_hints` already documents that exact fault for its own `small_set` array
and says "appended last" five times over.

**A benchmark row whose absolute value is context-dependent.** Run inside the full
criterion suite, `find/word_bound` reads 409 µs against 319 on the *same binary*.
Only a like-for-like interleaved comparison means anything there, which is why the
protocol is now stated in the stamp rather than left implicit.

## Verification

`full-local-gate` 22/22 on every commit in the train, plus CI green including the
windows-msvc leg. 769 tests. Coverage 95.6 % (floor 95.0). Differentials against
the route-disabled engine: 494 pattern × subject pairs on spans and 28 on every
capture group of every match, including a literal at offset 0, runs reaching the
subject start, multi-byte members either side of a boundary, and truncated UTF-8
tails — identical everywhere.

## Notes

Nothing here changes what REAL matches. The pitch is unchanged too: the
linear-time / ReDoS-safe guarantee and the bounded lookarounds the `regex` crate
cannot compile at all, delivered through a `regex`-shaped API. What changed is that
the compile-time engine is now at least as fast as the dynamic one on every row
this repository measures, which it was not.
