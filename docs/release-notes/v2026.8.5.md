# v2026.8.5 — an anchor is a mode, not a shape

Anchored patterns are the shape most validation code is written in — `^[a-z0-9_]+$` for an
identifier, `^\d{4}-\d{2}-\d{2}$` for a date field, `\w+$` for a suffix. In every version before this
one, writing that anchor cost between 13× and 94× against writing the same question without it.

Every match count, span and capture group is identical to v2026.8.4, on both ISAs.

## The anchor disqualified every fast route

`^[a-z]+` in search mode and `[a-z]+` in prefix mode are the same question. The second reached the
class loop; the first carried the anchor as an assertion in the compiled program, which disqualified
every shape route and dropped it on the general VM. Measured over a 100 KB subject:

| pattern | before | after | |
| --- | ---: | ---: | ---: |
| `^[a-z]+` | 2.585 ns/B | **0.032** | **81×** |
| `[a-z]+$` | 3.100 | **0.032** | **94×** |
| `^\w+$` | 1.450 | **0.066** | **22×** |
| `^[a-z]+$` | 0.573 | **0.043** | **13×** |

The recognizers now **peel** a leading `\A`/`^` and a trailing `\Z`/`$` and report them; the routes
they arm honour them. A lead anchor is a **mode** — a search becomes prefix anchoring, and a region
beginning past 0 cannot hold the match at all. A trailing anchor is a **limit** — the leftmost match
is the run that finishes exactly there, found by walking back from it rather than by scanning forward
and discarding every run whose end is wrong.

Multiline `^`/`$` are different assertions (line start, line end) and still disqualify the shape.

**`^X$` is NOT `fullmatch(X)`**, and the difference is why the limit is computed rather than assumed:
`$` also matches just before ONE final newline, so `^a+$` matches `"aaa\n"` while `fullmatch(a+)`
does not. `\Z` is the strict end. All three answers are pinned by the tests that ship with this.

**§A now has an anchored row**, because none of its eight existing cases could see any of the above —
every one is free-floating, so a 94× change moved nothing in any published table, and an unmeasured
row is one that regresses in silence. `anchored ^[a-z]+$` over a 200 KB subject reads:

| | REAL | PCRE2-JIT | RE2 | `std::regex` |
| --- | ---: | ---: | ---: | --- |
| **arm64** | **0.32 ns/B** | 0.43 (1.35×) | 2.19 (6.87×) | unsupported |
| **x86-64** | **0.51** | 0.52 (1.01×) | 1.78 (3.46×) | unsupported |

REAL ahead of PCRE2-JIT on both ISAs. `std::regex` is `unsupported` there and the word is doing real
work: libstdc++ recurses once per input character and **SIGSEGVs** on a 200 KB anchored subject —
about 98 000 stack frames — while libc++ survives. It is a crash, not a capability gap, and it cannot
be caught, so the harness declares the skip with that reason rather than dying with it.

## Three guards, from three oracles, none of them foreseen

This is the part worth keeping. The anchoring change was wrong three times, and each time a
*different* checker found it:

- **`[a-z]+\b$`**, by the seam differential. A `\b`/`\B` wrap takes its own branch in these routes and
  that branch never sees an end limit.
- **`\b(?>\w)$`**, by the Python binding's differential fuzz **against `re`** — the same hole through
  a *leading* wrap, which the first guard did not cover. REAL matched where `re` correctly does not.
  The C++ seam differential, the anchored-shape tests and 11 178 span comparisons had all passed.
- **A shadowed local**, by MSVC's `/WX` (`C4456`). It compiled clean through all 23 local gate steps
  and through gcc and clang in CI, because `-Wshadow` is in neither `-Wall` nor `-Wextra`.

A wrap and an end anchor together are now refused rather than combined — once the assertion is peeled
out of the program, nothing downstream can re-derive it. And `gcc-check` passes `-Wshadow`
explicitly, with the reason written beside it.

## The ReDoS table was measuring two engines out of four

§C's own text calls `^(a+)+$` the distinguishing shape — anchored at both ends with a breaking
suffix, so there is no required literal to prefilter and nothing to auto-possessify. The harness
asked it only of REAL and PCRE2. Asked of all four, at N = 100 000:

| engine | `(a+)+b` | `^(a+)+$` |
| --- | ---: | ---: |
| REAL | 0.003 ms | 4.00 ms |
| RE2 | 0.220 ms | 0.220 ms |
| PCRE2-JIT | 0.005 ms | refused (catastrophic backtracking) |
| `std::regex` | refuses from N = 13 | refuses from N = 13 |

The safety claim gets **stronger** — REAL and RE2 are the only two engines linear on both shapes, now
measured for all four rather than asserted for two. The throughput claim on that row gets **weaker**:
RE2 answers the resistant shape 18× faster, and the incomplete table was hiding that.

Two harness defects were fixed while adding those cells. The `std::regex` rows fed both shapes the
same subject, so whichever shape it happened to satisfy answered in microseconds and was reported as
having survived backtracking. And they sat entirely above libc++'s cutoff, so all three read
"refused" and showed none of the curve — swept 8…26, the time **doubles per added character**
(0.068 → 0.275 → 1.115 ms at N = 8, 10, 12) before the implementation refuses outright from 13.

## A site build broke on a deleted sentence

A benchmark re-stamp deleted the prose a documentation page sliced on with `:start-after:`, and
`full-local-gate` could not catch it: its docs-site step is skipped whenever `sphinx-build` is absent,
which it is on a plain dev machine. **`make check-site-anchors`** now runs in the gate's cheap
section, needs nothing but the standard library, and requires every `:start-after:`/`:end-before:`
under `docs/site` to resolve **exactly once** — an anchor that appears twice silently slices the
wrong region. Its own first version was blind to every MyST page and reported 18 clean anchors;
fixed, it sees 29, and both failure modes were injected to prove it fails.
