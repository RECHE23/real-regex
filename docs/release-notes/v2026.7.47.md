# v2026.7.47 — `\p{}` 2-stage membership (CJK page-bitmap extension)

Closes the structural CJK gap on Unicode property membership: the European page
bitmap (`cp_page`, U+0080..U+07FF) already answered Latin/Cyrillic/… in one load;
code points above U+07FF fell back to bsearch over hundreds of ranges (`\p{L}` =
675). That was the §Unicode hole vs PCRE2-JIT on `\p{L}+` CJK.

## What changed

**2-stage sparse `cp_hi_table`** (page = `cp>>8` → 256-bit block):

- Built lazily from the same `cp_ranges` tables (oracle-identical).
- Held **`thread_local`**, not on `pike_state` — `sizeof(dynamic_storage::state_type)`
  stays **7384** (ASCII class-loop safe; leçon §A / 7.43 fields drift).
- **K=32**: classes with fewer than 32 ranges stay on bsearch (`sc=Han`=22,
  `scx=Cyrl`=18 already quasi-tie).
- Build is cold-outlined; hot probe is last-hit sticky + bit test.
- Class-loop splits page (`cp_member_page`) vs high (`cp_member_high`); gcc outline
  (`cpclass_gcc.hpp`) follows.

## Honest residual

The arm64 +22–27 % on `\p{N}+` / `sc=Han` / `scx=Cyrl` is **codegen-luck**, not the
new 2-stage: those paths are page-only (Arabic-Indic digits ≤ U+07FF) or single-cp
VM under K=32 (still bsearch). **x86 does not reproduce it** (plat or faster on the
same cells). Accepted like the AC `fields +39 %` exception — **not chased** (leçon AC).
D1b (program-level shared tables, shared-confirm 7.45 model) remains on the shelf.

§A was re-stamped on v7.46 immediately before this train (docs-only): x86 class-loop
drift disclosed, arm64 flat.
