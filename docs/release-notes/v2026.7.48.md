# v2026.7.48 — mid-pattern `\b` fixed_shape peel (correctness)

A correctness fix for the **fixed-shape** fast path under `flags::bytes` (the
default for the `real::compat` std/RE2 drop-ins). No performance claim; ships
because the bug was **live in v7.47** and reaches every bytes-mode consumer.

## What was wrong

`detect_fast_shapes` treated **any** word-boundary assert after the consuming
body as a *trail* `\b`/`\B` wrap (`wb_trail`), even when more pattern followed
(e.g. `\w{2}\bthe`). At match time, `match_byte_klass_run` stops at the first
non-byte/klass op — so it verified only the prefix and applied the trail
boundary at that end, **silently dropping the trailing literal**.

Symptom (fuzz-compat, libFuzzer `__builtin_trap` on span/verdict divergence vs
`std::regex`):

| | |
| --- | --- |
| pattern | `\w{2}\bthe` |
| subject | `\xa3ox` (bytes) |
| buggy (bytes) | match `[1,3)` = `"ox"` |
| correct / std | no match |

(Unicode/default mode did not hit the same false positive on this case; compat
always builds with `flags::bytes`.)

## The fix

Trail `\b` is peeled **only** when it sits **immediately before** `save 1` /
`match`. A mid-pattern `\b` declines fixed_shape and falls through to the
general VM (which already handled the shape correctly).

True trail wraps keep the fast path: `\w{2}\b`, `\b[0-9a-f]{8}\b`, etc.

## Who should upgrade

Anyone on **v7.47** (or earlier with the same fixed_shape trail peel) using
**bytes mode** or the **compat** surfaces (`real::compat::std` / RE2 drop-in)
with patterns of the form `<fixed body>\b<more>` — not only the impossible
`\w{2}\bthe` shape, but any mid-pattern `\b` after a fixed-width run.
