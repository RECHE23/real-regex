# v2026.9.1 — five oracles, and the four wrong answers only they could see

This train is corrections. Four of them are **wrong answers**, not diagnostics — a `RegexSet` that
reported no match where every member matched, `^` that matched nothing at all on certain subjects,
an inverted region that leaked a standard-library exception, and a Rust search that answered with a
match before the offset it was given. Five C ABI entry points also segfaulted on an input the
header documents as an error.

They were found the same way, and it is the only new idea in this release: **each surface was swept
against ITS native oracle**, not against one oracle for all. Python against `re`, Go against
`regexp`, Rust against the `regex` crate, POSIX against libc's `regcomp`, and `RegexSet` against
N independent `search` calls. Two of the four wrong answers were invisible to `re` by construction
— `re` indexes `str` by code point, so a UTF-8 continuation byte can never be a start position
there, and no number of comparisons against it would have found the `^` fault. 628 740 comparisons
against `re` had already passed.

It also carries a **breaking change to the Go binding**, released separately as module `v0.3.0`.

## Four wrong answers

**A fused `RegexSet` did not see a member that matches the empty string.** Above the fusion
threshold (56 eligible members), a set of nullable patterns answered all-false on `""` where this
type's own contract — N × `search` — answers all-true. `RegexSet(["x*"] * 56).matches("")` gave
0/56. Below the threshold the set N-walks and was always right, so the fault appeared only at the
size where nobody re-reads a generated pattern list.

The fused walk folds accept masks *after* consuming a byte, inside a loop that an empty subject
never enters. The start state's own mask — "accepts before reading anything" — is now folded once
before the walk. The byte-consuming path is untouched and was already right.

**`^` matched nothing on a subject beginning with a UTF-8 continuation byte.** The seeding check
refuses a position whose byte is `10xxxxxx`, because a match cannot begin *inside* a multi-byte
sequence. That is a claim about the byte *before* the position, and the region's start has none —
so the subject lost its position 0 entirely, and `^`, which is the start of the subject by
definition, matched nothing. `$` never showed it: the same check short-circuits at end-of-text, so
the subject's end answered and its start did not.

Reachable from every byte-oriented caller — the C ABI, Go, Rust. Interior continuation bytes are
still refused, which is what keeps zero-width iteration codepoint-aligned rather than byte-aligned.

**An inverted region leaked a standard-library exception.** `search(text, pos, endpos)` with
`pos > endpos` handed `pos` to the VM past the end of a truncated subject, and a `substr` deep
inside threw `std::out_of_range` — a standard-library exception surfacing from a search, on input
`re` accepts and answers `None` for. It now returns no match, as `re` does.

**Rust's `find_at` answered with a match before the offset it was given.** `find_at("x*", "ab", 2)`
returned `(0,0)` where the leftmost match from 2 is the empty one at 2. Only the empty case was
wrong, and only because of how the empty case is handled: the iterator switches to driving the
search by position at the first empty match, and resumed that drive from a fallback of 0 when
nothing had been yielded yet — which is exactly the state an `_at` constructor starts in.
`find_at`, `captures_at` and `captures_read_at` were affected.

## Five C ABI doors that crashed

`real_capi.h` states its rule once for the whole header: `(NULL, 0)` is a valid empty buffer, only
NULL with a claimed length is an error, and no failure here is ever "a crash or a propagated
throw". Eight entry points returned the documented sentinel. Five dereferenced instead:
`real_find_iter`, `real_find_iter_at`, `real_find_iter_between`, `real_compile`, and
`real_set_compile` on a NULL **member** of a non-null array — that last one a different shape,
since a non-null `patterns` says nothing about `patterns[i]`, and its error now names the index.

The five that dereferenced now share one predicate. The eight that already returned the sentinel
keep their existing guards — a rule written once and copied is how a contract ends up true at
eight doors and false at five, and that is what this avoids on the path that crashed.

## An iterator that compared offsets, not walks

`basic_match_iterator::operator==` compared only "exhausted?" and "which offset?", so two iterators
over *different* walks compared equal whenever they sat at the same position — `find_iter("X")` over
`"aXbXc"` equalled `find_iter("Y")` over `"aYbYc"` at position 1, while dereferencing to different
text. Unlike a container iterator, this one owns the sequence it walks and the program it runs, so
the identity was already in the object.

Both exhausted iterators stay equal whatever they walked, and that is deliberate: `end()` returns a
default-constructed iterator, so a walk's own end carries neither text nor program. The check sits
on the live branch only — which is also why it is free, since a loop condition never reaches it.

## Diagnostics: what, not only where

The family the previous release opened is now closed. Each of these had the reading in hand and
threw it away:

| pattern | before | now |
| --- | --- | --- |
| `[z-a]` | `bad character range at 1` | `bad character range z-a at 1` |
| `ab\q` | `unsupported escape sequence at 3` | `unsupported escape sequence \q at 2` |
| `a\x1` | `invalid \x escape: expected two hex digits` | `incomplete escape \x1 at 1` |
| `(?P<a b>x)` | `bad character in group name` *(no name quoted)* | `bad character in group name 'a b' at 4` |
| `a(?i)b` | `global flags not at the start at 4` | `global flags not at the start at 1` |
| `a{2}{3}` | `multiple repeat at 7` | `multiple repeat at 4` |
| `a{2,1}` | `min repeat greater than max repeat at 1` | `… at 2` |
| `\N{X}` | `undefined character name 'X'` *(no position at all)* | `… at 0`, with `pattern` and `colno` |

Every one of those positions is `re`'s, verified against it rather than chosen. The wording is
`re`'s too on all but one row: an unrecognised escape keeps this engine's own `unsupported escape
sequence` where `re` says `bad escape`, because the `unsupported` classification is what a binding
branches on and only the *reading* was missing. `\N{X}` had no position at all — not a wrong one, an
absent one — and now carries `pattern` and `colno` besides.

Three of those were the same defect in three shapes: a diagnostic that reports where the *scan*
stopped rather than where the fault *begins*. The flag-group drift grew with the flag run — `(?imsx)`
was further off than `(?i)`.

A `RegexSet` compile failure also stops corrupting its own attributes: `e.pattern` was an integer
(the position, landed in the pattern slot) and `e.pos` was `None`. It now carries the offending
member, its position, and **which** member — `missing -, : or ) (in pattern 1 of 3)`.

## Additive

**`real_expand`** exposes `real_sub`'s inner half: expand a replacement template against one match,
given that match's spans. A binding whose flavour enumerates matches differently could not use
`real_sub` at all without inheriting Python `re`'s match sequence, and reimplementing the template
grammar binding-side would put a second expander on a drift course with this one.

**A group name may be any Python identifier**, as `re` allows — `(?P<café>…)` compiles.

## The Go binding: module `v0.3.0`

Not a patch. Asking `regexp` for every answer across the whole `Regexp` surface — 57 916
comparisons, plus 799 subject pairs for the `[]byte`/`string` duality and 3 916 for `ReplaceAll` —
found four things:

- **`$` was `re`'s, not `regexp`'s.** RE2's `$` without `m` is the very end of the text; the
  engine's default also matches just before a trailing newline. `foo$` matched `"foo\n"` here and
  did not under `regexp` — silently, on one of the most ordinary patterns there is.
- **The empty-match rule is a cursor, not a filter.** `regexp` never returns two matches from one
  start; `re` retries the same position for a longer one. `a*?` over `"a"` gave `[0,0] [0,1]` where
  `regexp` gives `[0,0] [1,1]` — and the two delivered matches **overlapped**.
- **`ReplaceAll` counted matches differently from every other method on the same object**, because
  it handed the whole job to `real_sub`. It now walks this package's own enumeration.
- **`FindStringSubmatchIndex` did not exist** — the one missing cell of an otherwise complete
  16-method `Find*` family.

If you use the Go binding, `Split`, every `FindAll*` and `ReplaceAll` may return different results
for patterns that can match empty, and `$` no longer matches before a trailing newline. Those are
the results `regexp` gives.

## Benchmarks: the tables do not move, and the stamp stays at `2026.8.15`

No number in `docs/BENCHMARKS.md` is refreshed in this train, deliberately. The document declares
its regime as **two ISAs** — x86-64 and arm64, both legs, three runs each with the minimum per cell.
Only arm64 was available. Re-stamping one leg would produce a table whose two halves describe
different trees, which is worse than an honest warning; `check-bench-stamp` allows proceeding
knowingly, and this is that.

What the engine changed here is small and mostly off the measured paths: a guard on the seeding path
that short-circuits before doing any added work, a mask fold that runs once before a walk, an
equality check on a branch a loop condition never reaches, and diagnostics that live on error paths.
The project's own veto matrix — 26 route-vs-core rows, 5 % tolerance — read clean on every gate over
this train. That is a veto, not a measurement of this train against the last one, and it is cited as
what it is.

See `CHANGELOG.md` for the per-train benchmark-impact entry.

## Upgrading

**C++, Python, Rust, C:** the wrong answers above were wrong; the fixes change what those cases
return, and nothing else changes what a pattern matches. Error *messages* and error *positions*
moved on the constructs listed above — code that matched on the text of an error was never promised
that it would stay still.

One C++ contract did tighten: `basic_match_iterator::operator==` no longer reports two iterators
from different walks as equal. Comparing iterators across sequences is unspecified for a standard
container too, so no correct program depended on the old answer.

**Go is the exception and it does not fail loudly:** results change for empty-matchable patterns and
for `$`. See the module notes for `v0.3.0`. Nothing stops compiling — `FindStringSubmatchIndex` is
an addition.
