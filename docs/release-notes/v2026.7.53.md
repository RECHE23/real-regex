# v2026.7.53 — hardening: a memory-safety reclaim, a warm-path perf recovery, binding crash-safety, and doc honesty

A **consolidation** release. It leads with a **memory-safety fix** — match-time
DFA caches no longer outlive the regex that built them — and carries a warm-path
performance recovery, a batch of binding/compat robustness fixes, differential
nets, and a documentation-honesty pass. Every engine change is measured on the
ProxMox devbox and, per the repository's law, confirmed on **both ISAs**
(x86_64 and arm64) with interleaved same-host A/B.

## Memory safety — the headline

**Reclaim shared DFA slots on regex destruction** (`3d17fe9`). The process-wide
side table that caches each regex's lazy-DFA / one-pass / inner-literal-reverse
transition tables was keyed by the compiled object's address and **never
erased** — a destroyed regex left its caches (megabytes, for a pattern like
`(\w+)@(\w+)`) alive until process exit. Distinct-pattern churn accumulated
without bound: **the exact shape the `SECURITY.md` threat model targets** (a
service compiling untrusted patterns over its lifetime).

The destructor now erases the entry. The slot is a `shared_ptr` so a concurrent
scan cannot be freed under it; an atomic epoch invalidates the per-thread
last-hit cache on address reuse (a new regex at a recycled address never
inherits a destroyed one's DFAs); the map is an intentionally-leaked singleton
so it stays valid through static teardown. Measured: **the cache map returns to
zero on destruction**, and freed memory is reused across create/destroy waves
rather than accumulating (200 distinct regexes retained ~nothing after
destruction, versus unbounded growth before). 2-ISA, thread-sanitizer-clean,
address-reuse correctness proven by a differential, guarded permanently by a new
lifetime test. If you compile many distinct patterns over a process's life —
especially on untrusted input — **upgrade for this.**

## Performance

**Warm-aware inner-literal haystack floor** (`e9b7ccf`). The inner-literal route
(memchr on the required literal, then a reverse-DFA confirm) is vetoed below a
size floor whose only job is to amortize the reverse-DFA *build*. That floor was
calibrated cold-safe (~94 KB for the email `\w+` prefix) — but the reverse DFA
now lives in the shared cache, warm across scans, so a **reused** regex (the
common case, and every benchmark) paid the slower core on sub-94 KB inputs for
no reason. The floor is now **warm-aware**: the first candidate-scan on a regex
keeps the cold floor; every subsequent scan drops to ~4 KB. Measured on warm
email at 64 KB, both ISAs: **sparse ~500× faster** (the memchr skips the filler
the core plodded through), **dense ~1.0–1.6×**, and no change above the old
floor. Honest cost: a compile-plus-single-sub-94 KB-scan one-shot pays ~3% (the
slot is touched one candidate earlier) — the accepted price for the warm win on
every reused regex.

## Binding & compat robustness

Five fixes closing crash and fidelity gaps found by reviewing the full API
surface by enumeration rather than by sampling:

- **Null-safe C ABI handles + a documented closed-handle contract**
  (`6bd0a8a`). Every C-ABI entry that dereferences a handle now null-guards; the
  header states the contract for each.
- **Go: crash-free after `Close`, and long `SubexpNames`** (`b54f861`).
  Post-`Close` calls on *every* `Regexp` / `RegexSet` method are now safe
  (recoverable, not a segfault), and group names longer than the old fixed
  buffer round-trip bit-for-bit via a two-call length protocol.
- **Rust: two-call group-name fetch — no truncation, no alias collapse**
  (`c193c92`). Names beyond 127 bytes were truncated and could collapse two
  distinct names onto one; the fetch now sizes exactly.
- **`real::compat`: the missing `regex_replace` output-iterator + C-string
  overload** (`c4b6710`), restoring literal-format
  `regex_replace(back_inserter, …, "+")` parity with `std::regex`.
- **Engine-doc flags brief corrected** (`67efb57`): case-insensitive matching
  folds Unicode in text mode (ASCII-only under `flags::ascii`), not ASCII-only
  across the board.

## Nets

- **Differential-fuzz word-boundary allowlist** (`bb35fc4`). `std::regex`
  (libstdc++ *and* libc++) mis-evaluates `\b`/`\B` in at least two independent
  ways, so it is not a safe oracle for word-boundary patterns — node and CPython
  agree with REAL, and the spec behaviour is pinned in the compat suite. The
  compat differential fuzzer now allowlists `\b`/`\B`, and skips inputs where
  `std`'s backtracker throws `error_complexity` mid-match (no oracle answer).
- **The 4-D veto matrix now samples the `codepoint_class` + short-run
  class-scan routes** (`0516b48`), closing a coverage hole.

## Documentation

A doc-honesty pass — the deep pages (compatibility, divergences, tests,
benchmarks) were already credible; the gaps were in the top-of-funnel and one
stale headline number:

- **The Python linearity guarantee names the fallback opt-out** (`3ad7402`):
  the site page stated the linear-time guarantee absolutely; it now says, as the
  binding README already did, that opt-in `fallback=True` delegates to the
  backtracking stdlib `re` and forfeits the guarantee for that pattern
  (`Pattern.engine` reports which backend ran).
- **The Features matrix is now exhaustive** (`1307674`): possessive quantifiers
  and atomic groups — marketed as differentiators and documented on the
  divergences page — now have rows, with CI-probe patterns.
- **The performance page leads with a summary** (`645ab5c`) instead of opening
  cold on the raw ledger; a stale wheel note is purged.
- **The landing qualifies "drop-in" per surface** (`5a7cdc5`) and grounds the
  lookaround-uniqueness claim by naming the compared engines in each family.
- **An honest ReDoS pair** (`f9b1a5d`): the headline `(a+)+b` figure was a stale
  number that measured neither the prefilter nor the engine. It is now two legs
  — the required-literal prefilter (~2 µs over 100 K: no `b` → reject without
  running the VM) and the bare engine on `(a+)+` (~5 ms at 100 K, ~50 ms at 1 M:
  **linear**, the guarantee) — re-measured on arm64 M1 with an x86 cross-check.

## Discipline

Every engine change here was measured before it landed and confirmed on both
ISAs with no per-ISA regression; the memory-safety fix additionally passed a
thread-sanitizer run and an address-reuse correctness differential. External
review findings were verified in code and by measurement — several against the
reviewer's own figures — before any line changed.
