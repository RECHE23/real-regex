# v2026.9.5 — `\w{2}$` answered None

This train ships for one reason: **`\w{2}$` reported no match where a match exists.** Not an exotic
construct, not a diagnostic — two word characters at the end of a string, and the engine answered
`None` on `"xab"` while matching the same pattern on `"xxab"`. Present in thirty published releases,
on all five surfaces, and confirmed in the `2026.9.4` wheel on PyPI.

## The false answer, and its arithmetic

A code-point class under a *counted* repeat, anchored at the end, was only found when the match's
start offset was a multiple of the repeat's width:

```
\w{2}\Z  "ab" → [0,2) ✓    "xab" → None ✗    "xxab" → [2,4) ✓    "abc" → None ✗
\w{3}\Z  succeeded iff (len - 3) % 3 == 0
```

The route that handles these shapes retries after a failed candidate by skipping past the whole run,
on the ground that **a maximal run stopping short of the limit can never be the match** — no later
start inside it could succeed. That holds for `+` and `{k,}`, whose run *is* maximal. It fails for
`{k}`, whose run is bounded from above: on `"xab"` the candidate at 0 fails, a match exists at 1, and
the skip lands on 2. Every odd offset was simply never tried.

The general VM was right throughout — forcing the class fastpath off answered `[1,3)` — so this was
a route disagreeing with the engine behind it, not a parser or a program defect.

**The fix is a refusal, and it has a twin that was already there.** `counted_end`
(`cp_max != 0 && close.end_anchor != 0`) unarms the route for exactly this shape, beside
`counted_wb`, which unarms it for a counted run under `\b`/`\B` for the *same* reason one assertion
over. That is why `\w{2}\b` was correct all along. The alternative — teaching both retry loops to
step by one code point — is the lift `counted_wb` named and deferred in the same breath, and it is
deferred again rather than attempted here.

**Both belong to the same commit.** The route for a counted code-point class and its word-boundary
refusal arrived together, on 2026-07-29; the end-anchor sibling was missing from the start. Affected
releases: `v2026.7.60` through `v2026.9.4`, thirty of them.

Unaffected, and each for its own reason:

| spelling | why it was right |
| --- | --- |
| `\w{2}` (unanchored) | no end limit, so no skip past a bounded run |
| `\w{2}\b` | `counted_wb` had already refused the route |
| `\w{2,}\Z`, `\w+\Z` | unbounded above: `cp_max` stays 0, the run is maximal, the skip is sound |
| `[a-z]{2}\Z` without icase | a byte class, never on the code-point route |
| `.{2}\Z` | a different route entirely |

`[a-z]{2}$` **under icase** was affected, and the reason is worth stating: the fold gives `[a-z]`
non-ASCII partners (the long s, the Kelvin sign), which is what turns it into a code-point class and
puts it on this route at all.

**Why no test saw it.** The end-anchor agreement test — which differences this exact route against
the general VM, and which exists for this class of bug — carried six patterns, and every one of them
was unbounded: `[a-z]+$`, `[a-z]+\Z`, `[0-9]+$`, `[a-z]{2,}$` and the `^`-prefixed forms. The skip is
only wrong for a run bounded from above, so the list could not reach the hole it was built to guard.
`\w{2}$`, `\w{2}\Z` and `\w{3}\Z` join it, and the new witnesses assert **answers**: the wrong
program produced no match where one exists, which no shape comparison names.

## How it surfaced

`REAL_FUZZ_ITERS=200000` is the budget the Python differential fuzzer's own docstring advertises for
a local run. CI runs 4 000. Nobody had run the advertised one, and it was red on `main`, on this
defect — `[a-z0-9]{2}\Z` under icase over `"2c00bcc2b"`, where `re` answers `[7,9)`.

That run aborted at the first disagreement, roughly a quarter of the way in by wall clock. With the
refusal in place the same seed and budget complete clean, so the three quarters that had never been
reached now have been. That is a statement about **those 200 000 draws under seed 20260612** and
nothing more: a different seed samples the space differently rather than more deeply, and no claim is
made here that this budget is sufficient, or that it would have caught any other defect.

## Also in this train

**The Go binding's living pages say `v0.3`.** The binding README's opening and its `API surface`
heading, the drop-in page's subset line and its version-specific paragraph, and the package comment
pkg.go.dev renders all said `v0.2` while the published module was `v0.3.3` — one minor behind.
Nothing they *said* was wrong; they were wrong about what they *were*, which no content check sees.
`check-go-version-labels` now reads the same `bindings/go/v0.*` tags the release recipe derives the
next module version from, so tagging a new minor turns the pages red at the moment they can still be
fixed. The label is the minor, not the patch, and the drop-in page's HTML comment still names the
v0.2.0 arity break, because that is the page's own history. No method count was added: a closed count
is what goes stale, one method at a time.

That change moves no answers.

## Benchmarks: the tables do not move, and the stamp stays at `2026.8.15`

Fifth train in a row, same reason and no new argument: `docs/BENCHMARKS.md` declares a **two-ISA**
regime and only arm64 was available. Publishing one leg would produce a table whose halves describe
different trees. **No cell was re-run and none is edited.**

**This train changes answers, so 9.2's "unreachable from a pattern that compiled" argument is not
available and is not reused.** What replaces it was measured, not asserted — and it matters here,
because the fix takes a shape *off* a fast route, which is exactly what a performance veto watches:

- **The one cell that looks like the affected shape is not on that route.** The date-time cell
  `^[0-9]{4}-[0-9]{2}-[0-9]{2}_…$` is a fixed-shape pattern and reports `greedy_cp_class == -1`
  **before and after** the refusal: `[0-9]` gains no non-ASCII partner under any flag, so it is a
  byte class and never reached the code-point route.
- **The shape actually disarmed is `\d{2}$` / `\w{2}$`**, measured `0` before and `-1` after. No cell
  has it: the nearest, `(\d{4})-(\d{2})-(\d{2})`, carries no end anchor, and `\d{2}` unanchored stays
  armed.
- **So `matrix-gate` has nothing to react to**, and the cost of the refusal falls on a shape that was
  answering wrongly.

Nothing else was run against the previous tree. `GATE_STRICT` is asserted nowhere, the veto matrix
was not exercised for this train, and `conformance` could not have seen this defect either: the
exhaustive compat sweep enumerates over the alphabet `ab`, where the shape is unreachable.

## Upgrading

**Everyone:** a patch. No source break, no API change. A counted code-point class anchored at the end
— `\w{2}$`, `\d{3}\Z`, `[a-z]{2}$` under icase — may start matching where it previously reported
nothing. If you worked around the old behaviour, remove the workaround.

**Go:** module `v0.3.4`, a patch. The Go surface did not change; the vendored engine header did, and
the fixed answers arrive with it.
