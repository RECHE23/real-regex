# v2026.8.18 — the first hour, the other surfaces

**The matching engine did not move.** Eleven commits, zero executable lines in the
matcher. What a newcomer types first did: Go's tutorial methods, a `ReplaceAll` that
no longer swallows `$year` as a success, `println!("{}", re)` in Rust, and three
hand-written lists replaced by the thing they were guessing at.

## Go

The binding was index-only. `FindSubmatchIndex` was there; `FindStringSubmatch` — the
line a `regexp` tutorial writes second — was a compile error. `Match` / `MatchString`,
`Find` / `FindString` / `FindIndex` / `FindStringIndex`, `FindAll` / `FindAllString` /
`FindAllStringIndex`, `Split`, `FindSubmatch` / `FindStringSubmatch` and the `FindAll`
submatch twins now wrap the same C ABI. Each is compared against `regexp` itself on
the same inputs, so nil-vs-empty and `n` (0 → nil, <0 → all) mean what they mean
there.

`ReplaceAll` accepted `regexp`'s `$1` / `$name` / `${name}` and emitted them **as
literal text with `err == nil`**. It refuses them now, and it decides by asking
`regexp.Expand` rather than by a hand-written list — the list it replaced was wrong
in both directions, missing `$name` (Go's documented spelling, the idiomatic
named-group replace) and rejecting `$&` (which Go leaves alone). `$$` stays two
dollars, and that is written down: collapsing it to one would be translating a
single `$` spelling in a binding that deliberately translates none.

Still a `regexp`-shaped subset, not a drop-in — the hero says so. `FindAllIndex`
takes no `n`; `Expand`, `QuoteMeta` and the package-level `Match` / `MatchString` are
not there yet. `Compile` and `MustCompile` are the only package-level entry points.
(`QuoteMeta` already exists on the vendored C++ RE2 surface; the Go binding does not
expose it.)

## Rust

`println!("{}", re)` and `"\d+".parse::<Regex>()` compile: `Display` and `FromStr`,
on `Regex` and on `bytes::Regex`.

An `Error::Unsupported` advertised the `fallback` feature whatever the pattern, and
two of those were dead ends. A `RegexSet` never delegates at all, and the `regex`
crate is linear too — it refuses a backreference exactly as REAL does, which this
repository's own test has pinned since it was written. The hint is now decided by
the delegate itself when the feature is on, and promises nothing it cannot check
when it is off. The same pass caught the README selling `\p{Bidi_Class=L}` as
delegable; the crate refuses that one.

`Captures::expand` is still absent and named as such — `replace` / `replace_all`
already take the `$` template.

## The engine did not move, and that is checkable

No executable engine line changed in this release. `include/` carries ten lines of
comment on `real.hpp` and one new alias header, `<real/regex.hpp>`, whose only
non-comment content is an include guard and `#include "real.hpp"` — the name a
newcomer types. `regex_set` and `dfa` stay opt-in. The tables in
`docs/BENCHMARKS.md` remain stamped `2026.8.15` and describe that stamp; with no
engine change here there is nothing for them to have missed.

## Two more instruments replaced by their oracle

The Go `$`-template list above is one. The other guarded the landing page: it
forbade "pasted snippet code" by grepping a list of tokens, one of which was
`static_regex` — the exact word the corrected constexpr card has to use, so honest
prose turned the site build red. The rule is now structural: every `<pre>` in the
template must be one `{{ quickstart_* }}` placeholder, and prose in a `<p>` cannot
trip it. Its premise — that a pasted snippet is a `<pre>` — is written down as the
assumption it is, since that is what bounds the coverage.

## Documentation

The landing named `real::regex` as the constexpr type. It is not one: it allocates,
so it cannot be held as a `constexpr` variable — `real::static_regex` carries the
pattern in its type. (A `real::regex` inside a `constexpr` function does evaluate
at compile time; the card no longer claims otherwise in either direction.)

C++'s `replace` was briefed as Python `re.sub` while its template is ECMAScript
`$1`; the brief now says which spelling lives where. `\u{…}` is the `regex` crate's
spelling — REAL wants `\u00e9` (four hex digits) or `\x{e9}` (braces belong to
`\x`) — and it now appears in the Rust README, the drop-in page, and the language
table, so C++ and Python are not silent about it either.

A rejected pattern now says where the way out is, and where there is none: a native
`real::regex` has no opt-in by design, C++ reaches one through
`real::compat::policy::fallback` and Python through `fallback=True`, while Rust's
`fallback` feature does **not** reach that far — it delegates to the `regex` crate,
which refuses the same constructs.
