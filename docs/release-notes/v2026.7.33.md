# v2026.7.33 — strict UTF-8 for `.` on every route, x86 stop-set regression recovered

Patch release. Closes a UTF-8 validation gap in `.` (bare dot, text mode)
found while hardening the test suite around 7.32's linear-time fix, recovers
a throughput regression that same release had shipped on x86, and drops a
compile-time-only flag added mid-train once its root cause turned out to
have a cleaner fix. No API changes.

## Fix (correctness) — `.` accepted three classes of malformed UTF-8 as one code point

`.` (and negated-ASCII-only classes like `[^,]`) wrongly matched an
**overlong encoding** (`E0 80 80`, `F0 80 80 80`), an **encoded surrogate**
(`ED A0 80`), and a **code point past U+10FFFF** via a structurally-plausible
lead byte (`F4 90 80 80`) as a single valid code point — a "UTF-8 smuggling"
class of bug: exactly the kind of input a validator built on `^.{1,N}$`-style
counting would be fooled by. `decode_codepoint_strict` (the pattern-side
decoder) and explicit-codepoint classes (`[é]`, `[^é]`) already rejected all
four correctly; the gap was isolated to two independent implementations of
`.`'s own width/validity check, neither of which narrowed the *first
continuation byte*'s valid range per lead byte the way a correct decoder
does (Unicode Table 3-7).

Both are now fixed via one shared bounds table
(`real::detail::utf8_second_byte_bounds_table`) giving that per-lead-byte
range directly — a lookup, not a full decode, so it costs nothing on the
hot per-byte scan path a first attempt (accumulating the code point via
shifts, `decode_codepoint_strict`-style) measured at +13% ns/byte and
rejected. The second site — every route other than a whole-pattern `.`
(combined with other pattern elements, lookaround content, and by
construction whatever the lazy-DFA/one-pass byte-programs and `real::dfa`
build from the same compiled program) — is fixed at its root: the compiled
program itself now uses the same canonical RE2-style range-splitting
already used for `\p{...}`, instead of a hand-written shape that never
narrowed the first continuation byte. Proven identical on every route: bare
fast-path, one-pass, the general Pike VM (forced via lookaround), the
lazy-DFA byte-program (differential against its own route toggle), and the
separate public `real::dfa` engine — the fix could not have made `.`
DFA-unrepresentable there, unlike the alternative design considered
(routing `.` through the `klass_cp` opcode `\w`/`\p{...}` use, which was
set aside specifically because it would have made `real::dfa` throw on any
pattern containing `.`, confirmed empirically before committing to the
bounds-table design instead).

Honest cost, not hidden: bare `.` over a corpus that is *entirely* dense
4-byte sequences (the structural worst case for the added bounds check) is
measurably slower on x86/gcc — +7.5% — while flat on arm64/clang (≤1.4%,
noise-level). The general path this same fix improves (`.` combined with
other pattern elements, e.g. `a.b`) is *faster* on the same x86 host,
−16%, a collateral win from the canonical-splitting rewrite. Net picture:
a real but bounded cost on a narrow, adversarial shape, in exchange for
closing a security-relevant correctness gap and a measurable general-path
win — logged as a small follow-up (packed bounds lookup / dedicated
4-lead branch) rather than held against this release.

## Fix (perf) — x86 stop-set regression from 7.32's O(n²) fix, recovered

7.32's fix for quadratic `(?i)<literal>` search (galloping cascade search)
cost the single-member cascade case (`run_cascade_stop`'s stop-set path) a
measured +15.7% on x86 — a single `memchr` call's cost already equals its
own progress, so windowing it can only add overhead, never protect against
quadratic behavior that structurally cannot occur with one cascade member.
Split: `n == 1` now bypasses the windowed loop entirely (one unbounded
`memchr`, the pre-fix code shape for that case); `n >= 2` keeps the
galloping window unchanged, since that is where the quadratic risk the
7.32 fix closes actually lives. x86 stop-set throughput recovered to its
pre-regression baseline (0.3966 → 0.3432 ns/byte, matching the ~0.3498
target); every other cascade case unaffected.

## Tests

A malformed-UTF-8 test matrix (12 invalid-byte-sequence shapes × the
Unicode-aware feature surface — `\w \d \s \b`, `\p{...}` in every syntax
form, case-insensitive matching, lookarounds, region search) proven
crash/OOB-free under ASan/UBSan, plus a dedicated route matrix for the four
`.`-specific cases above (fast-path, one-pass, general VM, lazy-DFA,
`real::dfa`) proving they reject identically everywhere. A `\p{...}`
differential fuzzer against UCD-source-derived oracles (never the
third-party `regex` module, whose bundled UCD version could disagree with
this engine's own pinned one) — General_Category, Script, Script_Extensions,
and binary properties — 17 seeds × 20,000 iterations, zero divergences.

## Tooling

A `-fconstexpr-steps` bump added mid-train (a newer libc++'s constexpr
`std::vector` internals tripped the default step budget compiling
`test_constexpr.cpp` once `.`'s compiled program grew) is reverted in favor
of the actual fix: splitting the oversized `static_assert` that bundled
many regex compiles into one constant-evaluated expression. Users writing
their own constexpr regex code keep the compiler's default limits — the
flag would have leaked the same fragility to them, and would have covered
only Clang (MSVC's independent, same-default `/constexpr:steps` limit was
never addressed by it). `CMAKE_EXPORT_COMPILE_COMMANDS` is also on now, so
tooling can be pointed at the exact flags CMake computed instead of a
hand-maintained list.

## Honesty

The `.` fix closes a real, security-relevant correctness gap — three
distinct malformed-UTF-8 shapes silently counted as a valid code point,
the kind of confusion a smuggling attack against a length-bounded validator
would exploit — at a measured, narrow, and disclosed cost (dense-multi-byte
`.` on x86/gcc) rather than a hidden one. The stop-set recovery restores
what 7.32 itself cost, verified against the same deterministic work-counter
that caught the original regression. Nothing in this release changes
matching semantics for well-formed input.
