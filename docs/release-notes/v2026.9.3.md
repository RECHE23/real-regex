# v2026.9.3 — two use-after-frees, and the code that stops compiling because of them

This train ships for one reason: **two of its fixes were undefined behaviour in published C++.** Not
a wrong answer that could be worked around, and not a diagnostic — a read of freed memory, on an
expression whose safe-looking sibling is one word away.

Everything else here follows from the same week's work: a literal that could not reach an overload,
three Python drop-in gaps, three documents the code contradicted, and six guards that now fail
instead of printing.

## The undefined behaviour, and why it waited for nobody

**`search_longest` on a temporary regex handed back a borrowing result.** Store it, ask for a group
BY NAME, and AddressSanitizer names a heap-use-after-free through `dynamic_program::~dynamic_program`;
without a sanitizer it is `string_view::substr` throwing `out_of_range`. The span was never the
problem — it points into the SUBJECT, which the caller keeps alive. What died with the temporary is
the pattern text and the named-group table.

`search`, `match` and `fullmatch` each already had a `const&&` twin that copies the name context
before the regex dies. `search_longest` was the one left out, so the very expression that is safe for
`search` was not safe for it:

```cpp
auto m = real::regex{R"((?<word>\w+))"}.search(text);          // safe, and always was
auto n = real::regex{R"((?<word>\w+))"}.search_longest(text);  // UAF on n["word"], until now
```

It now returns `owning_result_type` on an rvalue, through the same `detach` its siblings use.

**The leftmost-longest forms accepted a temporary SUBJECT.** The inverse defect, in the same
methods: `search_longest` returns a borrowing result and `find_iter_longest` returns a range over the
subject, yet neither carried the `const std::string&&` deletion its leftmost-first sibling has. So
`re.search_longest(std::string("xax"))` compiled and pointed into a buffer that died at the end of
the full expression. Those deletions now exist, and `find_iter_longest` on an **rvalue regex** is
deleted outright — an iterator has no owning twin, because a range-for outlives the regex that
produced it.

A named `std::string` was never affected: an lvalue cannot bind to `const std::string&&`, so only one
candidate was ever viable there.

## The C++ source break, from those same fixes

**Code that compiled — and was undefined — no longer compiles.** This is the ordinary shape of
fixing UB, and it is deliberate:

- `search_longest(std::string("x"))` and its region form are refused, at every arity. The subject
  must outlive the result.
- `real::regex{"a"}.find_iter_longest(text)` is refused at every arity. The range would outlive the
  regex.
- On an **rvalue** regex, `search_longest` now returns `owning_result_type` rather than
  `result_type`. Invisible under `auto`; visible to code that names the type.

`count_matches` is deliberately untouched: it returns a `std::size_t`, nothing borrows the subject,
and adding a deletion there would refuse safe code.

**One change goes the other way — additive.** A bare string literal could not reach the region forms
at all: `re.search("xax", 1)` was AMBIGUOUS, because `const char*` reaches `std::string_view` and
`std::string` by two user-defined conversions of equal rank, and the second candidate was the deleted
overload. The compiler therefore named a deletion whose comment reads "temporary text would dangle"
— about a literal, which has static storage duration and cannot. `search`, `match`, `fullmatch` and
`find_iter` all take a literal now, at both arities, and each diagnostic names the actual temporary:
`const std::string&&` where the subject is one, `const&&` where the regex is.

## Python: three drop-in gaps

**`real.compile("a", True)` is no longer an error.** Bit `0x1` is ignored rather than refused. `re`
compiles `True`, `1` and `3` on every interpreter this binding supports — the bit was `re.TEMPLATE`
before 3.12, itself a no-op for compilation, and is not a flag at all since. Accepting it is safe
because of what it is *not*: `re.compile("a", True).fullmatch("A")` is None, so the bit is not
ignore-case and no answer changes. `3` (`re.I | 1`) still folds case. Verified green on 3.11, where
the constant still exists, and on 3.14, where it does not; the test asks `re` rather than
transcribing it, because what `re` does with this bit has already changed once. No `real.TEMPLATE` is
exported and no message names it.

**An unknown flag bit is now named.** `unknown flag 0x400 passed to real.compile`, and pluralised for
several. `0x400` is still refused: this accepted one bit, not the principle.

**`(?ié` says what `re` says.** It reported `missing -, : or )` — the terminator's message for a fault
the terminator did not cause — where `re` reports `unknown flag` at the same position. The split
CPython makes once a flags group has started is `str.isalpha()`, and this parser asked
`is_ascii_letter` on one peeked byte. The boundary is not "non-ASCII", which would have traded one
false message for another: `é` is alphabetic and `😀` is not, so `(?i😀)` is a terminator fault on
both sides and stays one. Under `flags::bytes` the unit is the byte read as latin-1.

## Documents the code contradicted

**Nesting depth was in no catalogue.** REAL caps parser nesting at 200 groups and raises
`real.error` with `pos=200`; `re` has no cap and raises `RecursionError`, which is not a `re.error`
and which `except re.error` does not catch. No depth is quoted for `re` because it does not have one
— its boundary follows `sys.getrecursionlimit()`, measured at 400 nested groups failing at 500 under
the default 1000, and 900 compiling at 3000.

**A high-endpoint class range is refused by libstdc++, not by "std".** `[A-\x80]` is rejected there
(signed `char` endpoints, so the range reads inverted) and **accepted by libc++**. A sweep of this
had once been read as "std::regex refuses", which is false on one implementation of a
two-implementation split; the count was kept out of the catalogue for that reason and is now written
under the right name.

**`3.2 M` became `3 218 434`.** The rounding sat in the one sentence whose job is to say how much was
compared, where a loss of tens of thousands of agreeing cases would not have changed a character.

## Guards that now fail instead of printing

Six, briefly. The exhaustive compat check pins the SIZE of its space and its tolerated-divergence
count instead of printing them; an empty corpus is a failure rather than a declared success; the
tolerated count in four live pages is tied to the constant that measures it; the publishing workflows
pin Doxygen 1.9.8 with a witness, and so does the local tool that claims to reproduce them; the
sabotage harness rebuilds the artifact belonging to the file it broke rather than one fixed target;
and a guard's self-test now executes the branch that prints, not only the branch that refuses.

## Benchmarks: the tables do not move, and the stamp stays at `2026.8.15`

Third train in a row, same reason and no new argument: `docs/BENCHMARKS.md` declares a **two-ISA**
regime and only arm64 was available. Publishing one leg would produce a table whose halves describe
different trees.

The reach of this train is asserted, not a paired measurement. What it touches is lifetimes,
diagnostics, Python flag handling, documentation and gates. The one runtime cost it adds — `detach`
copying a name context on an rvalue-regex call — sits on a path no cell exercises: no benchmark uses
a temporary regex, and neither `search_longest` nor `find_iter_longest` appears in the benchmarks at
all. `CHANGELOG.md` carries the per-train entry.

## Upgrading

**C++ callers:** if your code did any of the three things listed under the source break, it will stop
compiling, and it was undefined behaviour before. The remedy is the same in each case — give the
subject or the regex a name — and a named `std::string` was always fine. Code using `auto` for
results is unaffected by the type change.

**Python callers:** `real.compile("a", True)` now works. Error text moved on `(?ié` and on unknown
flag bits; code matching on the text of an error was never promised that it would stay still.

**Go:** module `v0.3.2`, a patch. The Go surface did not change — the deletions and the owning result
type are C++.
