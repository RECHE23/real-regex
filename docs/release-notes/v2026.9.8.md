# v2026.9.8 — the DFA carries assertions

This train keeps the lazy DFA on patterns it used to hand to the Pike VM. **Anchors and word
boundaries ride in the DFAs**: `^`, `$`, `\A`, `\z`, `\Z`, `\b` and `\B` are decided on the bytes
around them, and a Unicode `\b` next to a non-ASCII byte hands that one search to the VM. **A regex
shared by threads scales with them**: each thread leases its own DFAs. **A lookahead may be
unbounded**, and a lookbehind costs one forward walk per search. **`can_extend`** tells a lexer fed
text in pieces whether more text could change a match, in C++, the C ABI, Rust and Go. And **the
engine can be compiled once**, as the `real::capi` library with a C++ façade over it. Every change is
compatible: no stable name is removed or changed, and the C ABI gains functions without moving
`REAL_ABI_VERSION`.

`docs/BENCHMARKS.md` is re-stamped at `2026.9.7` + tree `18809f4` on both ISAs, the first two-ISA
stamp since `2026.8.15`; `CHANGELOG.md` records what moved.

## Performance

- **A regex shared by threads scales with them.** The lazy DFAs of a regex lived in one process-wide
  slot scanned under its mutex, so threads sharing a regex queued on it: `[a-z]+ing|[0-9]+x` over
  3.5 MB read 93.7 MB/s on one thread and 46–58 MB/s aggregate on 2–8 (x86-64, g++ 13.3, 6 cores).
  Each thread now leases its own set of DFAs from the regex's pool: 98 / 194 / 383 / 452 MB/s on
  1 / 2 / 4 / 8 threads.
- **A lookbehind costs O(n·k·m), not O(n·k·L²).** It tried every start within L bytes behind a
  position and replayed the window from each. It now runs as one forward walk per search that carries
  every start together: `(?<=a{1,200}b)a` over 10 KB of `a` took 4.7 s and takes 32 ms.
- **A short search no longer pays for the Pike VM's machinery.** On a subject small enough that a bit
  per (instruction, position) fits 8 Kibit, the general loop now answers by bounded backtracking in the
  VM's priority order, with the same answers (differential against the VM on every mode, `find_iter`
  included): `(\w+)@(\w+)` over 9 bytes, 1124 → 216 ns per search (x86-64, g++ 13.3), 11 416 → 2 365
  instructions (arm64, Apple clang); over 63 bytes, 6698 → 696 ns.
- **Anchors and ASCII word boundaries no longer take the Pike VM.** A pattern with `^`, `$`, `\A`, `\z`,
  `\Z`, `\b` or `\B` used to leave the lazy DFA; the forward and reverse DFAs now carry those assertions
  and decide each one on the bytes around it. On 2 MB of English-like text (arm64, instructions
  retired, `count_matches`): `(?m)[a-z]+ing$` 935 M → 80 M, `[a-z ]*x$` 1 121 M → 79 M. Word boundaries
  in the default text mode are Unicode ones: the DFAs decide them between two ASCII bytes, where they
  are ASCII ones, and hand the search to the VM where one sits next to a non-ASCII byte. On 1 MB of
  ASCII prose `\b\w+ing\b` counts in 2.8 ms instead of 10.2, on prose with curly quotes in 6.9 ms
  instead of 9.8, and on French nothing measured is slower. Dense matches of such patterns got cheaper
  again once the scans read their memoized resolutions inline: `(?m)^.*$` from 170 to 95 instructions
  per byte.
- **A line start no match can begin at is no candidate.** Once the DFA took line-anchored patterns, a
  `(?m)^` search tried every line start; it now skips a line whose first byte cannot start a match.
  `(?m)^\w+` is 2.1 times faster than before this train.
- **A search no longer rereads a long run once per candidate.** With a known set of first bytes, the
  lazy DFA walks from each candidate; inside a run of candidate bytes that no match ends, every walk
  reread the run. The walks now give way to one forward pass and one reverse once the walks that find
  nothing cost clearly more than that pass, a rule fitted and then checked on 32 pattern and subject
  pairs (within 15 % of the better route on all of them). On 2 MB (arm64, instructions retired):
  `[a-z ]*x\d\d\d\d` 1 066 M → 92 M in `count_matches`, `\w+\d+` 294 M → 134 M.
- **An inner-literal match with no group to fill runs no engine.** Once the forward DFA confirmed a
  candidate, the groups were filled by the one-pass table or the Pike VM even when there was no group
  but the match. A pattern whose classes hold its own literal is not one-pass, so `[^ ]+=[^ ]+` over log
  lines ran the VM on every candidate, at 87 times the cost of `\S+=\S+`; it now runs at 3.4 times.
- **A DFA whose cache thrashes gives the search to the VM.** The fallback was specified and never wired:
  a pattern whose DFA needs a state per window of the subject built one on nearly every byte.
  `(a|b)*a(a|b){12}c` over random `a`/`b` ran at four times the VM's cost; it now runs at 0.9 times.
- **A pattern that can match empty no longer runs half its matches on the VM.** After an empty match,
  the rule that the next may not be empty at the same spot sent the whole next search to the Pike VM,
  which then found the following match itself: `.*` counted lines 700 times slower than `.+`. The VM now
  decides that one position and the DFAs take the rest: `.*` over 400 KB of lines, 48 ms → 3.7 ms.
- **Groups of a run of classes no longer need the VM.** With a Unicode `\w`, which is never one-pass,
  every match with groups ran the Pike VM over its window. A pattern made of classes, literals and
  greedy `+` loops now has its groups read by one walk: `(\w+)\s+(\w+)` runs 27 % fewer instructions.
- **A faster single-byte scan on arm64.** The scan behind every single-byte literal (the `-` of a date,
  the `@` of an address) was the platform `memchr`; a NEON loop of 64 bytes per round covers 64 KB with
  no hit in half the time. `\d{4}-\d{2}-\d{2}` over 64 KB with no date, the benchmark row where REAL
  trailed the regex crate most, drops from 1458 ns to 1000 ns. x86-64 keeps the platform `memchr`.
- **The single-pass DFA route reads its cached transitions inline.** The forward and reverse passes
  called a function per byte where the anchored walk already read the cache directly: patterns on the
  one-pass route run 17 % to 60 % fewer instructions (`[a-z ]*x\d\d\d\d` 46 → 18 per byte on arm64,
  −35 % on x86-64), `\w+\s+\w+` 25 % faster by the clock.
- **Counting a pattern with groups no longer extracts them.** `count_matches` reads no group, yet a
  pattern with any took the full route per match: `(a|e|i|o|u)+` now counts 2.4× faster, `(\w)+` 2.9×,
  `(\w+)\s+(\w+)` 2×.
- **`\b\w` and its kin are batched.** A code-point class with a kept `\b` or `\B` (`\b\w`, `\w\b`, `\B\w`,
  `\b\p{L}`) returned one match per route entry; it now fills a batch, checking the boundary per run:
  `\b\w` 1.8× faster.
- **The munch memo** (`dfa_munch_memo`) replays the walk after its last accept instead of holding it
  (472 MB → 21 MB on 16 MiB of adversarial input) and costs nothing until a long dead stretch arms it.

### Measured and not fixed

- `alternation the|fox|dog` on x86-64 went from 1.67 to 1.89 ns/B with fewer instructions and 14 % more
  branch mispredictions (cachegrind).
- `(?i)café` on x86-64 executes 7.6 % more instructions than at the last two-ISA stamp; the first
  crossing predates this train, and the count moves non-monotonically from commit to commit, the mark
  of GCC's inlining budget for `count_matches`.

## Added

- **`can_extend(text, pos)`**: whether `match(text, pos)` could come out differently if the text
  continued — the question a lexer fed text in pieces must answer before committing to a token.
  Conservative: a true may only delay the caller. On `basic_regex` and `real::compiled::regex`, in the
  C ABI as `real_can_extend` (additive; `REAL_ABI_VERSION` stays 1), in Rust as `Regex::can_extend`
  (`&str` and `bytes`) and in Go as `(*Regexp).CanExtend`. SciLex's streaming lexer is built on it.
- **The engine compiled once: `real::capi` and `real_compiled.hpp`.** Configure with
  `-DREAL_BUILD_CAPI=ON` to build the C ABI as a library (static or shared) and link `real::capi`; the
  header `real_compiled.hpp` gives C++ a `real::compiled::regex` over it — search/match/fullmatch over a
  region, find_all, count, sub, group names, results that own their spans. A translation unit that
  includes it compiles in 0.73 s against 6.1 s for `<real/real.hpp>` (arm64, clang 22, -O2).
- **Unbounded lookaheads.** `(?=.*\d)`, `(?!.*x)` and every other lookahead without a bound were refused
  ("unbounded lookaround is not supported"); they are now accepted and evaluated in linear time — one
  backward pass per subject answers every position. The password-rule idiom
  `^(?=.*\d)(?=.*[a-z])(?=.*[A-Z]).{8,}$` compiles and runs. An unbounded lookbehind is still refused.
- `real_abi_version()` and `real_version()` in the C ABI, and `REAL_ABI_VERSION`, which moves only on
  an incompatible change; `make check-abi-bump` refuses a change to the released interface that does
  not move it.
- A written versioning and stability policy (Developer → Versioning): the year is the major; what each
  surface promises; deprecation for at least three months; breaks developed on `next` and released as
  the next year's first version.

## Fixed

- **A search region that starts inside a UTF-8 code point keeps a leading `\b`.** Before a maximal `\w`
  run the engine drops a leading `\b` it can prove redundant, and guarded only the case where the first
  candidate is the region's start. When the region begins inside a code point the scan crosses only its
  tail, and the word character before the candidate went unseen: `\b\w+` from byte 7 of
  `"xe z\nyéx_é abc"` answered `x_é` where the first boundary is at `abc`. Only byte-offset callers (C,
  Go, Rust) can start a region there.
- **A leading `\B` (or a leading `\b` before anything but a run of word characters) no longer loses the
  match on long texts.** The inner-literal route checked the boundary at the leftmost start only, where
  a later start could satisfy it: `re.compile(r"\B\w+e").search(" " * 100000 + "99\n99e")` answered
  `None` where Python's `re` gives (100004, 100006) — in every mode, since the route shipped. The route
  now keeps the boundary only where the leftmost start is the only one that can be a boundary
  (`\b\w+@\w+\b`), and declines everywhere else.
- **Two threads searching at once no longer race.** Two process-wide test-observability values (the
  inner-literal and Aho-Corasick density gates' last decision) were plain variables written by every
  search that reached a gate — a data race, undefined behaviour, reported by ThreadSanitizer. They are
  relaxed atomics now; the store costs what it did.
