# v2026.10.11 — Prefilters that keep their filter, and limits a build can lower

Three search shapes lost their prefilter and paid for every position: a fixed-width pattern whose rare byte sits
past offset 255, a wide fixed-width pattern with no rare byte at all, and a case-insensitive literal. Each now
keeps a filter or moves to the lazy DFA — from 10 s to under a millisecond per MiB on the worst of them. A crash in
the C ABI is fixed, `left_context` reaches every binding, and a build that accepts untrusted patterns can lower
the resource limits as SECURITY.md advises.

## Performance

- **A fixed-width pattern longer than 256 bytes keeps its rare-byte prefilter.** The offset of a required rare
  byte (`x` in `[a-z]{300}x`) was stored in 8 bits, so past offset 255 the search fell back to a verify at
  every position the first class allows: 1 MiB with no match took 261 ms for `[a-z]{300}x` and 834 ms for
  `[a-z]{1000}x`; both now take 0.01 ms (arm64, Apple clang 16, `-O2`). The offset now has 16 bits, in padding
  the hints already had (their size is unchanged).

- **A fixed-width pattern wider than 8 bytes with nothing to skip candidate starts by runs the lazy DFA.**
  The fixed-shape walk verified every start up to the pattern's width, so a subject whose starts match far
  into it cost width × length: over 1 MiB of letters, `[a-z]{300}[0-9]` took 270 ms and `[a-z]{1000}[0-9]`
  870 ms; both now take 2. Prose and identifiers gain 2× to 5× from width 12 (`[a-z0-9_]{12}`,
  `\b[a-z0-9_]{12}\b`, `([a-z]{20})([0-9]{20})`), on arm64 (Apple clang 16) and x86-64 (GCC 15). A shape
  the fused scan, the pair filter, a rare byte, a single first byte or a start anchor filters keeps the walk,
  as does `static_regex`, which has no lazy DFA. Where nearly every start matches, the DFA costs up to
  0.6 ms/MiB more on arm64 (neutral on x86-64).

- **A case-insensitive literal keeps a prefilter.** Under `(?i)` a letter is matched in either case, and the
  required-literal scan used to stop at every letter: `(?i)Sherlock Holmes` scanned for its space alone
  (3.3 ms/MiB against 0.17 now), and `(?i)[a-z]{1000}x`, too wide for the lazy DFA, fell to the general engine
  at 10.6 s/MiB (now 0.1 ms/MiB; arm64, Apple clang 16, `-O2`). A letter whose case-fold orbit is exactly its two
  ASCII cases -- every letter but `k` and `s`, whose orbits hold the KELVIN SIGN and LONG S, in text mode --
  now joins the literal, and the scan finds both cases at once. `(?i)\w+ing` 11x, `(?i)error:\s\w+` 1.6x;
  no benchmarked pattern changes route.

## Fixed

- **`real_iter_next(iter, NULL)` no longer writes through a null pointer.** A NULL `spans` buffer now advances
  past the match without the spans, as `real_search` already allowed; a C caller that only counts matches
  crashed.

## Added

- **`left_context()` in the C ABI, Go and Rust** (`real_left_context`, `(*Regexp).LeftContext`,
  `Regex::left_context` and `bytes::Regex::left_context`, and `real::compiled::regex::left_context`): how many
  bytes before a position a match there may read, which a lexer keeps of text it has passed. C++ had it alone,
  while every binding already answered `can_extend`. A Rust pattern on the `regex` fallback says `usize::MAX`.

- **The resource limits can be lowered per build**: `REAL_MAX_PROGRAM_SIZE`, `REAL_MAX_REPEAT_COUNT`,
  `REAL_MAX_GROUP_COUNT`, `REAL_MAX_NESTING_DEPTH`, `REAL_MAX_LOOKAROUND_LENGTH` and `REAL_MAX_DFA_STATES`
  (`-DREAL_MAX_REPEAT_COUNT=100`), as SECURITY.md advises a service that accepts untrusted patterns. Raising
  one is refused at compile time: each default is also a storage bound. They were constants to edit in the
  header.

## Documentation

- `.` and an ASCII-only negated class never match a malformed UTF-8 sequence (the page said they did); PCRE2
  10.47 accepts a bounded variable-width lookbehind; the engine's backtracking is a bounded backtracker.
