# v2026.7.55 — performance: the literal route, capture extraction, and a cache-contention fix

A **performance** release. No behaviour changes, no API changes: every commit here
is a throughput change verified byte-identical (or instruction-identical) to the
code it replaces. Five changes, each measured on **both ISAs** — arm64 (Apple M1
Pro, clang) and x86-64 (devbox, g++ 13.3, natively) — because one of them turned
out to gain on one ISA and lose on the other, and only a two-ISA pass caught it.

The headline is the **fixed-literal search**: `find/literal` through the Rust
crate went **33.5 → 17.3 µs** on a 64 KiB corpus (−48 %), which takes the gap
versus the `regex` crate from 3.18× to 1.64×. Capture extraction moved further
still: **`captures/class` −53 %, `captures/email` −75 %**, and two rows
(`captures/digits`, `captures/fields`) now lead `regex` outright.

## The one-search exact-literal route

`run_exact_literal` redid three **per-match-invariant** steps on every match:
`next_candidate` re-walked its hint chain to re-derive the same `find_prefix`
call, `literal_at` re-`memcmp`'d the bytes `find_prefix` had just matched, and
`replay_literal` walked the whole compiled program to rediscover capture slots
that only shift by the match offset.

Eligibility is now folded into one compile-time bit
(`pattern_hints::literal_one_search`: a ≥ 2-byte literal, no `assert_position`,
no anchor, no rare-discriminant), and a single `find_prefix` answers the whole
search. One bit rather than a condition chain is deliberate — every term is a
property of the compiled program, never of the subject, so evaluating them per
match cost the shapes that *fail* the guard 1–1.6 % for a decision that cannot
change.

Assertion-freeness is read from the program's own opcodes, never inferred from
the `wb_lead` / `anchored_start` / `line_anchored` hints: an assert kind those
hints do not represent would make that inference silently unsound, and `\bdog`
would lose the retry the general loop exists for.

Measured: **arm64 −31.6 %**, **x86-64 −29.2 %** on a dense literal scan;
`localhost` −27.8 % / −41.4 %. Callgrind on x86 (deterministic): **9.57 M →
7.25 M instructions, −24.3 %**.

## A two-byte SIMD block filter — NEON only, and that is the point

`find_prefix` and `find_literal` both filtered on **one** byte, so on text where
the needle's lead byte is common (`d` for `dog`) every position survived to a
full verify. The new filter compares 16 candidate positions against **two**
needle offsets at once — the first byte and the last — and only the survivors are
verified. Four blocks per round (64 candidates, independent loads, one branch),
because a no-match scan spends all its time in the reject test and libc `memchr`
sets the bar there by covering 64 B per round.

**This one is NEON-only, and the reason is the release's methodological lesson.**
The filter is worth taking only where it beats the platform's own substring
search, and whether it does is genuinely per-ISA:

| | arm64 | x86-64 |
| --- | ---: | ---: |
| dense literal | **−31.6 %** | +13 % |
| no-match scan | **−60 %** | +19–24 % |

glibc's `find`/`memchr` on x86-64 are **AVX2** — 256-bit, twice this loop's
width — so a 128-bit SSE2 block filter loses to them on every row. The first cut
of this change shipped the SSE2 leg routed and was therefore a clean per-ISA
regression; it had been measured on arm64 only, the same failure mode that got
an earlier `memcpy`-based span fill reverted. Gating to NEON restores x86 to its
pre-filter numbers **exactly** on all six literal rows, and leaves arm64
bit-identical. The SSE2 leg of `load_pair_mask` is removed rather than left
unrouted: an unused primitive measured slower than what it would replace only
invites someone to route it. An AVX2 leg, with its own wider mask type, is the
honest way to bring this win to x86 — a separate arc.

Linearity is unchanged: the block loop advances 16 (or 64) per round and verifies
at most that many candidates of `|literal|` bytes, so the bound stays
`O(n · |literal|)` with `|literal|` capped at 16 by the hint arrays — the same
bound the `memchr`-lead scan carried.

## Capture extraction: no allocation per match

`Captures` in the Rust crate held a `Vec<Option<(usize, usize)>>`, so
`captures_iter` did one `malloc` + `free` **per match** — on a *groupless*
pattern, ~19–27 ns/match of allocator traffic to carry a single span. That was
the whole of the crate's `captures_iter`-versus-`find_iter` gap (the `regex`
crate's `captures_iter` costs exactly its `find_iter`; ours cost 1.6–2.6× more),
and it was previously described in `BENCHMARKS.md` as *"inherent to returning
owned group spans"*. It was not.

Slots are now stored flat and inline — `[start0, end0, …]` with `usize::MAX` for
a group that did not participate, the same representation the C ABI fills — with
8 slots (4 groups) inline and a spill to a boxed slice beyond, so many-group
patterns stay correct rather than capped.

| criterion row (arm64) | before | after | vs `regex` |
| --- | ---: | ---: | :--- |
| `captures/class` | 438.9 µs | **207** | 2.33× → **1.10×** |
| `captures/email` | 569.7 | **145** | |
| `captures/literal` | 52.1 | **20.7** | 4.95× → **1.97×** |
| `captures/digits` | 112.1 | **61** | **REAL 1.25× ahead** |
| `captures/fields` | 66.4 | **43** | **REAL 3.5× ahead** |
| `captures/alternation` | 186.5 | **112** | |
| `captures/word_bound` | 650.9 | **500** | |

Alongside it, the C ABI stopped filling its span buffer through the per-group
`start(g)` / `end(g)` accessors — each re-tests `matched()` and the group bound,
dead work for a caller that has already checked the return code — and reads the
flat slots pairwise instead. Pairwise specifically, *not* one `memcpy`: a runtime
length compiles to a real libc call, dearer than the stores at the 1–2 slot
shapes that dominate. That is how the earlier `memcpy` attempt regressed, and why
this one was A/B'd against three variants before landing. arm64 `\b\w+\b`
25.1 → 19.9 ns/match (−20.7 %); x86 callgrind −1.3 to −1.8 % instructions on
every pattern tried. Rust and Go both drive this path, so both gain.

## Shared-DFA cache: per-slot ownership

The thread-local last-hit cache in `shared_dfa_for` was validated against a
single **process-wide** epoch counter bumped on every regex destruction. So any
regex dying anywhere invalidated every thread's cache and sent them all back to
the global map mutex — the mutex the cache exists to avoid, once per
inner-literal candidate. Ownership now lives in the slot: a cached slot is this
regex's slot exactly while `owner == immut`, and retiring nulls it, so one regex
dying costs only the threads that were using it.

The larger win was the **quiet** path, not the contended one: the old fast path
loaded a process-wide atomic per candidate — a shared cache line, so not
registerizable across iterations even single-threaded. arm64 quiet scan
**−9.0 %**; under a concurrent thread churning ~85 k create/destroy cycles the
penalty halves, **1.09× → 1.04×** (x86: 1.19× → 1.07×). ThreadSanitizer clean on
both the core and the compat suites.

## Verification

Both ISAs, and the two-ISA pass is what makes this release trustworthy rather
than merely green:

- **arm64**: `full-local-gate` all 22 steps green, line coverage 95.82 %.
- **x86-64, natively** (devbox, g++ 13.3): the full suite, **317 745 checks**
  pass — including the exhaustive literal-search equivalence on the *scalar*
  path, where the SIMD filter is compiled out. Valgrind memcheck on that path:
  **0 errors, 0 bytes definitely lost**.
- **Callgrind** settled the small deltas that wall-clock could not. Two
  "regressions" reported during review — a span-fill row and an 11–21 % swing on
  the class-scan route — turned out to be artifacts of a multi-pattern
  measurement harness: the class route is **instruction-identical**
  (43 264 346 → 43 264 506 Ir, +0.0004 %) and, measured in isolation, 3.9 %
  *faster*. `-falign-loops` did not explain the swing either; only instruction
  counting did. For deltas under a few percent on codegen-sensitive routes,
  wall-clock across separately-linked binaries is not evidence.
- **Correctness nets**: `exhaustive-compat` 3.22 M cases, serious = 0;
  `fowler-compat` PASS; 102 k literal and 13 k lookaround cases differentially
  checked against node, 70 k against PCRE2; the new literal search checked
  exhaustively against `std::string_view::find` as an independent oracle over
  needle lengths 2–20 and haystacks 0–200 crossing every block seam (the suite
  grew 120 891 → 317 799 checks).
