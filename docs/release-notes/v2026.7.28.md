Trailing-lookahead class+ gets a real matching-only speedup (~10–11× vs the general VM), a new public
`count_matches` API exposes that path without allocating Match objects, multi-engine benches count
fairly again, and CI fails fast on cheap checks first. Pure `[a-z]+` is untouched (x86 regression ~0 on
gcc and clang). Nobody is slower.

## API: `count_matches`

New public method on `real::regex` (and the storage-parameterized twin): count non-overlapping matches
**without materialising result objects**. Once-per-walk dispatch (same cascade_ model as other monomorphic
routes): ordinary patterns use the pure walk; trailing-LA class+ shapes take the TrailingLA instantiation.

This is the right surface for "how many matches?" and for multi-engine throughput benches. Prefer it over
counting `find_iter` when measuring trailing-LA speed, and over `find_all().size()` (vector cost can dominate
at high match counts and is not comparable to engines that only count).

**Surfaces at 7.28 ship:** C++ and the Rust crate. The Python wheel shipped with 7.28 did **not** yet
expose `count_matches` (use `findall`/`finditer` there, or upgrade to the follow-up train that binds
`Pattern.count_matches` / `real.count_matches` to this path).

## Performance: trailing-LA class+ (P3c)

Patterns of the form *groupless class+ with trailing ahead lookaround* — e.g. `[a-z]+(?=[a-z])` — keep the
class-loop body and treat the lookaround as an end-of-body scan on a cold path. Dispatch is **once per walk**,
not per step: a monomorphic `TrailingLA=true` walk for eligible patterns; pure walks stay `TrailingLA=false`
with zero LA symbols in `advance()`.

**Matching-only** (x86, independent re-measure on the final tree, both compilers):

| | GCC | CLANG |
| --- | ---: | ---: |
| plain `[a-z]+` | 3.06 ns/B (= pre-P3c) | 2.57 (≤ pre 2.87) |
| LA `count_matches` | 9.26 | 6.93 |
| LA `find_iter` (general VM) | 92.65 | 77.15 |
| ratio LA VM → matching-only | **10.0×** | **11.1×** |

Correctness: `count_matches` and `find_iter` agree on match count (38597 on the probe corpus); small-span
check `[0,2)[4,6)` on `abc def` holds. The fast path returns the same result as the authoritative VM, just
faster.

### Honesty — API asymmetry (not a correctness split)

Bounded lookaround is always **correct and linear** on every public match API. The ~10–11× win is **not**
on every surface:

| Surface | Trailing-LA fast path? |
| --- | --- |
| `count_matches` | **yes** (matching-only) |
| `find_all` / `search` / `match` / `replace` (Python `sub`) | **yes** (`find_all` still pays Match-vector cost) |
| `find_iter` / Python `finditer` | **no** — general VM |

`find_iter`'s return type is fixed pure-monomorphic (`TrailingLA=false`) so pure `[a-z]+` codegen stays
pristine — a deliberate structural choice after a per-step branch on `trailing_lookaround` regressed that
path ~16% on x86. Correctness is identical; only throughput differs. Documented in
`docs/COMPATIBILITY.md`, `docs/BENCHMARKS.md`, and the `find_iter` / `count_matches` / `find_all` doxygen.

`bench_engines` counts via `count_matches` (matching-only, equitable with std / PCRE2 / RE2 counters).
Do not publish `find_all().size()` ns/B as scan throughput.

`docs/BENCHMARKS.md` §A table remains a **pre-P3c stamp** (general-VM order on the lookahead row); the
reading notes the post-P3c picture. Re-stamp §A at the next full `make bench-engines` refresh on both ISAs
— not re-measured for this fiche beyond the matching-only probes above.

## CI: fail-fast gates

Preflight runs cheap checks first (doc early), cancels in-progress work on a new push, and uses `pipefail`
so pipeline failures surface. Independent of the engine work; improves feedback for every following train.

## Process note

The pure class-loop regression was caught on x86 before train; the mechanism was proven by experiment
(forcing the hot per-step branch false recovered ~0 → once-per-walk monomorphic dispatch, cascade_ model).
Five implementation passes later, the history is three clean commits (CI · P3c · count_matches+equity) under
this tag.
