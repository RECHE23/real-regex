# v2026.9.10 — literals and alternations catch up with the regex crate

A train on the literal prefilter, driven by the comparison in issue #3. **A literal is now found by its
rarest byte and a two-byte block filter**, **an alternation of literals by a per-branch filter** (byte
pairs, then a nibble fingerprint where the CPU has a byte shuffle), and on x86 **both run on 32-byte AVX2
blocks where the CPU has them**, chosen at run time, so the wheels, the crate and the Go module built for the
x86-64 floor get them too. **`count_matches` no longer fills capture groups** it never reads. On the issue's
log-line corpus, measured with the crate on x86-64: the ten-word alternation went from 25× behind the regex
crate to 1.35×, the literal from 6× to 1.6×, the status line from 7.5× behind to 1.2× ahead. No answer
changes; every change is compatible.

## Performance

Figures are `count_matches` over 500 KB of log lines, each pair measured on one host before and after.

- **A literal is found by its rarest byte, and by a two-byte filter once that byte is common.** The
  literal and inner-literal routes scanned for the needle's first byte; they now scan for the byte the
  subject shows rarest, and once its stops come dense they hand the rest of the subject to a block filter
  that checks the needle's first and last bytes at 16 starts at once. x86-64 (g++ 13.3): `hello` 0.125 →
  0.057 ms, `error` 0.28 → 0.080, `the` 0.276 → 0.074. On arm64 the literal rows stay within 3 %; a csv
  `charlie` pays about 5 % for the density bookkeeping.
- **An alternation of literals is masked by a per-branch filter once its first bytes prove falsely dense.**
  The first-byte scan stops on every `c`, `d`, `f`… of prose. A 512-byte sample decides per subject; a dense
  one is masked by every branch's (first, farther) byte pair or, where the CPU has a byte shuffle (AArch64;
  x86 with SSSE3 in the build or found at run time), by a fingerprint of each branch's first three bytes
  whose cost does not grow with the number of branches. Candidates are still verified in branch order, so
  priority is unchanged. The issue's ten-word alternation: arm64 1.10 → 0.10 ms; x86-64 2.06 → 0.69 with the
  pairs (g++ 13.3), and a further −47 % in cycles with the fingerprint (g++ 15.2).
- **On x86 with AVX2, both filters take 32 starts a block**, chosen at run time: `hello` 0.054 → 0.035 ms on a
  Skylake-family core and 0.038 → 0.022 on Zen 2; the ten-word alternation 0.171 → 0.112 and 0.161 → 0.090.
- **Twelve branches or more no longer lose a dense subject to the Aho-Corasick automaton** when the
  alternation's block filter takes it: 1.62 → 0.36 ms on x86-64, 1.44 → 0.10 on arm64.
- **`count_matches` takes the span the DFAs found and fills no group.** The inner-literal confirm and the lazy
  DFA's walk from a candidate ran the one-pass table or the VM over each match to fill groups a count never
  reads. The issue's `(info|error|warn)\s+\d{4}-\d{2}-\d{2}\s+req=[a-f0-9]+`: 0.54 → 0.085 ms on x86-64
  (g++ 15.2), 0.338 → 0.092 on arm64, now ahead of the regex crate on both.

## Tests and gates

- Every filter is compared against the others in one binary through seams (pairs, fingerprint on 16 and 32
  starts, first bytes; the literal filter on 16 and 32), over random alternations and needles, long
  subjects, block edges and tails; counters witness which filter ran, and where the choice is made at run
  time it is held to the runtime's own CPU model.
- `gcc-check` also compiles the engine with the vector ISA macros undefined, and a new gate step runs the
  MISRA analysis for x86-64 in a container, where the ISA-chosen bodies compile.
