# v2026.8.9 — a limitation lifted, a route found, and three figures withdrawn

Two changes a user notices, one Windows fix, and a documentation train that takes back more than it
adds. No urgency in this one: nothing here is undefined behaviour, unlike its two predecessors.

## Possessive quantifiers now work on non-ASCII characters

`é++` threw `possessive/atomic over a compound body is not supported yet`. `[é]++` did not. Neither
did `(?i)é++`.

| rejected | accepted |
| --- | --- |
| `é++`, `あ++`, `𝔘++`, `é*+`, `é?+`, `é{2,}+` | `[é]++`, `[à-ÿ]++`, `[éàèùç]++`, `(?>é)b`, `(?i)é++` |

Same character, same language, three different answers — and possessive quantifiers are one of the two
constructs this project markets as differentiators, so they were unusable on any accented, CJK or
astral character written literally. A French or Japanese pattern hit it immediately.

Nothing fundamental stood in the way; an **AST shape** did. Tier-1 eligibility is tested on the node
*kind*, and a non-ASCII literal in text mode is a `concat` of UTF-8 bytes, so it could never qualify.
It is now promoted to the one-member code-point class it is equivalent to — the route `[é]++` already
took, reached by the precedent the case-insensitive promotion set a few lines above it, which is
exactly why `(?i)é++` already worked.

**Verified against CPython 3.14.6**, which has had possessive quantifiers since 3.11: all eight
discriminating cases agree, including the defining property — `é++é` never matches (the possessive
keeps what it took) where `é+é` does (greedy gives back) — at 2, 3 and 4-byte encodings, across all
four suffixes.

Scoped to **one** code point: `(?:éé)++` and `(?:ab)++` are still a clean rejection, the
VM-architecture wall this does not widen.

## `é+` was 3.2× slower than it needed to be, and the route counter said so

Found by **counting, not timing**. On a 180 KB corpus:

| pattern | route |
| --- | --- |
| `é`, `[é]` | `exact_literal` |
| `é+`, `[é]+`, `[éàèùç]+` | **`lazy_dfa_anchored` ×18 896 — one per match** |
| `[à-ÿ]+`, `[a-z]+` | none: the batch counting path |

`[éa]+` is the witness that settled it: adding one ASCII member makes the pattern **fast**, because it
breaks the members' common length and the byte-wise fixed-width emission declines.

So v2026.8.6's fixed-width class emission is right for a *bare* class — it routes as an exact literal —
and wrong under an unbounded quantifier, where it turns the class into a repeat of a two-**byte**
sequence that no route recognises. The literal has the same problem from the other side. Both now
become a one-member code-point class there:

| | before | after | |
| --- | ---: | ---: | ---: |
| `é+` | 5.62 ns/B | **1.765** | 3.19× |
| `[é]+` | 5.62 | **1.764** | 3.18× |
| `[éàèùç]+` | 8.44 | **1.915** | 4.41× |

`é+` reaches parity with `[a-z]+` (1.760). Identical to three decimals on **two independent builds**,
with the route counter confirming the mechanism independently of any clock.

The semantic tests for this pass *before and after*, and say so: it is a routing change, so what is
pinned is the compiled shape. A test counts opcodes and fails on 8 checks without the fix, naming what
is missing where an aggregate hash could only say that something moved.

## Reading this repository's own UTF-8 as UTF-8

The Windows Python jobs failed with `UnicodeDecodeError: 'charmap' codec can't decode byte 0x81` after
`あ` entered a comment. A test read the header with no encoding, so Windows decoded it with the locale
codec, where 0x81 is undefined.

**The defect was older than the character.** `é` is `C3 A9`, and 0xA9 *is* defined in cp1252 (`©`), so
these files had been decoding **wrongly all along**, silently. The new character introduced nothing; it
made a mute bug loud. Seven read and write sites are now anchored to UTF-8, not just the one that
fired — the others were waiting for the first character outside cp1252.

## Three performance figures withdrawn

This train takes back more than it adds, and that is the point.

- **The arm64 +5.6 % published in v2026.8.8 is retracted.** Rebuilt on two independent builds it reads
  −0.01 % and +0.03 %. It was one build's **code placement**. The evidence originally given for it —
  an ASCII witness moving with `words` — proves nothing: two instances of one pattern compile to the
  same code and so move together under a placement shift exactly as under a real cost. That argument
  separates per-row measurement noise and nothing else.
- **The x86-64 cost in the same release is now explained**, and it is placement too: every out-of-line
  engine symbol is byte-identical between the builds, forcing 16- or 32-byte alignment collapses the
  delta on every row that carried it, and under forced alignment the delta reappears on *different*
  rows — which is what placement does.
- **v2026.8.7's `cold` figure is requalified, not retracted.** It reproduces on two unaligned builds
  (`words` −11.95 %, −12.14 %), but under a mere 1 % of code inflation the same comparison reads
  **+5.70 %**, sign reversed. `cold` *is* a placement directive, so its measured benefit cannot be
  separated from placement — which is the blind spot of the discriminator above, found by turning it on
  a case it cannot judge. The annotations stay; the number describes the shipped build, not the change.

`design.dox` §10.1 carries all of it as a reusable rule: unchanged out-of-line symbols plus forced
alignment moving the delta means placement, not inlining — except for placement directives, where the
honest report is the shipped configuration's number **plus** its alignment sensitivity.

## Verification

**The published documentation site is not current at the time of writing.** GitHub's Pages build queue
