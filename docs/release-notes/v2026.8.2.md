# v2026.8.2 — a first search that stopped paying for work it was about to throw away

Three performance changes, all on the **first** search a pattern performs, found by profiling with
callgrind on the x86-64 host rather than by reading the code. Steady-state matching is untouched, and so
is every answer: spans, capture groups and match counts are identical to v2026.8.1.

## The inner-literal route built its tables, then abandoned on the next line

The route's small-haystack guard ran immediately **after** `ensure_immutables()`. So a short subject
with a literal candidate paid the entire byte-program expansion — for a text-mode class like `\w`,
the whole UTF-8 trie machinery — in order to discover it was too short to want the route at all.

Deciding before the build is exact rather than heuristic: the cold floor clamps at 64 KB and so is
never below the warm floor's 4 KB, which means a haystack under 4 KB abandons whichever applies.

Measured on arm64 with one live regex per sample (200 kept alive, one first search each):

| pattern | subject | before | after | |
| --- | ---: | ---: | ---: | ---: |
| `\w+@\w+` | 18 B | 459.51 µs | **0.71 µs** | **647×** |
| `(\w+)X(\w+)` | 13 B | 466.91 | **1.23** | **380×** |
| `(\w+)@(\w+)` | 80 B | 458.60 | **2.97** | **154×** |
| `[a-z]+@[a-z]+` | 80 B | 3.65 | 2.16 | 1.7× |
| `\w+@\w+` | **8 KB** | 1804.59 | 1720.72 | 1.05× |

The ASCII gauge moves too, and that is the honest reading: the saving is the **build**, not anything
specific to Unicode classes — text-mode classes merely make it enormous. The 8 KB row is the control
that shows the guard is size-gated rather than always-on.

**Confirmed without a clock.** A build counter reads **400 UTF-8 trie builds** across those 200
searches before the change and **0** after. That number cannot drift and cannot be contaminated by an
allocator; it is what settled the question when the timings disagreed with each other.

**Scope, since the ratio invites over-reading.** This is the first search, on a subject under 4 KB,
for a pattern that takes the inner-literal route and finds a literal candidate. A no-match scan was
already memmem-only and built nothing. Steady-state search is unchanged.

## The UTF-8 trie was built once per occurrence, not once per class

A trie is a pure function of its code-point class, but the builder emitted one per `klass_cp`
*instruction* — so `(\w+)X(\w+)`, whose two `\w` intern to the same class, built the identical
structure twice. Deduplicated within a build: **637.78 → 476.48 µs (−25 %)** on the same
one-live-regex-per-sample protocol.

Sharing one cache across the program's two expansions — Tier-A with assertions stripped, Tier-B with
them kept — was then written, wired and **refused**: it helps small classes and hurts large ones
(`(\d+)X(\d+)` −8.2 %, `(\w+)X(\w+)` **+2.0 %**), and the large ones are the entire reason to care.

## The compat `regex_iterator` keeps its walker

Each advance was a fresh `search()`, building a fresh VM state where `find_iter` builds one and reuses
it for the whole walk. That state holds every per-haystack decision — the Aho-Corasick density
verdict, the inner-literal gate, the DFA warmup — so the compat path re-derived all of them once per
match.

| pattern | `++it` | `it++` |
| --- | ---: | ---: |
| `[a-z]+` | 71.0 → 31.8 µs (**2.2×**) | 111.9 → 61.1 (1.8×) |
| `(\w+)@(\w+)` | 22.0 → 14.7 (1.5×) | 28.1 → 20.8 (1.4×) |
| 24-branch alternation | 254.3 → 57.0 (**4.5×**) | 274.2 → 73.0 (3.8×) |

**The walker is an accelerator, not the state**, which is what makes copies cheap. `real_pos_` stays
the source of truth; a copy gets no walker and rebuilds one only if it advances. Copying the walker
would clone 8232 bytes against the iterator's 320, and sharing it copy-on-write would clone on the
first advance — which post-increment performs on every call, buying `++it` at the price of `it++`.
Both forms improve; neither regresses. Copy independence is pinned against `std::sregex_iterator`
doing the same thing.

## How to measure a first search — three traps, all sprung here

This train's numbers were published wrong once, retracted wrongly, and then re-measured. The traps
are now written down in `docs/BENCHMARKS.md` because none of them is caught by the gate, CI or
coverage:

- **One live regex per sample.** The per-regex caches are invalidated by program *address*, so a
  construct-search-destroy loop can hand the next iteration the previous one's address and skip the
  build being timed — and `min` over that loop selects exactly the iterations that skipped it.
- **`git checkout <file>` for the "before" arm, after committing, measures the change against
  itself.** It restores the committed content, which now contains the change. Both arms read
  identically, which reads exactly like a refutation. Build each arm from a named revision.
- **`callgrind_annotate` marks recursion depth with a trailing `'2`**, and those lines are the same
  function. Summing them double-counts.

## Disclosed, not chased

- **The expansion is still blind to the subject.** For `\w`, over 99 % of what it builds recognises
  code points a pure-ASCII subject can never contain, and the subject *is* known at search time. An
  ASCII-first expansion upgraded on demand is the shape that would fix it; that changes when the
  immutables are built, which is engine structure, and it is sized in the source rather than
  attempted.
- **A per-search scratch-state cache was prototyped and refused.** Construction costs 9.5 ns, 21–27 %
  of a short search, with no member dominating. Reuse is safe within one regex — `find_iter` already
  does it — and segfaults across regexes: AddressSanitizer reports a heap-use-after-free through the
  class-table pointer. The only safe granularity is per regex per thread, and that lookup costs more
  than it saves.
