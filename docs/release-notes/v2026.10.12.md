# v2026.10.12 — A streamed token read once, a wide code-point shape kept on its walk

A lexer reading text in pieces can now go on munching a token still open at a piece's end from where the DFA's walk
stood, instead of reading it again from its start at every piece. A fixed code-point shape wider than 255 keeps its
inner-literal walk, and the C ABI refuses a flag it does not know.

## Added

- **`real::dfa_munch_progress`, and `dfa::munch(subject, offset, progress)`.** A munch whose walk is still alive at
  the subject's end records where it stood; the next call, over the subject with text appended, goes on from there
  and answers what a munch from scratch answers. A token of `n` bytes fed in pieces of `c` bytes costs `n` steps
  where munching it again cost on the order of `n²/c` (SciLex's stream: a 200 KB string in 64-byte pieces, 1.8 s →
  1.7 ms). The memo's munch is unchanged.

## Performance

- **A fixed code-point shape wider than 255 keeps the inner-literal walk.** The count of code points before the
  literal was 8 bits wide, so `\w{256}x` and wider fell to the Pike VM: `\w{300}x` 1 183 → 56 ns/B, `\w{1000}x`
  3 922 → 176 ns/B.

## Fixed

- **The C ABI refuses a flag bit no `real::flags` value has** (`REAL_ERR_ARGUMENT`, from `real_compile` and
  `real_set_compile`), where it ignored it: an older library handed a newer binding's flag matched with other
  semantics and said nothing. `real_match` with a mode no `REAL_MODE_*` names returns -1.
