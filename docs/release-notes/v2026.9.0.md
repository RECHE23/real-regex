# v2026.9.0 — the same complaint, three times, and the sweep that closed it

One reader reported the same defect three times in three weeks, each time from a different pattern:
an error message that says *where* something is wrong without saying *what*. This release stops
answering the cases and answers the family — measured over 486 patterns with `re` as the oracle,
which took the divergences in that branch from **165 to 53**, and the "unknown extension" family
from **114 to zero**. Everything still divergent there is deliberate, and now written down.

It also carries a **breaking change to the Go binding**, released separately as module `v0.2.0`.

## An error message that names what it refuses

`(?z)a` reported `unknown extension at position 2`. `re` reports `unknown extension ?z at
position 1` — it quotes the construct, and points at the `?` that opened it rather than at the
character that ended it. That gap covered **114 patterns**.

Both refusal sites now quote everything consumed since the `?` plus the character that failed, and
report at the `?`:

| pattern | before | now (and `re`'s wording exactly) |
| --- | --- | --- |
| `(?z)a` | `unknown extension at position 2` | `unknown extension ?z at position 1` |
| `(?P)a` | `unknown extension at position 3` | `unknown extension ?P) at position 1` |
| `(?\)a` | `unknown extension at position 2` | `unknown extension ?\) at position 1` |
| `(?` | `unknown extension at position 2` | `unexpected end of pattern at position 2` |

`(?P)` names `?P)` because the `P` was consumed before the failure; `(?\)` names `?\)` because an
escape is two characters to the reader as it is to the parser; the end of a pattern has nothing to
quote, so it says so instead. **No new knowledge was needed** — the parser had the offsets and the
characters all along, and threw them away.

## The flags terminator: a non-terminator is not a misplaced global

Reported against 2026.8.20: `(?i*)` and `(?i7)` answered `global flags not at the start of the
expression`. `(?i*)` at the start of a pattern *is* at the start; the complaint was about the
character after the flags, not about placement.

The terminator question now follows CPython's `_parse_flags` exactly — four outcomes rather than a
binary accept-`:`-or-blame-placement — so `(?i*)`, `(?i7)`, `(?i7:a)`, `(?i-7)`, `(?i )` and
`(?i$)` all report `missing -, : or )` at the position `re` names.

## Inline flags: what stays different, and why it is now written down

The sweep left 53 divergences in that branch. Every one is deliberate, and the two families that
were undocumented are documented now — a reader probing that corner would otherwise find them by
accident, which is how this whole sequence started.

**The set is not `re`'s, in either direction.** REAL adds `U` (ungreedy, RE2's spelling: it inverts
the default greediness of every quantifier in scope) and has no `u` or `L`. So `(?U)a+` is REAL-only,
and `(?iu)a` — valid in `re`, where `u` is a no-op — reports `unknown flag` here. `re.LOCALE` is
excluded by design: this engine is Unicode in text mode and raw bytes otherwise, never
locale-dependent.

**The grammar is wider.** `re` validates flag *combinations* and rejects several; REAL parses them
and applies the removal last. `(?i-i:a)` turns `i` on and then off — `re` calls that "flag turned on
and off", REAL runs the group case-sensitive. `(?i-a)` turns off `a`, which `re` refuses outright and
REAL reads as a return to the Unicode default.

Both are supersets: a pattern written for `re` never reaches them, so a drop-in cannot break on this.
A pattern written *here* and moved to `re` can.

## Constructs REAL names where `re` calls them unknown

The remaining 26 divergences in that sweep are the opposite trade, and they stay. `(?C1)`, `(?R)`,
`(?1)`, `(?-1)`, `(?&name)` and `(?P>name)` report `callouts are not supported` / `pattern recursion
is not supported` / `subroutine calls are not supported` where `re` says `unknown extension` —
naming a construct excluded by design is worth more than calling it unknown, which is the same
argument the first section of this note makes.

They are also classified `unsupported` rather than `syntax`, which is what a C caller branches on
(`REAL_ERR_UNSUPPORTED`) — it has no exception type and no message contract. A possessive or atomic
group over a compound body (`(?:ab)*+`, `(?>ab|a)`) joins them: well formed, beyond this engine, and
the Python binding now offers `fallback=True` for it, which was verified to actually run the
pattern rather than merely advertised.

## Python: an unknown group name raises `IndexError`, as `re` does

`m.expand(r"\g<nope>")` raised `real.error`. `re` raises `IndexError`, and since `real.error`
derives from `re.error`, **no single handler covered both libraries**: `except re.error` caught us
and missed `re`, `except IndexError` caught `re` and missed us. Whichever one a caller had written
against `re`, porting broke it.

`re` is inconsistent here on purpose — an unknown group *name* is `IndexError`, an out-of-range
*number* stays `re.error`, in the same call — and a drop-in copies that rather than tidying it,
because the handler in user code is written against the inconsistency.

Also documented rather than aligned: a `sub` callable **must return a string**. CPython reads a
returned `None` as an empty replacement, which its own documentation does not promise; REAL raises
`TypeError: expected str replacement`. `return ''` is the portable erase and agrees in both.

## Go module v0.2.0 — `FindAllIndex` and `FindAllSubmatchIndex` take `n`

A **breaking change**, tagged separately as `bindings/go/v0.2.0` with its own note
(`docs/release-notes/go-v0.2.0.md`). Six of the eight `FindAll*` methods already took `regexp`'s
`n`; these two did not, so a caller porting from `regexp` hit a compile error on two methods out of
eight and had to remember which. Fixing your code is mechanical: add `, -1`.

Worth knowing even if you do not use the Go binding: `make release` hardcoded
`bindings/go/v0.1.<n+1>`, so the first release after this change would have shipped a **compile
break as a patch upgrade** — which `go get -u` delivers silently. The minor is now read from the
newest Go tag and never assumed, and the target refuses rather than guessing if it cannot parse one.

## Under the hood: a rule that was only prose

Five pages under `docs/site/` name a canon they must agree with. The rule lived in an HTML comment
and had no instrument, and it had drifted **twice, both shipped**: the divergences page was edited
alone four times, and the `std::regex` reference kept naming an internal template parameter for two
weeks after the canon deliberately stopped naming it.

`make check-doc-mirror` now compares the two pages that are true mirrors, section by section, each
with its own splitter and its own declared transformations — and checks the three that *distil*
their canon only for the thing a machine can honestly say about them: that the canon still exists.
Comparing their prose would be wrong, not merely hard. Writing the transformations into each page's
header before teaching the script about them is what surfaced a fifth one nobody had recorded.

## Upgrading

**C++ and Python:** the changes are error *messages* and error *types*. No pattern changes what it
matches, and no working code stops working — unless it matched on the text of an error, which these
notes have never promised to keep still.

**Go is the exception, and it does not fail quietly at first:** `FindAllIndex` and
`FindAllSubmatchIndex` change signature, so a call site is a compile error until you add `, -1`.
See `go-v0.2.0.md`, which also covers the empty-match rule that changed the *results* of `Split`
and every `FindAll*` in the release before this one.
