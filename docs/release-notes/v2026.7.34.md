# v2026.7.34 — fixed false `\b`/`\B` at a multi-byte/ASCII word junction

Patch release. Closes a correctness gap in `\b`/`\B` next to a single
Unicode word or digit code point, found while stress-testing 7.33's `.`
fix, plus a dev-tooling fix for the local calibrated gates. No API
changes.

## Fix (correctness) — `\b`/`\B` + a single code point claimed a false boundary at a multi-byte/ASCII junction

`\b\w`, `\w\b`, `\b\d`, and their `\B` counterparts — a `\b`/`\B` wrapped
directly around a SINGLE code point, no `+` — could claim a word boundary
between two adjacent word code points whenever one side was multi-byte
UTF-8 and the other was ASCII: `\b\w` on `"éa"` matched twice (`é` at
`[0,2)`, wrongly again at `[2,3)` for the `a`) where a single match is
correct, and the same in the other direction (`"aé"`).

The root cause is architectural, not a byte-level bug: the fast path's
own word-boundary predicate (`word_before`/`word_after`) was already
correctly code-point-aware. The gap was a soundness hole in an
*optimization* — "B-1", which drops an explicit `\b` check next to a
`\w` class on the reasoning that a **maximal greedy run** (`\b\w+`) can
only ever start where the preceding character is non-word, making the
check redundant. That reasoning does not hold for a *single* code point:
`\b\w` may legally start on any word code point, including one
immediately preceded by another word code point. The fast-path
recognizer for `\b\w+` and bare `\b\w` shared one code path but never
passed through whether a `+` loop was actually present, so `\b\w`
silently inherited a redundancy guarantee it never earned, and the
resulting fast path skipped the boundary check entirely.

Fixed by threading an explicit "is this a maximal run" flag through the
optimization: the ASCII class-loop path (`\b[a-z]+`-style) is
structurally always a maximal run and keeps behaving exactly as before;
the Unicode single-code-point path (`\b\w`, `\b\d`, …) now keeps the
boundary check it was wrongly dropping. `\b\d`-style patterns were never
affected (they already take a different, always-safe branch of the same
optimization) — only `\b`/`\B` wrapped around an *exact* `\w`-class
single code point.

## Fixed but not shipped — an x86/gcc residual stays as it was

7.33 accepted a measured +7.5% (x86/gcc only, arm64/clang flat) on
`.`-heavy corpora as the bounded cost of closing a UTF-8 smuggling class
of bug. Two candidate recoveries were built and interleaved-A/B'd on both
ISAs this cycle — a packed single-load bounds table, and a branch on the
four narrowed lead bytes — and **both were eliminated by measurement**:
the branch design cost ~4% more on arm64/clang before x86 was even
reached; the packed-table design cleared arm64 clean but did not recover
the x86/gcc regression either. Conclusion: the existing two-byte
bounds-table lookup is the measured optimum for this hot path on both
ISAs, and the +7.5% is the durable, accepted price of the strictness
fix — not a gap left open, a verdict reached by data. Nothing shipped
from this arc; the tree is unchanged from 7.33 on this hot path.

The same dual-ISA A/B run also closed out a small open question from the
`\b`/`\B` fix above: an early single-machine read had suggested a ~3.9%
layout-shift cost on `\w+`/`\b\w+`-style maximal-run scans. Confirmed on
both ISAs this cycle: flat (+0.3–0.5%, noise), not a real regression.

## Tooling — `gate-bump`/`gate-doc`/`gate-test` diff against a configurable base

The three calibrated local gates compared unconditionally against
`origin/main`, so on a stacked train — several commits deep, not yet
pushed — a late commit's own diff accumulates every earlier commit's
files too, and the category guard correctly refuses even when that
commit's own change is squarely in-category. Seen twice on the 7.33
train, forcing a manual fallback each time. `GATE_BASE` is now a
Makefile variable (default `origin/main`, so the fail-closed behavior is
unchanged for anyone who does not override it); `GATE_BASE=HEAD~1 make
gate-bump` scopes the category check to just the latest commit. This
release's own version bump used it for real for the first time.

## Honesty

The `\b`/`\B` fix is a real, if narrow, correctness gap: any Unicode-text
pattern combining a word boundary with a single non-greedy word or digit
class, on non-ASCII text, could silently over-match. `\b\w+`-style
maximal-run patterns — almost certainly the more common shape in
practice — were never affected. The x86/gcc dot-emoji residual from 7.33
stays exactly as it was: two honest attempts to recover it, both
measured and both rejected, is a more solid finding than one untested
guess would have been.
