# v2026.9.2 — the unit of the mode

This train has one idea running through it, and it is not a feature. A regex engine that works in two
modes has, in each, **one unit**: a code point in text mode, a single byte under `flags::bytes`. That
unit decides three separate things — what a `\` consumes, what a diagnostic quotes, and what a
character-class member is worth — and in each of those three places this engine used the wrong one.
The symptoms looked unrelated. `\é` did not compile. `(?é` raised a text-decoding failure instead of
an error message. `[é]` on a bytes pattern was refused outright. One rule explains all three, and
each fix is small because the rule was already written down; only the code disagreed with it.

The second thread is less comfortable. Four of these eleven commits fix a **document that stated the
opposite of what the code did** — sometimes a document this project published as a correction. They
are listed as what they are.

With one exception, named below, every change here either accepts a pattern that previously raised
or changes the text and position of an error. The exception is `{,}`: it compiled before, and what it
matches has changed.

## The unit of the mode

**A `\` before a non-ASCII character is that character.** `\é`, `\€`, `\😀`, `[\é]`, `a\éb` were all
refused with `unsupported escape sequence`. Python `re`'s rule — this engine's model — is that a `\`
before an unknown ASCII *letter* is an error and a `\` before anything else is that character
literally, so every one of those is a valid pattern there. ECMAScript's Annex B identity escape
answers the same, and so does `std::regex`, whose unit is a `char`: `\<C3>` matches the one byte.
Three references, one rule.

The escape consumes one unit of the mode, and that is why the fix could not route through the
existing `\xHH` path: that path yields a BYTE, and its caller emits a byte node for any value
`>= 0x80` — the documented `\xHH` provenance split. A `\é` sent there would have compiled and then
failed to match `é`. Both parse sites now decide before that call and emit exactly what each already
emits for the *unescaped* character a few lines above, so the two forms agree by construction: `\é+`
repeats the code point, `icase` folds `\é` to `É`, and `[\à-\é]` is one code-point range.

RE2 is the one family that reads it the other way — Go `regexp` and the Rust `regex` crate both
answer `invalid escape sequence`, the same error they give `\q`. REAL is a superset there, not a
divergence in meaning, and both binding READMEs say so per surface.

**`unknown extension` quoted a byte, so the message itself was not text.** `(?é` did not report an
unknown extension: it reported a *decoding failure about the diagnostic*. The parser copied the
offending construct one byte at a time, so a non-ASCII character contributed only its lead byte,
`what()` was not valid UTF-8, and the Python binding's conversion of that message raised
`UnicodeDecodeError`. `real.error` was never raised at all — `except real.error` did not catch it —
and the actual fault, an unknown extension at position 1, never reached the caller. A message that
cannot be read is worse than a vague one, because the vague one still carries the position.

The quoted unit is the mode's: the whole code point in text (`unknown extension ?é`, `?😀`, and `?\é`
where the escape is two characters), one byte under `bytes`, written `\xHH` in ASCII above `0x7F`
exactly as `re` writes it — `b'(?\xc3\xa9'` gives `?\xc3`, not `é` and not the raw byte. That
spelling is not cosmetic: a bare `0xC3` in the message is invalid UTF-8, which is what
`PyObject_CallFunction(..., "s", ...)` refuses, so on a bytes pattern the escape is what makes the
error reportable at all. The binding therefore needs no change and gets none.

The invariant is stated once and tested as itself: **`what()` is valid UTF-8 whatever the pattern
held.** That also settles a case `re` has no witness for — a text-mode pattern carrying a byte that
opens no code point, which a Python `str` cannot reach but a C++ caller can.

**A bare high byte is an ordinary class member under bytes.** `[<C3>]` was refused —
`non-ASCII character class member not supported` — while the same class written `[\x80-\xff]`,
`[\xc3]` or `[\<C3>]` compiled and ran. `re` on a bytes pattern and `std::regex<char>` both read the
bare form as the plain byte class, so this was the last spelling of a byte class this engine would
not take, and the only one where the escaped forms and the raw one disagreed.

The refusal existed to make the `std::regex` compat layer fall back, and that was the wrong trade. A
byte class is not a construct a linear engine cannot represent: it is the language `\xHH` already
compiles to, and the class bitmap already carried bytes `>= 0x80` because the escaped spellings put
them there. So the refusal surfaced under `policy::strict` as *"this pattern requires a non-linear
(backtracking) engine"* — which it does not — and under `policy::fallback` it delegated to
`std::regex` and gave up the linear-time guarantee, for an answer REAL was already giving in another
spelling. Every form of it now reports `uses_real()`.

Text mode does not move: there the unit is a code point, `[é]` is the character, and a byte sequence
that is not a code point is still refused.

## Diagnostics: the position, and what it points at

**`e.pos` counts characters on a `str`, as `re`'s does.** The Python binding handed the engine's
BYTE offset straight through, so every position drifted by the UTF-8 width of whatever preceded the
fault: `é(` reported 2 where `re` reports 1, `€(` 3, `😀(` 4. `colno`, derived from `pos`, drifted
with it; `lineno` did not, because a newline is one byte either way — which is exactly what made this
easy to miss, and why `a\n(` looked fine while `é\n(` was off by one column.

This extends a claim **v2026.9.1's notes made**, without contradicting it: they said every position in
their table is `re`'s, and for those rows — all ASCII — that was true and is still true. What was off
is a different surface, the binding's conversion of the engine's byte offset, which no ASCII row
could expose. This train closes that hole, so the claim now holds for a non-ASCII `str` too.

The conversion belongs to the binding, not the engine — C++, the C ABI, Go and Rust are byte APIs and
`regex_error::position()` means the same thing in all four; only `re.error` counts characters, and
only on a `str`. It is gated on str-ness, and that gate is not caution: a bytes template's offsets
are already right, so an unconditional conversion would have broken a path that agreed. A separate
commit supplies the witness that gate was missing — the first version of the test had no bytes
*template* case, so removing the gate entirely passed it.

**A braced repeat on an anchor reported past its own closing brace.** `\A{1}` reported at 5, the byte
after the `}`, where `re` reports the `{` at 2 — and the drift grew with what the braces held:
`\A{2,}` four past, `\A{10,20}` seven. A position that moves with the length of the construct it
describes is not a position. Same cause as three faults the previous train fixed: the check spells
"is there a quantifier here" as a parse that CONSUMES. `*`, `+` and `?` consume nothing and were
always right, which is why this looked half-broken rather than broken.

## Where the catalogue said the opposite of the code

**`{,n}` is Python's shorthand for `{0,n}`, and `{,}` is `{0,}`.** The comma makes the bounds
optional, not absent. The engine read `{,}` as literal text, and — worse — the divergences page and
its mirror both listed `a{,}` among the forms that are "ill-formed on both sides", which is the
opposite of what `re` does. A follow-up removed the last residue: `parse_quantifier`'s own Doxygen
still listed `a{,}` among the ill-formed literals, three lines from a grammar line that already named
`{,m}` correctly.

**`[\é]` is not the class of two bytes.** The escaped-non-ASCII work cited `[\é]` as a class that
stays on REAL, but the UTF-8 spelling of that pattern is `[ \ C3 A9 ]`, where the backslash escapes
only é's *first* byte — and at the time, a bare second byte was still refused. The class of two bytes
needs a backslash before each. The wrong example sat in a document and in a code comment, and the
document was a **canon** with a machine-compared mirror, so editing it alone turned the docs-site
gate red. Both now name the trap instead of demonstrating it.

## The harness that judges the work

Two fixes to `tools/sabotage.py`, the harness that breaks one thing on purpose to prove a guard
reacts. Both are failure modes where the tool reports something other than the truth.

**SIGTERM skipped the revert.** The restore lives in a `finally`, which covers a crashing check (an
exception) and not a killed run (a signal). A harness timeout firing between apply and revert left
the working tree **sabotaged**, so the next gate would have judged the sabotage rather than the code.
SIGINT and SIGTERM now raise so that `finally` runs; SIGKILL is uncatchable and is not claimed.

**Strict decoding discarded the verdict.** The tool read the check's combined output with the default
strict UTF-8 codec, so a check whose output is not valid UTF-8 raised *inside* `communicate()` —
after the check had run and before its exit status was read. The one thing the script exists to
deliver was replaced by a harness traceback. This is reachable from ordinary work, not a contrived
input: a test suite prints the pattern it failed on, and a byte-mode witness holds whatever bytes it
holds. A lone `\<C3>` is a valid pattern and not a valid UTF-8 sequence — so a sabotage of the
byte-mode escape path took the harness down instead of reporting RED, which is the failure mode most
likely to be misread as "the sabotage did not apply".

## Benchmarks: the tables do not move, and the stamp stays at `2026.8.15`

No number in `docs/BENCHMARKS.md` is refreshed, deliberately and for the same reason as the previous
train: the document declares its regime as **two ISAs**, and only one was available. Publishing one
leg would produce a table whose halves describe different trees.

What this train changed is off the measured paths by construction rather than by argument. Every
engine edit is on the **parse** path or an **error** path, and each new branch is reachable only
where compilation previously *failed* — so for any pattern that compiled before this train, the
emitted program is the same one, with the single exception named above: `a{,}` now emits `a*`. No row
in `docs/BENCHMARKS.md` carries a braced repeat with an absent lower bound, so that exception is real
but falls outside every cell here — checked, not assumed. `CHANGELOG.md` carries the per-train
entry.

## Upgrading

**One pattern that already compiled now matches something else: `{,}`.** It was read as literal text,
so `a{,}` matched the four characters `a{,}`; it is now the `{0,}` shorthand, so it matches like `a*`
— `aaa` yes, `a{,}` no. That is `re`'s reading, and it is the only emitted program in this train that
changes for an input that previously compiled. **If your code relied on `a{,}` being a literal, it
will now see `a*`.** The rest of the family did not move: `a{,3}`, `a{,1}` and `a{,0}` already agreed
with `re`, and `a{}` — no comma, so the bounds are genuinely absent — is still literal.

**Everything else that compiled before compiles the same.** Patterns that previously raised now
compile: `\<non-ASCII>` in and out of classes, and a bare high byte in a bytes-mode class. If your
code *depends* on those raising, it will no longer see the exception — the same caveat every superset
carries.

**Error text and error positions moved**, on the constructs listed above. Code matching on the text
of an error was never promised that it would stay still. On the Python surface specifically, `(?é`
now raises `real.error` where it raised `UnicodeDecodeError`, and `e.pos`/`e.colno` on a `str` count
characters rather than bytes — both are corrections toward `re`, and both change what a caller sees.

**The Go module goes to `v0.3.1`**, a patch: new patterns compile and messages improved, no API
change, and no result change for any pattern that already worked — except `{,}`, which is the same
engine and therefore the same change on this surface. Note what that costs here specifically:
`regexp` **accepts** `a{,}` and reads it as literal text, which is what this package did too until
now, so the change moves REAL away from `regexp`'s reading and onto `re`'s. It is not new as a class
— `a{,2}` has read as `{0,2}` here, and as literal text under `regexp`, for some time — but `{,}`
joins it. The Go binding's **API** is `regexp`'s; its **engine** is `re`'s, which is precisely why
flavor differences exist there at all, and `{,}` moves toward `re`, not toward `regexp`. If you
carried such a pattern it now repeats instead of matching its own text.
