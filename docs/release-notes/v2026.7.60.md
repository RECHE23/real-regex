# v2026.7.60 — a counted repeat gets a route, and the suite learns to see it

A **performance** release, and a measurement release: the largest number in it was
found by a row this release also adds. No API changes, no behaviour changes: every
span, every capture group and every match count is byte-identical to v2026.7.59,
verified as a differential against the same engine with the routes switched off
rather than asserted — 494 pattern × subject pairs on spans, 28 on every capture
group of every match, plus 825 pairs on the new route specifically.

## The row this was about, which did not exist before this release

The suite had eight families and not one counted repeat: every family used `+`, `*`
or a literal. It also had no case-insensitive pattern, while both compile-cost
defects this project has shipped lived in the icase path. Three families were added
for the second reason and immediately found something bigger, for the first:

| criterion row | v2026.7.59 | v2026.7.60 | vs the `regex` crate |
| --- | ---: | ---: | :--- |
| `find/repeat` (`\w{8}`) | 2.24 ms | **123.9 µs** | 24.55× behind → **1.35× behind** |
| `captures/repeat` | 2.26 | **125.7** | 24.46× behind → **1.33× behind** |
| `first_use/repeat` | 15.4 µs | 12.5 | 93.5× ahead → **113.4× ahead** |

`\w+` and `\w{8}` look alike and are not. Three shapes bracket the counted one and
all three were already fast — `[a-z]{8}` through `fixed_shape`, `\w{8,}` and `\w+`
through the code-point class loop — which left exactly one combination unserved: a
code-point class with a bounded count. It ran on the general Pike VM (`add_thread`
22.3 %, `step` 22.2 %) and grew superlinearly in the count: 247 µs for `\w+`, 499 for
`\w{4}`, 2369 for `\w{8}`.

The recognizer declined that shape on purpose and said why — "no MIN-only run to
bound a search against". That is the real obstacle, not an oversight: the route
extends greedily and bounded the result from *below*, and an exact count needs it
stopped from *above*, since `\w{8}` over a nine-letter word matches the first eight
and not the nine. `greedy_cp_class_max` is that bound.

arm64 wall clock on a 64 KiB walk: `\w{8}` **−95.1 %**, `\w{4}` −57.0 %, `\d{4}`
−9.9 %, with `\w+`, `\w{8,}`, `[a-z]+` and `\b\w+\b` all at 0.0 %. x86-64: `\w{8}`
**−96.8 %** on the clock.

## What the differential caught before it shipped

A first version of the route was wrong on word boundaries. `\w{4}\b` over
"abcdefghi" must match at 5; it matched nothing. Both retry loops advance by the
whole run when a candidate fails — right for a maximal run, whose end *is* the
boundary, and wrong for a bounded one, where failing at 0 says nothing about 5.

The counted shape now declines a word boundary rather than shipping wrong, and the
code says what lifting it would take. This is the second release running where
differencing a new route against the general VM was the thing that caught a defect,
and it is why the route is narrowed rather than merely tested.

## Compile cost, continued from v2026.7.59

That release made each case fold cheaper without stopping it happening once per
repetition. A bounded repeat holds ONE class node in the AST and emits it k times, so
`\w{500}` folded `\w` five hundred times. A four-way direct-mapped cache on
(class index, fold mode, negated) fixes it, and caches the *finished* class so
`coalesce_ranges` stops re-sorting per repetition too.

| compiling with icase, arm64 | v2026.7.59 | v2026.7.60 |
| --- | ---: | ---: |
| `\w{64}` | 3.84 ms | **0.128 ms** (−96.7 %) |
| `\w{256}` | 302.6 µs | **241.9** (−20.1 %) |
| `\d{4}-\d{2}-\d{2}` | 26.0 µs | 12.8 (−51.0 %) |

x86-64 instructions for `\w{500}a` with icase: **−97.0 %** (70.9 G → 2.1 G). `\w{k}a`
now grows sub-linearly in k where it was linear — 0.28 ms at k=50, 0.36 at k=200,
0.96 at k=800, against 25.50 / 76.94 / 305.14 two releases ago.

## A net, and a fuzzer that was refuted before it shipped

`tests/frontend/test_compile_scaling.cpp` gates the invariant both compile-cost
defects broke: compile cost must scale with the number of DISTINCT constructs, not
with how often one is repeated. It asserts the marginal cost of one further
repetition under icase against the same marginal without it — a form that cancels
machine speed. Measured either side of the fix: `\d` 671.68× → 0.78×, `\w` 383.25× →
0.67×, `\s` 196.08× → 0.89×. The bound sits at 8×, nine times the worst passing ratio
and a seventh of the smallest failing one. Verified to **fail** on the tree the fixes
landed on, not merely to pass on this one.

It replaces a compile-cost *fuzzer* whose design its own first measurement refuted: a
budget of nanoseconds per compiled instruction does not discriminate, because the
legitimate spread is 340× and no stable factor separates that from a defect.

## Disclosed, not chased

- **`(?i)[a-z]+` scans 3.37× behind the crate** and 4.3× behind its own plain form.
  Under icase `[a-z]` gains the long s and the Kelvin sign, stops being a pure ASCII
  class and emits as a code-point class. `(?i)dog` is 1.17× *ahead*, so this is the
  class widening and not the flag. Visible for the first time here, because the row
  did not exist before.
- **`(\w+)@(\w+)` first use remains 2.64× behind**, unchanged by this train.
- **`\w{k}\b` keeps the general VM**, as described above.

## One measurement that disagrees with itself

On gcc/x86-64 the unbounded shapes read **+2.3 % in instructions** (`\w+`, `\w{8,}`,
`\b\w+\b`) from codegen perturbation in a file the project already keeps a
gcc-specific variant of. Three branch orderings were measured and all three read the
same +2.3 %, so it is the code's presence and not its position. On the **clock** the
same `\w+` reads **−0.2 %** and `\b\w+\b` +1.3 %, and arm64 reads 0.0 % for both.
Both numbers are here because only one of them is the answer, and the instruction
count is not it.

## Verification

Criterion figures come from an interleaved A/B against v2026.7.59 with the same bench
file on both sides — which is what lets the new families exist on both — one group at
a time, two rounds, machine otherwise idle. No row regresses by more than 3 %; every
row other than the three `repeat` gains lands within ±2.2 %.

Both engines were verified to agree before any deficit was named: identical match
counts and identical total matched bytes on all three new patterns over the corpus.

`full-local-gate` on every commit in the train, plus CI green including the
windows-msvc leg. 780 tests, 345 120 checks. Coverage 95.60 % (floor 95.0).
clang-tidy clean, MISRA 0, sanitizers clean, Go and Python bindings green, gcc-14
green.

## Notes

Nothing here changes what REAL matches. The linear-time / ReDoS-safe guarantee and
the bounded lookarounds are unchanged, and so is the API.
