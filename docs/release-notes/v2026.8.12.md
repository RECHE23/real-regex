# v2026.8.12 — three more routes stop paying per match, and a cost only one compiler paid

A performance train with no API change and no behaviour change: `exhaustive-compat` reads identically
before and after (3 218 434 cases, 4 548 documented divergences, 0 serious). Nothing here is urgent.
What it is, is a train whose largest single finding was invisible to every instrument this project had
— and the four instruments added to find it are as much of this release as the speed is.

## If you build with GCC, you get a per-call cost back for free

`basic_pike_state` held its two thread lists as `ThreadList lists[2]`. An array of two is constructed by
a loop, and GCC widens that loop body's sparse zero-stores — each list's handful of bookkeeping words —
into a `memset` over the whole element: **2472 bytes per list, 4944 per state**, which is precisely the
inline buffers the engine documents as deliberately left uninitialized, and which `search()` builds
fresh on every call. Clang emits scalar stores at the real offsets and pays none of it.

Two named members are constructed straight-line and the `memset` is gone. `sizeof` is 7736 before and
after, the fields stay consecutive: this is code generation and nothing else.

| a short anchored match, one call | before | after |
| --- | ---: | ---: |
| x86-64, g++ 15.2 | 112.1 ns | **82.5 ns** |
| arm64, g++-14 | 103.5 ns | **50.8 ns** |

Clang was already doing this, so a clang build sees nothing — 24 of 24 rows indistinguishable. If you
ship on Linux against libstdc++, this is the change in the release you did not have to ask for.

**Why it survived this long:** local development and the layout instrument both use clang, the CI matrix
builds with GCC but times nothing, and a per-call cost divided by a 100 KB corpus is 0.0004 ns/byte.
The first GCC timing leg this repository has ever had found it in its first run.

## Three more routes stop paying an engine entry per match

Six route families already handed out matches in batches; three did not, and an unbatched route pays the
whole dispatch on every match it returns. Measured on the consumer-shaped instrument, cumulatively
across the train, against recalibrated floors at 24 paired draws:

| pattern | what it is | change |
| --- | --- | ---: |
| `[a-z]+\|[0-9]+` | the plain tokenizer idiom — no recognizer claims it, so it lands on the lazy DFA | **−41.7 %** |
| `charlie` | a plain literal | **−20.8 %** |
| `\w+@\w+` | a match that does not START with a literal but requires one inside it | **−11.1 %** |
| `https?://` | same as the first, plus a rare-discriminant scan that was wrongly excluded | **−35 %** (throughput) |

`[a-z]+|[0-9]+` was the striking one: it read **10.00 ns/byte against `[a-z]+`'s 1.20** for the same
match count, and none of that was the scan. The DFA sweep is nearly free; the return was the cost, at
0.9949 engine entries per match where a batched route bills 0.2501.

The literal one had been **written, measured and refused before** — refused for what it charged five
other rows, up to +10.7 %, with the mechanism pinned by comparing machine code rather than argued: the
shared entry point every bench row measures was being recompiled. That diagnosis was right, and the
condition it named came true on its own — that function has since shrunk from 610 instructions to 377
for unrelated reasons, and at that size the filler no longer moves it (**377 → 377**). The refusal is
overturned by measurement, and both readings are kept side by side in the source.

## Anchored patterns, and an iterator that was taking the slow road

Two findings from earlier in the train, both reported by users measuring real deployments rather than by
this repository's own benchmarks:

**A short anchored pattern with a guaranteed hit** was 3.1× slower than `std::regex` through the
drop-in compatibility layer. It is now **1.7× faster** — the fixed-shape route was refusing anchored
shapes outright, and teaching it to honour the anchor as a *mode* rather than decline reads −73 % to
−87 % on the three per-call rows.

**`find_iter` could not reach the trailing-lookaround route** at all, because its return type names a
specialization a runtime hint cannot pick. `count_matches` ran `[a-z]+(?=[a-z])` at 4.41 ns/byte while
`find_iter` ran the same pattern, over the same corpus, at **53.84**. Same answers, 12× the time, and no
table showed it because the instrument measured one surface for every row. It now reads **−91.8 %**.

## What this train costs, in full

Three rows are slower, all three judged REAL at 24 of 24 draws, and they are real costs of the engine
rather than artefacts of a benchmark binary — the cumulative run on the consumer instrument says so, and
it says the opposite of what the four-engine harness alone would have suggested:

| row | cost | what it buys |
| --- | ---: | --- |
| `date {4}-{2}-{2}` | **+15.0 %** | the anchored fixed-shape route above (−73 % to −87 %) |
| `lookahead [a-z]+(?=[a-z])` | **+12.6 %** | `find_iter` reaching that route at all (−91.8 %) |
| `short trim replace` | +4.6 % | — |

Both large ones are trades, and both trades return between five and seven times what they cost. The
third is not attributed: this train is 30 commits and the judgement is cumulative.

On the published four-engine harness the class-scan band moves +1 % to +9.8 % on x86-64 and −0.3 % to
−5.1 % on arm64 — **opposite directions on the two ISAs**, which this project reads as code placement
rather than cost. `docs/BENCHMARKS.md` carries every figure from both instruments.

## Correctness and conformance

No behaviour changed, and one answer is now pinned that was previously only true:
`.A+A\n#\x01A@|.A+Azz\x00|.A+A\n#\x01A@|.A+` on a 61-byte subject reports the FIRST alternative at
(36, 44), which is what CPython reports span for span. The `regex` crate reports the fourth alternative
at (36, 39) — its known leftmost-first bug, and it reproduces there even under anchoring, which is why
the Rust differential fuzzer's exemption for that upstream class now confirms a span branch by branch
instead of asking the crate about the whole pattern. The exemption still cannot swallow a defect of
ours: that was checked by counter-example, not asserted.

## If you use the Python binding, this train barely reaches you

§B was re-measured over three passes and did not move: five of its six headline rows read within 2 % of
the previous release on every pass — `words · findall @100KB` 2.15 / 2.14 / 2.16×, `digits · sparse`
12.22 / 12.28 / 12.37×, `literal · hit` 11.60 / 11.86 / 11.77×, `anchored miss` 0.90× three times,
`date · search` 437 / 432 / 433×. The sixth is that section's known-unstable `sub · dates with refs`,
which read 79× and 85× on two quiet passes against a documented 56.84–76.08× spread; nothing in this
train explains a rise there, so it is not claimed as one.

That is a location rather than a disappointment: the binding's dominant cost is the Python round trip,
not the scan, so an engine train lands in the C++ figures and stops at the boundary. If you call `real`
from Python on large inputs you were already getting 2× to 400× over `re` depending on the shape, and
you still are.

## The instruments, because they are why this train found what it found

- **A GCC timing leg** (`make bench-compilers`). The project had timed itself with one compiler for its
  whole life.
- **A batched clock.** Per-call rows were reading **exactly 0.0 ns** under one compiler and 42 under
  another, purely from where each landed relative to the clock's tick. A row reading 0.0 ns is an
  unmeasured row, never a fast one.
- **A clock ramp and core pin** (`benchmarks/bench_warmup.hpp`). On a `powersave` host, five runs of one
  unchanged binary read 163.9, 230.2, 300.1, 301.8 and 315.5 ns on the same row. Both halves are needed:
  ramping without pinning lets the process migrate to a core that has not ramped.
- **A per-call duel against `std::regex`** (`make bench-percall`) and **three bench rows** for routes the
  instrument did not measure at all — which was not a coincidence: an unmeasured route is exactly where
  an unamortised per-match return survives.
