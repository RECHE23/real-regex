# v2026.7.50 — rare-discriminant prefilter: closes the URL gap vs rust (issue #3)

A **performance** release driven by dongweigogo's external report (#3): URL
patterns like `https?://[^\s]+` were ~19–21× slower than rust on filler-heavy
corpora. Root cause: REAL prefiltered on the weak first-byte `h` (and the
literal `http`), while rust memchr's a rare mid-byte (`:`) in SIMD.

## Headline: rare-discriminant prefilter

**Mechanism.** `memchr` a rare *discriminant* byte (e.g. `:` of `://`) →
**back-verify** the surrounding fixed shape (`http` + optional mono-byte `s?` +
`//`) → **confirm VM** for the rest of the pattern. **Not** multi-byte
`memmem` (measured and declined in 7.46 as P0.2: substring search lost to the
then-strong first-byte/`http` baseline when the optional made the colon offset
non-fixed).

The fixed-offset `rare_byte` prefilter alone cannot arm here: `s?` puts `:` at
offset 4 *or* 5. Extraction walks past a mono-byte optional, keeps the disc when
it is several times rarer than the first-byte filter, and records enough for
reverse-verify. Runtime density abandon (sticky per haystack) falls back to the
literal-prefix path when `:` is dense so colon-heavy text does not regress.

**Measured gain (dual-ISA, parity-checked).** On a **representative sparse-URL /
filler-heavy** corpus (URLs rare inside prose — log/scan shape, dongweigogo's
case):

| ISA | before | after | speedup |
| --- | --- | --- | --- |
| x86 | 0.766 ns/B | **0.057 ns/B** | **~13×** (rust order, ~0.068 ns/B class) |
| arm64 | ~0.37 ns/B | **~0.026 ns/B** | **~14×** |

Match-count parity verified (e.g. **130=130** on the sparse-URL corpus;
near-misses `http:/`, `shttp://` → **0 false matches**). **Neutral on
URL-dense** corpora (memory-bound; no gap to close). Class-loop flat;
witness −7.7% incident; multi-literal StatusLine/Teddy remains the **next** arc.

## What this is not

- Not a universal speedup claim: the gain is **corpus-dependent** (large on
  filler-heavy sparse URLs, neutral on dense URL streams).
- Not multi-literal / Teddy acceleration (StatusLine `info|error|warn…req=`):
  follow-up, deliberately out of this train.
- Not a change to match semantics: the prefilter only skips guaranteed
  non-matching filler; the VM always confirms.

## Who should upgrade

Anyone scanning for URL-shaped patterns in mostly non-URL text (logs, crawls,
mixed documents) who saw the 19–21× gap vs rust on #3. No API break.
