# v2026.7.35 — possessive quantifiers and atomic groups (Tier 1)

Feature release. Adds possessive quantifiers (`x*+`, `x++`, `x?+`,
`x{n,m}+`) and atomic groups (`(?>...)`) over a bare or singly-captured
atom, in linear time — a capability neither RE2 nor the Rust `regex`
crate support at all, and parity with `re` (3.11+) / PCRE2 for the
supported shape. No breaking API changes.

## Feature — possessive quantifiers and atomic groups over an atom

`re` and PCRE2 support possessive quantifiers and atomic groups
generally, over any body; REAL now supports the dominant real-world
shape — a possessive quantifier or atomic group wrapping a **bare
single atom** (a literal byte, a character class, or `.`), optionally
inside exactly one capturing group (`(a)*+`), plus an atomic group
with no repeat at all over any deterministic (split-free) body however
compound (`(?>ab)`, `(?>)`). `(?>X*)`-style atomic groups desugar to
the possessive-quantifier case regardless of the inner repeat's own
written form, so the two dominant real-world atomic-group shapes —
`(?>[^"]*)` and `(?>\d+)` — are not rejected as "unbounded".

A possessive quantifier or atomic group over a **compound, repeated
body** (`(?:ab)*+`) or over a genuine **alternation** (`(?>ab|a)`) is
rejected "not supported **yet**" — a design-first spike confirmed the
linear-time argument holds in principle for the general case (the same
bounded sub-VM technique bounded lookaround already ships could
plausibly carry it), but the VM-integration work is separately-scoped
future work, not shipped in this release. See `\ref div_possessive` /
`\ref div_rejected` in the C++ docs for the full accepted/rejected
boundary and the reasoning behind it.

Mechanically: three new opcodes make the match/no-match decision for a
possessive loop at **epsilon-closure time**, not deferred to the
per-byte step — precedented by bounded lookahead's own closure-time
sub-VM evaluation. An earlier design that deferred the decision one
round shipped with a real correctness bug (a lower-priority alternation
sibling could claim a shared convergence point ahead of a
higher-priority possessive thread); it was caught by the differential
fuzzer's own possessive-quantifier generator before this ever shipped,
and the fix is regression-pinned. That's the culture we want this
project to show: the fuzzer found it, not a user.

## Performance — an honest cost, disclosed rather than hidden

The possessive path runs through the general VM, which does not (yet)
participate in the fast-path route selection (lazy-DFA, one-pass,
class-loop) that the equivalent *greedy* pattern enjoys. Measured up to
~4-6× (arm64) / ~18× (x86-64) slower than the greedy equivalent on the
same input — it is the greedy path that is accelerated, not the
possessive path that regressed; absolute cost is ~19 ns/B. A
route-integration arc to close this gap is planned as follow-up work,
not part of this release.

## Coverage

Local line coverage raised from 95.45% to 95.71%, with targeted
behavior tests on the new opcodes' edge cases (miss-at-min, max-reached
on a bounded count, min=0 immediate exit, end-of-text mid-run, `\b`
interaction), the Tier 3 rejection messages, and the parser's
possessive-suffix / atomic-group desugaring paths — not padding.

## Honesty

This ships a real capability gap closed (neither RE2 nor `regex` come
close), a real but scoped divergence from `re`/PCRE2 (compound bodies
and alternation, "not supported yet" — separately tracked, not a
permanent exclusion), and a real, disclosed performance cost on both
measured ISAs rather than a number picked from the friendlier of the
two. The one correctness bug found during development was caught by
this project's own fuzzer before the code ever shipped.
