# v2026.8.7 — two silent wrong answers, and one shape behind both

Both bugs shipped in v2026.8.6. Neither crashes, throws, nor reports anything: they answer wrongly and
say nothing. They come from the same mistake made twice, in code that shares no lines — **a cache or a
hint validated by a key too weak to identify what it stood for.**

## Assignment cleared two of the four identity keys, and `ac_for` was not among them

`regex_immutables` caches four lazily-built artefacts, each guarded by a key holding the address of the
program it was built for. `operator=` cleared two of them. Copy-assigning the underlying
`std::vector` reuses the *destination's* buffer, so `code.data()` does not change — the stale key
matches, and the Aho–Corasick automaton of the **old** pattern is used to answer for the new one.

After `a = b` on a regex `a` that had already run once:

| | expected | returned |
| --- | ---: | ---: |
| new pattern matches nothing | 0 | **3230** |
| new pattern matches 3125 | 3125 | **0** |

**Why the suite missed it.** The existing assignment test assigns a *temporary* — which moves. A move
reallocates, the address changes, and the stale key correctly fails. The test exercised the one form
of assignment that cannot expose the bug. The new test assigns a named lvalue, after warming, and
fails without the fix.

Invalidation is now one function that clears **all four** keys, called by both assignment operators.
It cannot be `constexpr`: `std::atomic::store` is not, and gcc says so under `-Werror=invalid-constexpr`
where clang accepts it.

## A byte equal to the literal's first byte is not the literal

Two inner-literal anchors compared **one byte** and then used the answer to decide how far the route
walks back from a candidate. A prefix that merely repeats that byte was taken for the literal itself:

| pattern | subject | expected | returned |
| --- | --- | --- | --- |
| `\w\d(?:a){2}ax` | `é1aaax` | match | **no match** |
| `(?:\d+xy){1}xz` | `5xyxz` | match | **no match** |

Both anchors now require the **whole** literal — length, and every byte of it — before the route is
armed.

**Why the suite missed it, and why the first review of the report was wrong.** `static_regex` has no
small-haystack guard, so it failed at *any* subject size; the dynamic engine abandons the
inner-literal route below a size floor, so on a short subject the bad hint is never reached and the
pattern matches. This project's first pass tested both patterns on a short dynamic subject, saw them
match, and refuted the report. The shape was tested without controlling the **route** — and the route
was the bug. The regression test pins the armed path.

## The build-time functions were bidding for the scan routes' inline budget

`build_byte_program`, `compute_lazy_alphabet`, `emit_utf8_trie`, `onepass::minimize` and
`detect_fast_shapes` run once per pattern compile and never during a scan, but gcc weighed them in the
translation unit's `--param inline-unit-growth` budget all the same. Marked `cold`, on x86-64:

| row | |
| --- | ---: |
| `words` | **−11.8 %** |
| its ASCII witness | −11.7 % |
| `digits` | −12.2 % |
| worst row (`\p{sc=Han}`) | +4.8 % |

> **Correction, added after release: this magnitude is not portable.** Audited later with a placement
> discriminator, every figure above reproduces on two independent unaligned builds — `words` −11.95 %
> and −12.14 %, `digits` −11.91 % / −12.15 %, witness −11.74 % / −11.84 %, and the +4.8 % cost at
> +4.92 % / +5.02 %. But rebuild both sides with `-falign-loops/-functions/-jumps=16`, which inflates
> the binary by only 1 %, and the same comparison reads **`words` +5.70 %** — the sign reverses; at 32
> bytes it reads −3.34 %. `cold` **is** a code-placement directive: its whole mechanism is to move
> code out of the hot path's neighbourhood, so its measured benefit cannot be separated from placement
> in this translation unit. The annotations are correct and are kept — those functions are cold, and
> the median across the table is +0.15 % / +0.19 %, i.e. neutral overall. What is withdrawn is the
> reading of −11.8 % as a property of the CHANGE; it is a property of this build configuration. The
> evidence originally offered — `words` and its witness moving together — cannot support the claim
> either, for the reason set out in v2026.8.8's notes.

Published with the cost, because it pays on both ISAs and the regression is one row.

## `(?:a)+` was 2.8× slower than `a+`

The quantifier's single-byte promotion — a bare literal byte under an unbounded quantifier becomes a
one-member class, so the class loop takes it — looked past a non-capturing group and gave up. The
group is now peeled first: **1.368 → 0.490 ns/B**. Capturing groups and atomic groups are refused,
since peeling them would change what the match reports or where it can backtrack to.

## The Rust crate's allocation-free capture path has a standing row

`captures_read_at` avoids the per-match allocation `captures_iter` makes, but nothing measured it, so
nothing defended it. A `captures_read/{name}` group now does: **−27.5 %** against the crate's own
`captures_iter`, with REAL ahead on 10 of the 11 cases. The `regex` arm uses that crate's *idiomatic*
path — a hand-rolled `captures_read_at` loop on it proved 2× slower than its own iterator, and
benchmarking a competitor's non-idiomatic path is not a comparison.

## Three design figures described code that no longer runs

They misdirected three separate audits in one day: `regex_set` "~97 % of branches re-probed" (the
expansion is fused; the residue is 7–10 %), route memoisation as an open gain (measured, refuted — the
cascade's depth costs nothing detectable), and an anchors figure asserting the inverse of what the
harness now prints. The failure mode is named in the file: **a figure stated as an open opportunity
outlives the work that closes it**, because closing the work does not require revisiting the prose
that proposed it.
