# v2026.8.20 — a wrong answer, a protocol, and a floor

**BROUILLON — le numéro de version et la date sont fixés à la coupe, pas ici.**

Three things a user notices. One is a **silent wrong result** and is the reason to upgrade. One is a
capability the Python binding was missing. One is a packaging change that drops CPython 3.10.

## A search could return the wrong match

This is the headline, and it is the worst class of defect this project can have: not a crash, not a
refusal, a **different answer** with nothing to signal it.

```cpp
real::regex re("(ab|)bb");
re.search("abbbbbbbbbbbb");     // [0, 4) — "abbb", correct
re.fullmatch("abbbbbbbbbbbb");  // false — and this builds the pattern's immutables
re.search("abbbbbbbbbbbb");     // [1, 3) — "bb". WRONG: the match at 0 is never considered.
```

It did not depend on call order: a fresh `regex` whose first call is `fullmatch` is wrong from its
first `search`. Anything that built the immutables armed it.

**The shape at risk is narrow and precise:** an alternation with an **empty branch** — `(ab|)`,
`(|ab)`, `(a|b|)` — followed by a literal run long enough for the inner-literal scan to select it.
The idiom "optional prefix written as an alternation" (`(www\.|)example`) is exactly this shape.
Every other nullable form — `(a?)bb`, `(a*)bb`, `(a{0,2})bb` — already declined the route and was
never affected; that was verified, not assumed.

**Why.** The inner-literal extraction walks an alternation branch by branch, asking of each "is this
a run of literal bytes". That predicate answers *yes* for an empty one, which is correct where it is
also used — an empty node beside bytes in a concat that is non-empty overall. For an alternation
*branch* it is not enough: an empty branch makes the alternation nullable, and a nullable segment
cannot stand in a reverse-prefix, which must consume what it spans. `bb` was found by memmem at
offset 1, the prefix confirmed at width 0, and the earlier match was skipped. The branch check now
also requires at least one byte.

Found by the differential fuzzer against `std::regex`, whose failing net was named for match flags
while the input set none of them — the flags were never the mechanism.

## Python reads bytes-like subjects where they lie

`bytearray`, `memoryview`, `array`, `mmap` — anything exporting a flat contiguous buffer — were
refused. `re` takes them all. They are now borrowed through the buffer protocol rather than copied,
which is the only reading worth having: a caller who reaches for a `memoryview` is avoiding exactly
the copy `bytes(obj)` would reintroduce.

The subject-type matrix is now **32 of 32 cells identical to `re`**, wording of every refusal
included — compared against `re` as an oracle rather than transcribed.

Three hazards came with it, each measured against `re` rather than reasoned about:

| | |
| --- | --- |
| **Lifetime** | the export is released on every path, including error returns; `finditer` holds it for the iterator's life, which is why mutating a `bytearray` mid-iteration raises `BufferError` here exactly as in `re` |
| **Bounds** | a `Match` pins its subject's *object*, not its bytes, so a mutable subject can shrink under it; slices clamp to the current length — a span of (6,11) over a bytearray since cut to 3 bytes gives `b""`, and the span itself does not move |
| **The GIL** | the scan releases it above 512 B; an export pins the address and length so the scan stays in bounds, and another thread overwriting the bytes in place is the caller's race — one `re` does not have, since it does not release the GIL here |

## The abi3 floor moves to CPython 3.11

**This drops CPython 3.10.** The reason is not stylistic: `Py_buffer`, `PyObject_GetBuffer` and
`PyBuffer_Release` entered the stable ABI **in 3.11**. Under `Py_LIMITED_API` 3.10 the type does not
exist, and no workaround reaches the pointer — `memoryview` answers the question but hands back the
same forbidden struct. Reading a bytes-like subject without copying it is impossible below 3.11.

**Nothing installed breaks.** A 3.10 caller is not served an incompatible wheel: pip resolves to the
newest release that still admits 3.10, which is **2026.8.19**. CPython 3.10 reaches end of life on
**2026-10-31**.

The floor is declared in five places that no two tools read the same way — `requires-python`,
cibuildwheel's `build`, the wheel tag, and `Py_LIMITED_API` twice (`setup.py`'s `-D` and
`_real.cpp`'s `#define`, the latter placed right before `Python.h` and therefore the one that
actually governs the translation unit). `make check-abi3-floor` now asserts all five agree; it was
written because the source `#define` still said 3.10 after the other four moved, and only
`-Wmacro-redefined` noticed.

## Constructs excluded by design now say so — and the escape hatch is offered only where it works

`(?C1)`, `(?R)`, `(?1)`, `(?-1)`, `(?&name)` and `(?P>name)` all produced a generic "unknown
extension": classified `syntax`, worded like a typo, while the documentation presented them as
deliberate exclusions. Each is now named and tagged `unsupported`, which is what a C caller branches
on — it has no exception type and no message contract. Conditional groups and both lookaround
refusals had the same wrong classification.

That widened the reach of the Python fallback hint, which exposed a false promise it already
carried: `unsupported` was taken to mean "a backtracker can run this", and it does not. The two
questions are now separated — `error_kind` describes REAL; whether the remedy exists is asked of
`re` itself, with the same flags the fallback would pass. Where `re` would refuse, the message says
so instead of sending the reader through a door that is not there.

Which fallback takes what, measured on all three:

| construct | Python `fallback=True` | C++ `policy::fallback` | Rust `fallback` |
| --- | --- | --- | --- |
| backreference | yes | yes | no |
| conditional group | **yes** | no | no |
| recursion, subroutine, callout | no | no | no |

## Go: the FindAll* matrix is complete, and its empty-match rule is `regexp`'s

`FindAllStringSubmatchIndex` was the one method missing from the eight-method matrix; it is there.

More consequential: the enumeration now follows `regexp`'s empty-match rule rather than the engine's.
`regexp` ignores an empty match abutting the preceding one; the engine reports it, because its model
is Python `re`, where that match is real. So `regexp.Split("axbxc", -1)` on `x*` gave `["a" "b" "c"]`
while this binding gave `["a" "" "b" "" "c"]`.

`Split` was innocent — it is a verbatim port of `regexp`'s own. The filter belongs in
`FindAllSubmatchIndex`, the single enumeration every `FindAll*` and `Split` derive from, so the rule
is applied once and inherited everywhere, including by `n`, which then clips the *filtered* sequence.
Compared against `regexp` over eleven shapes on five methods each.

## Smaller Python fixes

- **A negative `count` / `maxsplit` did everything instead of nothing.** `re` treats a negative count
  as "no replacements" and a negative maxsplit as "no splits"; both performed the full operation.
- **`\N{...}` was rewritten inside `(?#...)` comments and VERBOSE `#`-to-end-of-line text**, where it
  is not an escape at all — and `RegexSet` did not perform the rewrite on `str` members at all.
- **Subject-type refusals are `re`'s again.** The dispatch asked the *pattern* first, so any subject
  that was not the matching one got the mismatch sentence: `p.findall(None)` was told it had used a
  string pattern on a bytes-like object, which is wrong about `None` twice over.
- **`Pattern.flags` under-reports inline flags** — documented, not changed: `re.compile('(?i)a').flags`
  folds the inline flag into the field, REAL's stays `0`. The flags **do** apply; do not branch on
  `p.flags` after inline syntax.

## Upgrading

**C++ and Python:** no pattern changes meaning except through the wrong-answer fix, which can only
make a result *more* correct.

**Go: results change, and silently.** The empty-match enumeration now follows `regexp`'s rule, so an
empty match abutting the preceding one is dropped — `Split`, `FindAll`, `FindAllString`,
`FindAllIndex`, `FindAllStringIndex` and both submatch forms all return fewer elements for patterns
that can match empty (`x*`, `\s*`, `a?`). The new answers are `regexp`'s, so code written against the
standard library becomes *correct* here where it was wrong before — but code that compensated for the
extra empties will now over-compensate. If you special-cased empty strings out of a `Split` result,
that workaround is what to remove. Patterns that cannot match empty are unaffected.

**Packaging:** if you install the wheel, the floor is now CPython 3.11.
