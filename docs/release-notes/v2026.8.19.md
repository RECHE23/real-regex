# v2026.8.19 — a report closed, a spelling accepted

**An issue closed against a commit you cannot install is a promise half-kept.**
Viorel opened [#6](https://github.com/RECHE23/real-regex/issues/6) with a two-case
minimal. The message was wrong on seven forms, not two. This ships that commit,
the braced `\u{…}` everyone coming from JS or the `regex` crate writes, and the
last two package-level Go entries of the tutorial (`QuoteMeta`, `Match` /
`MatchString`).

## The #6

`(?zi)a` already said `unknown extension` — `z` is the first character after `?`,
so it never enters the flags parser. `re` says the same family. The bug was the
other branch: once a valid flag letter (or `-`) had started a flags group, an
unknown letter fell through to `global flags not at the start of the expression`
or `missing flag after '-'`. A scoped group (`(?iz:a)`) was blamed for a
placement rule it does not have. `(?i-z)a` was the worst: it claimed a missing
flag while a letter was sitting there.

CPython `_parse_flags` reports `unknown flag` before it asks whether the group
was a misplaced global. REAL does the same now, at the letter, at the same
positions `re` names (`at 3`, `at 4`, `at 5`). The genuine placement and
missing-flag messages stay for the cases they actually describe.

REAL's inline flag set is not `re`'s in either direction: it adds `U` (ungreedy,
RE2's spelling) and has no `u` / `L`. `(?iu)` reports `unknown flag` here even
though `re` accepts it. That is by design, not part of the fix.

## `\u{…}`

`\u{e9}` is now a synonym of `\x{e9}` / `\u00e9` — the same `parse_braced_hex_scalar`
path `\N{U+…}` already shares. A class member inherits: `[\u{e9}]` needs no extra
site. `\U{…}` is not this form; REAL's `\U` stays Python's eight hex digits.

`re` rejects the braces (`incomplete escape \u`). Accepting them is a documented
superset, same family as `\N{U+…}` and `\p{…}`: it cannot break re-compatible
code, which could never write it. The docs that said REAL wanted four digits or
braces on `\x` now say the opposite. The v2026.8.18 notes stay historical.

## Go

`QuoteMeta` and the package-level `Match` / `MatchString` are the two entries
v2026.8.18 named as missing. They are here. Signatures match `regexp`
(`Match` / `MatchString` return `(bool, error)`; an invalid pattern is the
error). The compiled handle is closed before return.

`QuoteMeta` delegates to `regexp.QuoteMeta`, not to C++ `compat::re2::QuoteMeta`.
The C++ one escapes a larger set (`user-id` → `user\-id`); both results would
still match, so a matching test would not catch it. A function whose job is to
produce a string the caller logs, compares, or stores would have shipped a
silent divergence. The pin is not `real.QuoteMeta == regexp.QuoteMeta` (a
tautology) but that REAL compiles `QuoteMeta(c)` and `FullMatch`es `c` for every
ASCII byte — and that a leftover wildcard (unescaped `.`) does not also
`FullMatch` `"x"`.

`FindAllIndex` and `FindAllSubmatchIndex` still take no `n`. That is a breaking
change, v0.2.0, not this tag. `Expand` is still absent.

## The parser moved; the matcher did not

`include/real/frontend/ast.hpp` is +73 / −33 against v2026.8.18. Every line is
in the front-end parser, which runs when a pattern is compiled and never during
the scan. The tables in `docs/BENCHMARKS.md` measure throughput in ns/byte on
corpora; they cannot move. What could move, marginally, is the cost of compiling
a pattern, and that is not what those tables measure. They remain stamped
`2026.8.15`.

Writing "no engine change" would be false. Writing "no change these tables can
see, and here is why" is the claim. The stamp is now four releases behind, and
the deferral is knowing rather than empty: `d0dc644` (inner-literal, `pike.hpp`)
is a perf change on a hot path. This release adds nothing those tables can see;
earlier ones did, and a re-measure is owed — it is a bench wagon, not a release
blocker.

## What a newcomer does not see

The Unicode cross-oracle now publishes its verdict instead of a silent skip:
`ucd-skew` on 3.10 (interpreter `unicodedata` 13.0.0 ≠ tables 16.0.0), `skew` on
3.14 (`regex` and UCD 16.0.0 disagree on U+088F). Installing `regex` in CI goes
in `pre-install`; `deps` clones repositories, and putting `regex` there killed
every Python leg. The exhaustive comparison still has not run. Aligning the
tables is a Unicode wagon, not a guard wagon.

`make doc-check` is the instrument for a new C++ member: CI pins Doxygen 1.9.8,
a local 1.17.0 green is a different tool, and a preflight red skips the jobs
that would have exercised the parser on Windows, macOS, and the Rust fuzzer.

## Still not this release

`Captures::expand` remains absent and named as such. `(?C1)` still says
`unknown extension` while `div_rejected` names callouts next to backreferences
and conditionals, which have their own message. Neither has a reason to open
those files today.
