# v2026.7.32 — linear-time fix for case-insensitive literal search + doc corrections

Patch release. Restores the "linear time, always" guarantee for a second class
of patterns that had regressed to quadratic search time (a sibling of the bug
7.31 fixed), and corrects two documentation errors surfaced while measuring
it. No API changes.

## Fix (P0) — quadratic search on `(?i)<literal>` over sparse-match haystacks

`(?i)<literal>` — a case-insensitive literal search, e.g. `(?i)cafe` — could
take **O(n²)** time on a haystack sparse in true matches (a rare literal in a
large text, the common shape for this kind of search): an icase literal loses
its exact-prefix hint (case-folding needs a small first-byte *set*, e.g.
`{c, C}`, not one byte) and routes through the prefilter's memchr cascade,
which handed the **entire remaining haystack** to `memchr` as its search
window on every rejected candidate. Members enumerate in ascending byte
value, so for `{c, C}` the uppercase byte is always checked first — with the
full window — before the far commoner lowercase byte gets a chance to narrow
it; on a stretch of text where the uppercase fold variant does not occur,
every rejected candidate paid a full remaining-haystack scan for a byte that
was never there.

Restored to **linear** time: the cascade's window now grows exponentially
(galloping search, seed 128 B) from a modest probe instead of being handed
the whole remainder up front, bounding one call to roughly twice the distance
to the actual hit regardless of any set member's frequency. Its cost is now
billed to the same deterministic work-counter the 7.31 linearity gate uses
(`prefilter_note_scan`) — the cascade had never been covered by it before,
which is the actual reason that gate did not catch this class of regression
the first time. A new test in the same style (`icase_literal_cascade_
throughput_smoke`) closes that hole; proven to catch the pre-fix regression
by direct revert-and-rerun.

Affects any `search` / `find_iter` / `findall` call on a case-insensitive
literal (`(?i)` on plain text, not a class or a compound pattern) against a
haystack where most of the text does not match — the common "needle in a
large text" shape. Result-invariant — same matches, just no longer quadratic.
On the worst measured case (`(?i)café` over ~1.8 MB of sparse French prose):
~500× faster (483.6 → 0.96 ns/byte), and now 1.5× faster than the rust
`regex` crate on the same pattern, having previously been 166× slower.

## Docs — Unicode benchmark section corrected

`docs/BENCHMARKS.md`'s `## Unicode — comparative` section (added this train)
had two bugs found while re-measuring it post-fix: a copy-pasted ratio cell
(`std::regex` on `\w+` showed PCRE2's ratio, not its own) and an inverted
verdict (`\p{L}+` vs PCRE2-JIT was labeled a "win" at what is, correctly
read, REAL's worst result in that table — REAL 5× slower). Both traced to two
contradicting ratio conventions stated in the same subsection. Fixed: one
convention for the whole section (matching the rest of the document), every
ratio recomputed programmatically from the measured ns/byte pairs rather than
hand-typed, and a new checker (`benchmarks/verify_unicode_ratios.py`) that
asserts every displayed ratio matches its ns/byte pair — proven to catch the
`\p{L}+` regression by reintroducing it on a scratch copy.

The honest verdict this section actually shows: REAL trails PCRE2-JIT on
every Unicode row measured (0.20×–0.96×, worst on `\p{L}+`), beats RE2 on
every comparable row (1.24×–6.02×), and is far ahead of `std::regex`
(13×–40×, as expected — `std::regex` has essentially no Unicode support to
race against). Consistent with the rest of the document's positioning:
linear-time-safe and feature-complete, not the raw-throughput leader — that
is PCRE2-JIT, on Unicode as much as on the ASCII `date`/`literal` shapes in
§A.

`README.md` also undersold a shipped feature: its `\p{…}` description said
only "General_Category and Script." Corrected to General_Category, Script
(`sc=`, short ISO codes), Script_Extensions (`scx=`), and 63 binary
properties (`\p{Alphabetic}`, `\p{Emoji}`, …) — all of which shipped in
7.31's Unicode arc and are covered by the regen tests.

## Honesty

The P0 fix closes a real gap against "linear time, always" — REAL was never
exponential here (no backtracking, so classic ReDoS was never in play), but
the polynomial slowdown was real and shipped in 7.31, discovered by the same
Unicode-comparative benchmarking arc that landed alongside it. The doc
corrections are exactly that — corrections, not new claims: the honest
Unicode verdict is that REAL loses to PCRE2-JIT's throughput and wins on
completeness and the linear-time guarantee, which is the project's
positioning regardless.
