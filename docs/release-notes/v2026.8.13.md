# v2026.8.13 — a veto restored, and a per-call copy removed

A short train, released promptly for one reason: **v2026.8.12 crossed a performance veto this repository
maintains, and the version people install today is the one carrying it.** No answers changed in either
release — this is speed, not correctness — but the guard exists precisely so that this kind of
regression does not ship, and it should not stay crossed while other work accumulates.

## What v2026.8.12 regressed, and why it got out

`make matrix-gate` fails a cell when the routed path is *slower than the core path it replaces*. On a
dense corpus of dates, v2026.8.12's inner-literal batch filler made it so:

| | route | core | verdict |
| --- | ---: | ---: | --- |
| v2026.8.11 | 2.617 | 2.584 | ok |
| v2026.8.12 | **2.883** | 2.563 | **regression** |
| v2026.8.13 | **2.609** | 2.569 | ok |

The mechanism is worth stating because it was not what it looked like. The inner-literal route gives up
on a haystack it judges unprofitable, and that abandon is *sticky* — it was working exactly as designed.
The **walk** was not listening: the new filler asked the route again on every single match, the route
declined every time, and each refusal cost a wasted `memmem` before the per-match path did the real work.
Route counters on that corpus, 3641 matches: **3637 attempts where the previous release made 7.**

The filler now disarms itself for the rest of the walk the moment the route abandons — which is the
behaviour that existed before it. One wasted refill per haystack instead of one per match. The win the
filler was built for is untouched: `\w+@\w+` is still batched at 0.251 engine entries per match, and
`email dense` still reads 2.044 against the core's 8.730.

**Why it shipped:** the canonical pre-push gate in this repository is twenty-four steps and includes that
matrix at step 14. A hand-picked subset of eight was run instead, so a veto written for exactly this case
was bypassed rather than lifted. That is a process failure, not a tooling gap — the gate existed and was
green when finally run.

## One of two bulk copies per call is gone

`basic_match_result`'s constructor took its slot storage **by value**, so the caller's `std::move`
constructed the parameter and the member was then move-constructed from it: two moves. Under gcc on
x86-64 those lowered to two `rep movsq` — 12.15 % and 10.20 % of the inlined per-call path — for a
groupless pattern where each copy carries sixteen bytes, because `rep movs` pays a fixed startup whatever
the volume. Taken by rvalue reference, one of the two is gone (verified in the machine code before any
timing: `rep movs` in the caller goes 2 → 1).

| per-call row | x86-64 | arm64 |
| --- | ---: | ---: |
| anchored match, rejected | **−13.2 %** | **−11.8 %** |
| anchored match, hit | **−10.0 %** | **−8.2 %** |
| exact-length search | **−9.6 %** | **−7.9 %** |
| search inside a longer subject | −8.8 % | **−7.2 %** |

Everything else is indistinguishable from layout noise on both platforms, with no cross-row cost. It was
expected to be an x86-64-only fix, since arm64 has no `rep movs` instruction at all; the gain is the same
on both, so what was removed is the **move** — sixteen bytes, the container's bookkeeping, the
temporary's stack traffic — and not the instruction's startup.

**This is also the first change this project has judged on x86-64.** That host's measurement floors were
27–59 %, which made anything under a third of a doubling invisible; with its CPU governor set to
`performance` they are **1.8–8.3 %**, and the table above exists because of it.

If you build the Python extension, its own call site now moves the slots too, so the binding gets the
same removed copy rather than working around the narrower signature.

## A confidence withdrawn, with no number moving

The Aho-Corasick route is chosen by *candidate density* — how often a branch's first byte appears. That
quantity cannot decide the question. Holding it fixed and varying only the fraction of candidates that
complete a match flips the verdict:

| candidates that complete | 0 % | 25 % | 50 % | 75 % | 100 % |
| --- | ---: | ---: | ---: | ---: | ---: |
| arm64, automaton ÷ cascade | **0.87** | 1.09 | 1.43 | 1.75 | **2.19** |
| x86-64 | **0.56** | 0.76 | 1.00 | 1.34 | **1.90** |

A false start punishes the cascade (verify, reject, resume) and leaves the automaton indifferent; a match
rewards the cascade (it stops) and charges the automaton a per-match return. One number is arbitrating
two forces that oppose each other — the same argument the branch *count* lost, now applying to what
replaced it.

**No constant was retuned**, deliberately: the fix is a second quantity, and retuning against those
tables would move the error rather than remove it. The finding is recorded in the gate's own
documentation, along with a real-world counter-example (a nine-branch alternation over ordinary prose
reads 3.56 ns/B on the automaton against 1.87 on the cascade).

## And a guard for the defect that started all of this

v2026.8.12's headline was that GCC zeroed 4944 bytes per state construction because two thread lists were
held as an array of two. Nothing in this repository could see that: local development and the layout
instrument are clang, the CI matrix's GCC legs build and test without timing, and the cost divided by a
100 KB corpus is 0.0004 ns/byte. A single member array anywhere in that state brings it back.

`make check-state-zeroing` now compiles one translation unit that constructs the state with every real
GCC on the machine and refuses a bulk zeroing in it — step 4b of the local gate. It took three attempts
to get right, and the first two reported OK on a tree that provably has the defect; it is now validated
in **both** directions, which is the only form of validation a guard like this can be trusted on.
