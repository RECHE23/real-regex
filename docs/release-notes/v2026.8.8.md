# v2026.8.8 — four answers where there should have been errors

A correctness train, and nothing else: no new routes, no new shapes, no performance work. Every one of
these was in v2026.8.7 and in every version before it. None crashes, throws, or reports anything —
each **answers**, wrongly, on input the engine had already decided was an error or could not represent.

## A result from a temporary regex borrowed name tables it took with it

`real::regex{"(?<w>[a-z]+)"}.search(text)` returns a result that borrows the regex's pattern text and
its named-group table. Store that result, ask for a group **by name**, and it reads freed memory:

```
==ERROR: AddressSanitizer: heap-use-after-free
  #0 real::basic_match_result<…>::group_index(…) real.hpp:249
freed by:
  #9 real::detail::dynamic_program::~dynamic_program() program.hpp:776
 #13 real::basic_regex<real::detail::dynamic_storage>::~basic_regex() real.hpp:685
```

`find_iter` and `find_all` were already deleted on an rvalue regex for exactly this reason. The single
attempts were not, **and must not be**: the one-expression form is safe — the temporary outlives the
full-expression — and this repository alone has 868 call sites of it. Only a result that outlives the
temporary is unsafe.

So the rvalue path yields `real::owning_match_result`, which owns the context instead of borrowing it.

**Three designs were built and measured before one was kept** — one type with the owner inside
`result_type`, the same with the owner marked `cold`, and two types leaving `result_type` untouched.
The third shipped.

> **Correction, added after release.** These notes originally justified that choice with arm64
> numbers — `words` +5.59 % for the single type, +11.23 % with `cold`, +0.19 % for the split — and
> presented the ASCII witness moving with `words` as proof the first figure was "not layout noise".
> **Those numbers do not reproduce.** Rebuilt on two independent builds, folding the owner into
> `result_type` measures `words` −0.01 % and +0.03 %, witness +0.02 % and +0.03 %, median +0.04 %.
> The original was one build's code placement, and the witness argument was wrong on its own terms:
> two instances of one pattern compile to the same code, so they move together under a placement
> shift exactly as under a real cost. The design is unchanged; its stated justification is corrected.

What holds without any benchmark is the API argument. `owning_match_result` is a **distinct** type
deliberately: no conversion exists that could quietly drop the ownership and hand back the dangling
views it exists to prevent, and the borrowing path — every walk, every attempt on a live regex —
keeps a trivially destructible result rather than one carrying an owning box it can never use. On the
compile-time policy the two collapse into one, `static_storage` keeping its tables in `static
constexpr` objects that outlive every result by construction.

`std::shared_ptr` is the obvious handle and is **forbidden** here: `real::regex` is
constant-evaluable, so its result type must stay literal. The owner allocates through
`std::allocator`, the only constexpr-usable source in C++20 — the same reason `small_vec` grows
through it since v2026.8.6.

**Why the suite missed it:** it had no test that outlived a temporary regex. And the first cut of the
fix carried its own version of the same bug — the implicit copy constructor duplicated the owner but
kept its views pointing into the *original's*. The copy test caught it; the owner is now the single
source of truth, which is what makes the implicit copy correct without a hand-written rule of five.

## A lookaround index that does not fit the field carrying it

`assert_lookaround` holds its index in a `uint16` and nothing checked the cast, so the 65536th
assertion pointed at sub-pattern 0. With `(?=)`×65535 followed by `(?=b)a` the answer is right; at
65536 **the same pattern matched `"a"`** — sub-pattern 0 being the empty lookahead, which always
holds, while the `b` the pattern demands does not occur at all.

Reachable under `max_program_size` because an **empty** lookaround costs only three instructions:
65536 × 3 = 196 608 against the 262 144 cap. With `(?=a)` at four instructions each, the cap bites
first — which is why the shape that exposes this is the cheap one. Guarded exactly as the two class
tables next door already were.

## A group reference that overflows and lands back inside the valid range

`$<digits>` accumulated into a `size_t` with nothing guarding the multiply. Unsigned overflow wraps,
and a wrapped value can fall back below `match.size()`, so the bounds check under it passed:

| replacement | is | became | should |
| --- | --- | --- | --- |
| `$18446744073709551616` | 2^64 | group 0 — **the whole match** | raise |
| `$18446744073709551617` | 2^64+1 | group 1 | raise |

`$99999999999999999999999` already raised — by accident, its wrap landing out of range. The guard is
on the multiply, so every reference that fits is untouched, leading zeros included.

## A class shorthand used as a range endpoint, on one side only

`[a-\d]` already raised `bad character range`. `[\d-z]` did not: the parser returns a negative
sentinel for a set item, the loop moved on, and the `-` was then read as an ordinary member — so the
class quietly became `\d` ∪ `-` ∪ `z`, and matched `"-"`.

This engine had already **chosen** Python's rule by rejecting the mirror case (ECMAScript's Annex B
would allow both); only half of it was implemented. All of `[\d-z]`, `[a-\d]`, `[\w-z]`, `[\d-\w]`,
`[\d-\d]`, `[\s-z]` now agree with CPython character for character, reported position included, and a
`-` that is not between two endpoints stays literal exactly as there: `[\d-]`, `[-\d]`, `[\d\-z]`.

This was the one with real risk — it rejects patterns ECMAScript accepts, and `exhaustive-compat`
runs against `std::regex`. It does not move: 3 218 434 cases, `agree` = 3 213 886, divergences
= 4 548, identical before and after.

## The alias that was wrong from the first commit

`real::match_result`, documented as "the result type of the default, runtime-compiled `real::regex`",
was spelled over `std::vector<std::size_t>` while the dynamic policy's slots are SBO-backed. Naming
the documented type **did not compile** against the function it documented.

Correcting the spelling fixed the instance and left the hole: the alias *restated* a type instead of
asking for it, and a restatement and its subject are free to drift. `real::regex` and
`real::static_regex` never drifted for the opposite reason — they derive. So this one derives too,
`using match_result = regex::result_type`, which makes that class of drift **unrepresentable** rather
than merely detectable.

## What it costs

Published rather than mentioned, on gcc/x86-64, from four independent draws (two rebuilt from
scratch) that agree row by row: `digits` **+9.5 %**, `\p{N}+` +5.2 %, `alt` +5.4 %, `words` +1.6 % and
its ASCII witness +1.6 % — against `(?i)café` **−4.8 %**, `\p{sc=Han}` −3.1 %, `[à-ÿ]+` −3.1 %, `date`
−2.7 %, `lookahead` −2.5 %. Median +0.36 %. arm64 is flat throughout (worst row +0.19 %).

**The mechanism was not established when these notes were written; it is now — it is code
PLACEMENT in the harness's translation unit.** Every out-of-line `real::` symbol is byte-identical
between the two builds, forcing 16- or 32-byte alignment collapses the delta on every row that
carried it, and under forced alignment the delta reappears on *different* rows — which is what a
placement effect does. That also explains the two recovery attempts that died on the numbers
(de-templatising the hot `run`, marking the rvalue overloads `cold`): neither changes alignment. See
design.dox §10.1 for the discriminator.

## Verification

Ten regression tests across two new files, every one of them **proven red without its fix** —
reverting the hunks fails 8 checks in the parser/replacement train, and three tests fail or trip ASan
in the lifetime train. All target the **armed** paths: a temporary regex, a stored result, a lookup by
name.

829 tests, 345 602 checks, 0 failures. `exhaustive-compat` 3 218 434 cases with `agree` identical
before and after every change. `fowler-compat` PASS, counts pinned. Line coverage 96.53 % against the
95.0 floor. All 23 `full-local-gate` steps green, plus `docs-site-gate` verified locally against the
pinned Sphinx toolchain. CI green across 29 jobs.

§A and §Unicode are re-stamped on this tree, on both platforms — Apple M1 Pro under Apple clang 16 and
the x86-64 devbox under g++ 13.3.0 with PCRE2 10.47 pinned — three full harness runs per ISA, minimum
per cell, match counts compared before any ratio was printed. The x86-64 cost above is *why* they are
re-stamped rather than carried over: shipping v2026.8.7's table would have published numbers already
known to be wrong.

**§B (the Python binding table) is NOT re-measured for this train** and still carries its `2026.7.55`
stamp, which is what `make version-check` warns about. Nothing here touches the binding's comparison
against `re`; the warning is accurate and is left standing.
