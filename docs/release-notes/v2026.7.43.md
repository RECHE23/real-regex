# v2026.7.43 — Aho-Corasick multi-literal alternation route (issue #3)

Closes [issue #3](https://github.com/RECHE23/real-regex/issues/3)'s "Alternation" gap: REAL's
existing `small_set` fast path is a first-byte memchr-cascade prefilter capped at 8 distinct
first bytes — an alternation of pure literals past that count (`cat|dog|fish|bird|fox|bear|wolf|
deer|hawk|frog|lion|tiger`, and larger) had no fast path at all, falling to the scalar bitmap
loop. Past a measured branch-count threshold — re-validated against the wired engine (not just a
standalone POC) on two corpus shapes, a mostly-non-matching prose corpus and a majority-matching
one — a dense-trie Aho-Corasick automaton now takes over instead: **2.5–2.6× faster on a
15-literal alternation** (arm64, min-of-11), growing wider the more literals are added, since AC's
own cost stays flat per byte scanned while the branch-by-branch scalar loop it replaces does not.

## Design

`is_fixed_alternation` (the existing recognizer backing `small_set`/`fixed_alternation`) already
structurally guarantees no captures anywhere in the construct it recognizes — an interior `save`
op for a real capture group breaks its byte/klass-only branch-body whitelist before the branch
loop even runs. Verified empirically across every capturing shape (an outer group, per-branch
groups, mixed) rather than assumed: none of them ever reach `fixed_alternation`, so "AC for
non-capturing alternation only" — the safe, recommended scope — is enforced for free by that
pre-existing gate, not by new code written for this arc.

The automaton is built lazily, once per distinct compiled program (mirroring the existing
lazy-DFA/inner-literal-prefix cache-by-program-pointer precedent already in the VM's scratch
state), walking the compiled byte/klass opcode stream directly rather than re-deriving anything
from the source pattern text. An icase literal already folds to a small `klass` opcode at parse
time (REAL's existing case-fold machinery, unrelated to this arc), so AC's construction fans out
over each position's accepted byte set to build every concrete spelling — bounded at 64 expansions
per branch; a branch whose fold combinatorics would exceed that bound declines AC for the *whole*
pattern, falling back to the existing `run_alternation` path unchanged, rather than building an
unboundedly large trie.

Word-boundary wraps (`\b(?:cat|dog|...)\b`) are handled correctly by walking deeper into a
matching state's output-link chain only when the shallowest candidate fails the boundary check: a
*trailing* `\b` depends only on the match's end position (identical for every branch ending there,
so checking it once suffices), but a *leading* `\b` depends on the branch-specific start position,
which does differ across branches sharing one output-link chain — verified via both a dedicated
meta-seam differential entry and the fuzzer below, not just reasoned about.

Storage is pool-based throughout (`std::vector<ac_node>`, zero raw `new`/`delete`) — the design
spike that preceded this arc found the same anti-pattern in an old prototype implementation and
this was written to avoid it deliberately. The automaton's actual construction work
(`add_literal`/`build`/`build_ac_automaton`, run once per distinct program) is marked
`__attribute__((cold))`; the dispatch entry points (`ensure_ac_automaton`/`run_aho_corasick`,
called on every AC-eligible search) are marked `noinline` but deliberately *not* cold, keeping
them fully optimized while out of `pike_vm::run()`'s own function body.

## Proof

`full-local-gate` 18/18 (667 tests, 53199 checks, 0 failed, project-wide line coverage 95.73%,
floor 95.0%). A parity matrix — {case-sensitive, icase} × {with/without `\b`} × {N=11..30 branches}
× {dense-hit, sparse-hit corpora} (400 checks) — plus a large-scale randomized differential fuzzer
(5×100k trials, 1,412,318 checks) against the pre-existing route (toggled via a test-only
`aho_corasick_route_disabled()` seam, the same "route on vs forced off" contract every other
fast-path runner in this engine already carries): zero divergence. Both post-mortem bugs from the
design spike that preceded this arc (alternation declaration order at equal start position;
empty alternation branches) are reproduced as explicit meta-seam seeds, not just asserted fixed.

icase support is verified correct in isolation — a direct unit test of the klass-fan-out
construction logic, bypassing the compiler frontend entirely — since a pre-existing, unrelated
compiler-frontend limit currently keeps any 3+-branch icase alternation off `fixed_alternation`
altogether (confirmed on the pre-D1-AC baseline, not a regression introduced here), making that
scope unreachable through `real::regex`'s own public API today regardless of AC.

## A known, documented limitation: x86+gcc-only `fields [^,]+` regression

An x86-64/gcc A/B (this host is arm64; the x86 leg's numbers are relayed, consistent with this
project's own established two-ISA discipline, not independently re-run here) found a *non*-
alternation class-loop pattern — `fields [^,]+`, `docs/BENCHMARKS.md`'s own tracked §A case —
regressing roughly 39%, despite never dispatching through the new route at all: a class-loop
pattern returns from `run_class_loop` at `pike_vm::run()`'s very first dispatch check, long before
the code ever reaches the alternation/AC branch further down.

A callgrind/cachegrind comparison isolated the cause precisely: `fields`'s executed instruction
count, I-cache misses, and D-cache misses are all identical between the pre- and post-AC builds to
within noise (executed-instruction delta +0.0003%) — ruling out a code-path or memory-access-
pattern change and pointing at the one layer those tools don't model, front-end loop-entry
alignment, apparently nudged by the AC engine's mere presence elsewhere in `pike.hpp`'s
translation unit (`code bloat`, a well-known class of compiler-codegen-neighbor effect).

Two targeted `__attribute__((optimize("align-loops=N")))` fixes were tried and reverted:

- **On `run_class_loop` itself** — measured as a complete no-op. Root-caused directly on this
  host's own gcc-14 (a compiler-attribute/inlining question, not an ISA-specific timing one, so
  verifiable without x86 hardware): a minimal reproduction confirmed GCC's `optimize` attribute on
  an `always_inline` callee does not travel with the inlined copy into its caller — only the
  attribute's *own* function body is affected, and `always_inline` forces that body to live in the
  caller instead. `run_class_loop` is `always_inline`d into `run()`, so the loop that needed
  aligning had, at the object-code level, always lived in `run()`'s body.
- **On `run()` itself instead** — this one *did* align the correct loop (confirmed via disassembly
  on this project's own headers, not just the minimal repro: six `.p2align 6` occurrences inside
  `pike_vm<dynamic_storage::state_type>::run<...>`, versus one incidental occurrence in the
  pre-AC baseline) and did resolve `fields`. But `fields`, `witness [a-z]+`, and `wplus \w+` all
  share this same inlined class-loop body with different alignment optima — forcing one traded the
  `fields` regression for new ones on the other two (+36–38% and +5–9% respectively). No uniform
  alignment satisfies all three simultaneously.

Accepted as a documented regression rather than shipping a fix that *moves* the problem instead of
removing it. The affected surface is narrow (x86-64 **and** gcc specifically; arm64 and clang are
both confirmed unaffected by construction, the attribute never reaching their compiled output —
verified via `c++ -E`), the finding is disclosed here and in `docs/BENCHMARKS.md`'s own Version
row rather than silently absorbed into that document's baseline, and the Alternation route's own
gain is unconditional and considerably larger in absolute terms than this one pattern's cost. The
full diagnostic trail — five earlier fix attempts, all reverted — remains available on this
repository's `backup/d1-ac-12commits` branch for anyone who wants the blow-by-blow.
