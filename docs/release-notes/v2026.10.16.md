# v2026.10.16 — A read past the subject, a lost match in bytes mode, an overflow in `\U`

Three defects found by the long fuzzing run on v2026.10.15, all present since v2026.7.57 or earlier.

## Fixed

- **A line-anchored search could read one byte past the subject.** With `(?m)^` (or another pattern whose search
  tries the position after a final `\n`) over a subject of 512 bytes or more ending in `\n`, the search read the byte
  after the subject when no match started at that last position. The answer was right, but the read is outside the
  subject: on a buffer that ends there, a crash or a sanitizer report. The search now ends at that position.
- **In bytes mode, a byte class ahead of a required literal could lose its matches.** `.` and other byte classes
  match a byte of 0x80 or more there, a UTF-8 continuation byte included; the inner-literal route stepped back over
  them by code points, landed before the match's start and missed it: `(.)((a|\x9d))a.` found nothing in
  `\x9da\x9da\xff\x9d` once the regex had been used. Since v2026.7.57; text mode was not affected. In bytes mode that
  shape is now placed by the reverse automaton, byte by byte.
- **`\U` with eight hexadecimal digits past `\U7FFFFFFF` overflowed a signed sum** before being refused as out of
  range: undefined behaviour, in practice the same refusal. It is now summed unsigned.

## Changed

- **The sanitized test suite stops on undefined behaviour** (`-fno-sanitize-recover=undefined`), as do the robustness
  and C ABI fuzzers; recovering, it printed a report and passed, which is how the `\U` overflow went unseen.
- **The route differential (`make fuzz-routes`) draws bytes-mode patterns** over {a, b, 0x9d} with 0xFF in the
  subjects, and inner literals past the 16 bytes a route keeps.
