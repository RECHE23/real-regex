# v2026.9.4 — an alternation that matched neither of its own branches

This train ships for one reason: **`🥨|é` matched nothing.** Not a diagnostic, not a rounding — a
pattern whose two branches are both correct, whose fused class is the right set, and whose compiled
program is byte-identical in shape to the one that works, answering `false` on both of its own
alternatives. Reported from outside, reproduced on all five surfaces — C++, Python, Rust, the C
ABI and Go — and present in fifteen published releases.

The rest of the train is the invariant that made it possible, one more caller-supplied buffer that was
trusted, and a release-metadata fix.

## The false answer, and the exact shape it took

**An alternation of single code points lost members whenever the branches were written in the wrong
order.** `fuse_single_atom_alternation` recognises `(?:é|à|è)` as `[éàè]` — the same language, and it
must compile to the same program. It collected the branches' code points into the class's range list
**in branch order**, and never sorted them.

Every consumer of a code-point class requires those ranges ascending and disjoint, and two independent
match-time paths split at U+07FF and both read the order as meaning: the U+0080..U+07FF bitmap is
filled by a loop that **stops** at the first range past `cp_page_max` ("ranges are sorted: nothing more
falls in the page"), and everything above is answered by a **binary search**. A descending list
therefore loses members on **both sides of that boundary at once** — the bitmap never reaches the low
one, the search cannot find the high one.

The precise condition: every branch is one code point, and the **first** exceeds U+07FF and is greater
than a later one. Both branches then fail together.

```
🥨|é   on "🥨" → false      on "é" → false        (U+1F968, U+00E9)
€|é    on "€"  → false      on "é" → false        (U+20AC,  U+00E9)
あ|€   on "あ" → false      on "€" → false        (U+3042,  U+20AC)
```

**Nothing astral is required, and the report was wider than its own example.** Two ordinary Latin or
CJK characters in descending order are enough; the emoji in the original report is incidental.

These spellings were never affected and are unchanged:

| spelling | why it was right |
| --- | --- |
| `[🥨é]` | a hand-written class normalises through `coalesce_ranges` |
| `é|🥨` | already ascending |
| `🥨|e` | an ASCII branch lands in the bitmap, never in the ranges |
| `é|à` | both under U+0800, where neither consumer can react |
| `(?i)🥨|é` | the case-fold path normalises |
| `flags::bytes` | the fusion declines in bytes mode by construction |

`coalesce_ranges` — the call `finish_class` already uses — now ends the fusion, which is what its own
documentation had claimed all along by promising that `(?:é|à|è)` and `[éàè]` are one program.

**Affected releases: `v2026.8.10` through `v2026.9.3`, fifteen of them.** The fusion landed on
2026-08-06.

**Why no test caught it, and this is the part worth keeping.** The fusion's tests compare compiled
programs by instruction SHAPE, and the shape is *identical* either way — both forms emit the same
opcodes in the same counts, and the entire difference lives in the interned range order, where a shape
comparison cannot look. Measured: `shape_of("🥨|é") == shape_of("[🥨é]")` was **true with the defect
present**. Every order-independence claim in those tests happened to sit below U+0800, where neither
consumer reacts. The new witness asserts **answers**, and a sabotage that removes the normalisation
turns nine of its checks red while the other 376 000 in the suite stay green.

## The invariant, asked where every class passes through

The requirement above was written only where it is **consumed**, and asked of no producer. Every
producer satisfied it by construction rather than by contract; the one that collected in source order
satisfied it only for inputs that happened to be sorted already.

`cp_ranges_are_normalised` now states it once, and `intern_cp_class` — the single point every
code-point class in every program passes through — refuses a class that fails it with
`code-point class ranges are not normalised`. A throw and not an assertion: the message has to exist in
a release build, and it has to exist during constant evaluation too, so a `static_regex` whose class
arrived unordered stops being a constant expression. That is verified rather than asserted — a
`static_assert` on such an intern fails to compile, with the diagnostic pointing at the gate.

The check demands **order and disjointness, never minimality**: `coalesce_ranges` additionally merges
neighbours that merely touch, but a redundant split costs a comparison and no answer, so refusing one
would reject a correct class.

**It is asked once per DISTINCT class, not once per emission — and that placement is measured.** Asking
on every call is a full pass over the class's range table per emission, on a path that interns the same
class once per repetition: `(?i:\w{256})\w{256}` compiles ~512 classes over `\w`'s table, and the
redundant pass cost **+36 %** (517 → 705 µs), moving the compile-scaling probe's worst local ratio from
6.88 to 8.49 against its 16× bound. CI's `linux-clang` sanitize leg failed that probe on **both**
attempts. Moving the check to the new-class path is not a weakening: the interner dedups by content, so
a class matching an existing one is bit-identical to one already checked when it was first recorded,
and an unordered list can only match another unordered list — which could never have been recorded.
Every distinct class is still checked exactly once, before it exists, and the placement's own risk is
witnessed: an unordered class whose ASCII bitmap *and* range count match a recorded ordered one —
exactly what the dedup screens on before comparing ranges — is still refused.

Honestly bounded: the +36 % is measured, on arm64 at `-O2`. That it is what crossed the 16× bound on a
shared `linux-clang` runner is **not** measured here — the same cost restored under a local sanitizer
build passes. What is on record is that the probe was never red before this train, red 2/2 with the
per-emission pass, and green with the placement.

## `real_expand` validates every span pair, not only the referenced ones

The C ABI's `real_expand` promises that "a span pair outside [0, len] or inverted" is an error, with no
reservation. The check followed the parsed **template**: a pair no group reference reached was never
examined. So `(a)` on `"ab"` with group 0 at `[50, 100)` — or inverted at `[2, 0)` — expanded `"\1"`
happily.

That is the wrong perimeter for this door, and the header says why in its own rationale: **the caller
supplies the matches**, because its flavour enumerates them differently from `real_sub`'s. A binding
off by one in a group its template happens not to reference is exactly the class the sentence
announces.

Every complete pair in the caller's buffer is now checked after the template parse and before a byte is
expanded, by the same rule the referenced path uses — `SIZE_MAX` at the start is an unmatched optional
group and contributes nothing, anything else must lie in `[0, len]` and not be inverted. **A purely
literal template with a corrupt buffer is refused too**; the promise is about the spans, not about what
the template reads. `real_sub` is untouched, the two-call convention is unchanged, and
`nspans == 2 * group_count` remains unclaimed.

## `date-released` is the commit's calendar day

`make release` stamped `CITATION.cff` from `date -u`, while the guard that compares the stamp to the
tag reads the tag's **local** `creatordate`. The two disagree for anything cut after 20:00 local, and
the guard is structurally mute during the operation that violates it: it is gated on the tag existing,
and the recipe stamps *before* tagging. The stamp now takes the commit's calendar day. `v2026.9.3`
permanently carries `date-released: 2026-09-08`; no tag was moved.

## Benchmarks: the tables do not move, and the stamp stays at `2026.8.15`

Fourth train in a row, same reason and no new argument: `docs/BENCHMARKS.md` declares a **two-ISA**
regime and only arm64 was available. Publishing one leg would produce a table whose halves describe
different trees. **No cell was re-run and none is edited.**

**This train changes answers, so 9.2's argument is not available and is not reused.** What is claimed
instead is narrower and was grepped rather than asserted:

- **No cell has the shape whose answer changed.** No benchmark pattern is a single-code-point
  alternation with a non-ASCII branch — the only non-ASCII `|` characters anywhere in `benchmarks/` are
  markdown table separators. The two fusing patterns that do exist, `(a|b|c)` and `(a|a)*…c`, are
  ASCII: measured, they emit **zero** `klass_cp` instructions, because an ASCII fused set lives in the
  bitmap and never in the ranges, so neither the sort nor the gate is on their path.
- **The gate's cost IS reached by cell patterns, and that is not hidden.**
  `((?:ERROR|WARN|FATAL):\s+.*)` interns a code-point class through `\s` and `.`, so "unreachable" is
  not the argument.
- **It is invisible because it lands outside every timed region.** Verified per harness rather than
  assumed: `bench_minimal.cpp:309`, `matrix4d.cpp:219`–`224` and `shift_or_census.cpp:216` all build
  their patterns before the measured loop, which receives an already-compiled regex.
- **Two cells DO time a compilation, and they are named:** the ReDoS rows at
  `bench_engines.cpp:688` and `:696` construct inside the timed lambda. Their patterns are `(a+)+b` and
  `^(a+)+$` — measured, **zero** `klass_cp`, so they never reach the gate.

So the reach of this train is a scope statement, not a paired measurement. No instrument was run
against the previous tree, `GATE_STRICT` is asserted nowhere, and the veto matrix was not exercised for
this train.

## Upgrading

**Everyone:** a patch. No source break, no API addition, no behaviour change other than the fixed
answers above — if you have an alternation of single non-ASCII code points anywhere, it may start
matching where it did not.

**C ABI callers:** `real_expand` now refuses a corrupt spans array even when the template does not name
the offending group. A caller that was passing garbage in an unreferenced pair and getting an answer
will now get `(size_t)-1` and the span message. That is the documented contract, arriving late.

**Go:** module `v0.3.3`, a patch. The Go *surface* did not change — the vendored engine header did,
and the fixed answers arrive with it: `real.MustCompile("🥨|é").MatchString("é")` was false and is now
true, like everywhere else.
