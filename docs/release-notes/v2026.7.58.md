# v2026.7.58 — the membership accessors stop paying for themselves

A **performance** release on the byte- and code-point-class scan paths. No API
changes, no behaviour changes: every span, every capture group and every match
count is byte-identical to v2026.7.57, verified as a differential against the same
engine with the routes switched off rather than asserted — 494 pattern × subject
pairs on spans, 28 on every capture group of every match.

## The row this was about

`\b\w+\b` has been this repository's largest tracked scan deficit for three
releases, disclosed and not chased each time. It moves here, and not by touching
`\b`:

| criterion row | v2026.7.57 | v2026.7.58 | vs the `regex` crate |
| --- | ---: | ---: | :--- |
| `find/word_bound` | 317.8 µs | **261.6** | 1.90× behind → **1.56× behind** |
| `captures/word_bound` | 453.2 | **318.5** | 2.71× behind → **1.91× behind** |

Direct harness, same 64 KiB corpus, arm64 wall clock: `\d+` **−40.1 %**, `\w+` and
`\b\w+\b` **−17.7 %** each.

## What it turned out to be

Three separate things, all found by profiling per function rather than by
reasoning about the code. That distinction is the honest lede of this train:
**seven hypotheses were measured and refuted, and every fix came from a profile.**

**The accessors were being emitted out of line.** On a 64 KiB `[a-z]+` walk
`class_table` cost 6.23 M instructions as its own symbol against 1.44 M when
inlined — its call frame cost more than its body. Two causes: `derive_class_table`
had been split out to keep the 256-iteration loop out of the accessor but carried
no attribute, so the compiler simply inlined it back; and the accessor itself needs
the decision taken away from the compiler. `noinline` on the derive, `always_inline`
on all three accessors. clang was already inlining `class_table` and *not* the two
code-point accessors, which is why the code-point families gain most on arm64 and
the byte family on x86-64.

**The per-regex flags were three allocations where one word does.** A pattern with
no code-point class still allocated two one-element `std::vector<std::atomic<char>>`
it would never read, on every regex construction. They are now one bit per row in a
single atomic word, with a vector only for patterns carrying more than 64 interned
classes. arm64 first use: `[a-z]+` +10.8 % → **+4.4 %**.

**A compare that a caller can prove unnecessary.** The accessors re-checked, on
every `run()` — so per *match* on a walk, 11 327 times over 64 KiB on `[a-z]+` —
that the state's cached row still belonged to the current program, a pointer chase
through the view. Neither caller in `real.hpp` can violate that: the walk
iterator's state is its own member with the program fixed, and the single-search
helper builds its state fresh. Both now say so through a `StateBoundToProgram`
template parameter, and the branch is folded away at compile time rather than
predicted. It defaults to false, so an embedder holding a state across regexes (the
Python binding, the meta-seam harness) keeps the compare with no source change.

## What it costs

Stated at full precision because two of these are regressions:

| | vs v2026.7.57 |
| --- | :--- |
| `first_use/fields`, `/digits`, `/class` | **+4.1 %, +3.6 %, +3.3 %** |
| `captures/class`, `find/digits`, `captures/digits` | +2.6 %, +2.5 %, +2.1 % |
| `[a-z]+` 64 KiB walk, arm64 | **+2.8 %** |
| `dog` 64 KiB walk, arm64 | neutral (distributions overlap over 12 runs) |
| every other criterion row | within ±1.7 % |

x86-64 instruction counts move the other way on the byte family: `[a-z]+`
**−3.7 %**, `[^,]+` −0.6 %, `\b\w+\b` −0.0 %, `\w+` +0.2 %, `\d+` +0.2 %,
`dog` +1.1 %. The `[a-z]+` walk is the one row where the two ISAs disagree in sign,
and it is the residual this train did not close.

`static_regex` keeps its v2026.7.57 promise: all eleven table rows and all ten
inner-literal rows still favour the compile-time regex, walk 1.00×–1.19× and single
shot 1.22×–72.76×.

## Two faults this train introduced, and what caught them

Both are stated because neither was visible to the instrument the work was tuned
against.

**Three cache fields added mid-struct.** Placed next to the array they belong with
in `basic_pike_state`, they shifted every field after them: `find/word_bound` went
**+32.3 %** on one round and +28.4 % on a second, on a pattern that reads none of
them. Appended last instead, the same row reads +1.1 %. Only the C ABI path sees
it — it crosses per match, where the C++ harnesses call the engine directly and
measure the same edit as neutral. `pattern_hints` documents this exact fault for its
own trailing fields and says "appended last" five times over; the rule was in the
file and was read after the consequence was measured.

**A version stamp bumped by a directory-wide `git add`.** `include/real/version.hpp`
went to 58 while the other six stamps stayed at 57, and `preflight`'s version-check
— which exists for exactly this — failed and skipped every other CI job on two
consecutive commits. Reverted; the guard did its job.

## The seven refuted hypotheses

Recorded so they are not retried, since each cost a measurement cycle: a state memo
of the last verified row (0.9 %), caching the row pointer (nothing), `noinline` as
the arm64 cost (nothing — it stays because x86-64 wants it), moving `lookaround` to
the end of the state struct per this repository's own placement rule (nothing, to
the byte), code placement (the gap holds under default, 32- and 64-byte function
alignment), the lazy lookaround itself (nothing, though bisecting points at it in
isolation — the cost is distributed across commits, not attributable to one), and
the row's memory location (copying it back into the VM state changed nothing).

## Verification

Criterion figures come from an interleaved A/B against v2026.7.57 with the same
bench file on both sides, one group at a time, machine otherwise idle: two rounds
for `find`, `compile` and `first_use`, and four rounds of 5 s for `captures`, where
two rows first read as noise (`captures/digits` showed +8.7 % on two rounds and
+2.1 % on four, with per-round dispersion falling to 0.1 %). `compile` is carried as
a control throughout — nothing in this train touches it, and it stays within 1.8 %.

`full-local-gate` on every commit in the train, plus CI green including the
windows-msvc leg. 777 tests, 345 104 checks. Coverage 95.59 % (floor 95.0), including new probes for
the flag-overflow path: a 96-branch alternation compiles to 96 interned byte classes
— verified, not assumed — so flag indices 64..95 land in the vector half.
clang-tidy clean, MISRA 0, sanitizers clean, Go and Python bindings green, gcc-14
green.

## Notes

Nothing here changes what REAL matches. The linear-time / ReDoS-safe guarantee and
the bounded lookarounds are unchanged, and so is the API.
